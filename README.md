# NetVision

ネットワーク機器のインベントリ・保守期限・ライフサイクルをまとめて管理するツールです。

「この機器はいつ保守が切れるのか」「どの型番がサポート終了を迎えるのか」を
Excel 台帳ではなく、常に最新の状態で見られるようにすることを目的にしています。

## できること（現時点）

- 機器インベントリ — ベンダー / 型番 / シリアル / OS バージョン / 導入日 / 設置場所（拠点・ラック・U）を管理
- 保守契約管理 — 1台に複数の契約を紐付け、最も遠い終了日を「保守期限」として自動判定
- ライフサイクル判定 — 保守期限・EoS（販売終了）・EoL（サポート終了）の残日数を計算し、重要度を色分け
  - `expired` 期限切れ / `critical` 90日以内 / `warning` 365日以内 / `ok` / `unknown` 情報未登録
  - しきい値は環境変数で変更可能
- ダッシュボード — 重要度別の台数、期限が近い機器、ベンダー別台数を一覧
- 更改計画向けの抽出 — 「今後 N 日以内に期限を迎える機器」を期限が近い順に取得
- 既存台帳の取り込み — Excel / CSV をそのまま読み込み、列名を自動で対応付け（後述）
- 台帳の書き出し — Excel / CSV で出力。書き出したファイルはそのまま取り込み直せる（後述）
- 変更履歴 — 機器・保守契約・拠点への変更をすべて自動記録。誰がいつ何をどう変えたかを追える
- 最適化の指摘 — 払わなくてよい保守費とリスクを洗い出し、年間削減見込みを算出
- 将来構成シナリオ — 台帳に触れずに「入れ替えたらどうなるか」を試算し、現状と比較
- Config の取り込み — running-config / show 出力から構成情報を自動抽出、世代管理と差分表示
- トポロジー図 — LLDP / CDP から結線を自動推定し、人が配置を整えて仕上げる図エディタ。VLAN / VRF で絞り込み、現場向けのシンプル図も出せる
- VLAN 台帳 — 番号ごとの名称・用途を人が管理。アクセス / ネイティブ / トランクを分けて持ち、両端の食い違いを図で出す
- リファレンス管理 — EoL 情報を型番単位で管理。出典と取得日を必ず記録し、鮮度を可視化
- 脆弱性の突合 — CVE と機器のバージョンを突き合わせ、悪用確認済み（CISA KEV）を最優先で提示
- ベンダードキュメント — コマンドリファレンスやマニュアルを、ベンダー・型番・バージョン範囲で管理。古い版は消さない
- Config テンプレート — 機器を選ぶとその書式に合ったテンプレートで設定変更用 Config を生成（実機には投入しない）
- Config 計画 — 現行フル / 将来フル / その差分を出し分け。差分は将来フルに収束することを機械で検証してから渡す
- 更改支援 — 保守期限と EoL から年度別の更改計画を組み、その機器を止めたときの影響範囲を出す
- 脆弱性への対処 — CVE の該当から、その機器で何をすればいいか（修正版 / 回避コマンド / 根拠資料 / テンプレート）まで1本でつなぐ
- 対処状況の台帳 — 機器 × CVE を1件ずつ追い、対処漏れを構造的に防ぐ。対応版 Config も生成する

`unknown`（情報未登録）を `ok` より重い扱いにしているのは、台帳の抜けを見逃さないためです。

## 起動方法

まず自分の端末で試したい場合は [docs/GETTING_STARTED.md](docs/GETTING_STARTED.md) を見てください。
サーバーは不要で、Docker も要らない1台完結モードがあります。

```bash
cd backend && .venv/bin/python -m scripts.standalone   # http://127.0.0.1:8000
```

データは `~/.netvision/netvision.db` の1ファイルに入るので、コピーすればバックアップになります。
認証がまだ無いため、既定では自分の端末からのみ待ち受けます。

### 閉域環境へ導入する

インターネットに繋がらない環境へは、持ち込み用の1ファイルを作って渡します。
閉域側で Git もネットも使いません。

```bash
./packaging/make-bundle.sh        # ネット側で実行 → dist/netvision-YYYYMMDD.tar.gz
```

閉域側は展開して `./install.sh`（Windows は `install.bat`）だけ。必要なのは Python 3.11 以上のみで、
Node.js もインターネットも要りません。

Python すら入れられない環境向けに、インストール不要版も作れます。
python.org の embeddable package を同梱するので、ZIP を展開して `NetVision.bat` を
ダブルクリックするだけで動きます（管理者権限もレジストリ変更も不要）。

```bash
./packaging/make-bundle-windows.sh   # → dist/NetVision-YYYYMMDD-windows.zip
```

手順は [docs/INSTALL.md](docs/INSTALL.md)、運用は [docs/OPERATIONS.md](docs/OPERATIONS.md) に
まとめています。Windows で Python を入れられない場合は
[docs/WINDOWS_BEGINNER.md](docs/WINDOWS_BEGINNER.md) に、画面の操作から順に書いてあります。

### Docker Compose（本番と同じ構成）

```bash
docker compose up --build
```

- 画面: http://localhost:8080
- API ドキュメント（Swagger UI）: http://localhost:8000/docs

デモデータを入れる場合:

```bash
docker compose exec backend python -m scripts.seed
```

### プレビュー（Vercel）

PR ごとに実際の画面を触って確認できます。DB の用意は不要で、デモデータが自動で入ります。
手順と制約は [docs/PREVIEW.md](docs/PREVIEW.md) を参照してください。

本番運用の想定は変わりません。 閉域のオンプレが前提です。サーバーに載せるのが
理想ですが、採用の前に現場のノートPCで実データを試せないと話が進みません。
導入テストと1人での運用は `scripts.standalone`（SQLite）で完結します。
複数人で共有する段階で Docker Compose と Postgres に載せます。
プレビューは確認用で、データは永続せず、実機の情報を入れる場所ではありません。

## 既存台帳の取り込み

ゼロから入力し直す前提を置かず、いま使っている Excel / CSV 台帳をそのまま読み込むことを
移行の起点にしています。画面は「台帳の取り込み」から。

対応形式は `.csv` / `.tsv` / `.xlsx`。CSV は Shift_JIS（CP932）・BOM 付き UTF-8 のどちらでも読めます。

### 仕組み

1. 列名の自動対応付け — 「機器名」「メーカー」「型式」「導入年月日」「保守期限」のような
   現場でよく使われる表記を別名辞書で解決します。全角/半角・大文字小文字・記号の揺れも吸収します。
2. 判別できない列は画面で指定 — 自動判別を上書きしたり、取り込まない列を選べます。
3. 必ずプレビューしてから取り込む — 行ごとに「新規 / 更新 / スキップ / エラー」と理由を表示します。
4. エラーが1行でもあれば取り込まない — 中途半端に一部だけ入る状態を作りません。
5. エラー行だけ書き出して直せる — エラーになった行を、元の列のまま
   「エラー内容」列を付けて CSV に出力します。Excel で直してそのまま取り込み直せます。

### 取り込み時の扱い

| 項目 | 挙動 |
|---|---|
| 既存機器の判定 | ホスト名（既定）またはシリアル番号で突き合わせ。選択可 |
| 既存機器の更新 | 値が入っている列だけ反映。台帳の空欄で既存値を消さない |
| 拠点 | 台帳の拠点名から自動作成し、機器に紐付け |
| 保守契約 | 保守終了日の列があれば契約を作成。同じ契約は重複登録しない |
| 日付 | `2024/4/1` `2024-04-01` `2024年4月1日` `2024/04` などを解釈 |
| 金額 | `¥480,000` `480000円` のような表記を解釈 |
| 種別・状態 | `L3SW` `FW` `ルーター` `稼動中` `撤去済み` などの日本語表記を解釈 |

記入用テンプレート CSV は画面からダウンロードできます（`GET /api/v1/import/template.csv`、
Excel でそのまま開けるよう BOM 付き UTF-8）。

## 台帳の書き出し

機器一覧の絞り込み条件をそのまま引き継いで、Excel / CSV に書き出せます。

| 形式 | 用途 |
|---|---|
| Excel (.xlsx) | 日付は日付セル・金額は数値セルで出力。見出し固定とオートフィルター付き |
| CSV | BOM 付き UTF-8。Excel で開いても文字化けせず、そのまま取り込み直せる |
| CSV (Shift_JIS) | UTF-8 を読めない古いツールへ渡す場合のみ。画面では小さく出す |

書き出したファイルは、そのまま取り込み直せます。取り込みは文字コードを自分で判別し
（BOM 付き UTF-8 / Shift_JIS / UTF-8）、算出列は読み飛ばすので、書き出したものを
そのまま戻せます。出力の列見出しは取り込み側の項目名と一致させてあるため、次の運用が
回ります。

```
書き出し → Excel で一括編集 → 取り込み
```

これにより、最初の1回さえ取り込めば、以降はフォーマットの揺れを気にせず運用できます。
往復して内容が変わらないことは自動テストで担保しています（`tests/test_export_api.py`）。

算出列（保守期限・残日数・経過年数・アラート）も既定で出力されます。これらは取り込み対象では
ないため、取り込み時は自動的に「取り込まない」列として扱われます。稟議・見積依頼用の資料には
そのまま使えます。

## 変更履歴

機器・保守契約・拠点への変更はすべて自動で記録されます。画面での編集も台帳の取り込みも、
同じ履歴に残ります。

- 更新は項目ごとに「変更前 → 変更後」を記録します
- 対象が削除された後も、何を削除したかが履歴から読めます
- 取り込み1回分の変更は同じバッチIDでまとまるため、「あの取り込みで何が変わったか」を追えます
- 発生元（画面操作 / 台帳の取り込み / デモデータ）で絞り込めます

実装は SQLAlchemy のフラッシュに介入する方式（`app/services/audit.py`）です。
個々のAPIに記録処理を書くと必ず抜けが出るため、1か所で全ての変更を捕捉しています。

## 最適化の指摘

登録済みの台帳から、外部データを使わずに判定できる「無駄」と「リスク」を洗い出します。
削減できる年額の見込みも出すので、契約見直しや更改の稟議の根拠に使えます。

| 分類 | 指摘の例 |
|---|---|
| 無駄をなくす | 撤去済み機器に保守契約が残っている / 予備機に稼働機と同等の保守 / 契約期間の重複 / EoL より先まで伸びた契約 |
| リスクを減らす | サポート終了済みなのに稼働中 / 稼働中なのに有効な保守契約がない / 導入から7年超 |
| 台帳を整える | EoL も保守期限も未登録 / 設置拠点が未登録 |
| 契約をまとめる | 同じ型番なのに保守ベンダーが分かれている |

## 将来構成シナリオ

「この機器を入れ替えたらどうなるか」を、実際の台帳に一切触れずに試算します。

- 「期限が近い機器から入れ替え案のたたき台を作る」で、ゼロから並べる手間を省けます
- 入れ替え / 新規追加 / 撤去 / 据え置き を並べ、台数・単価・保守年額・想定EoLを入力
- 現状と適用後を同じ指標（台数・年間保守費・サポート切れ台数・平均経過年数）で比較
- 初期投資と年間保守費の増減を算出
- 評価時点（`target_date`）を将来に置けば、「その時点で何台が期限切れになっているか」も見られます
- 検討中 / 稟議中 / 承認済み / 見送り の状態を持てます

対象の機器が台帳から削除されても案は残り（何を検討していたかは名前で残る）、
比較時に警告が出ます。

## Config の取り込み

running-config や show 出力を読み込み、機器情報・インターフェース・VLAN・隣接情報を抽出します。
対応ベンダーは次のとおりです（自動判別）。

| ベンダー | 系統 | 備考 |
|---|---|---|
| Cisco | IOS / IOS-XE / NX-OS | Catalyst 2960 / 2960-X / 3850 / 9300 / 9500 などを確認済み |
| Juniper | Junos | |
| Fortinet | FortiOS | |
| NEC | IX シリーズ | IX2000 / IX3000。`device-name`、`GigaEthernet0.0` 形式 |
| NEC | QX シリーズ | QX-S。H3C Comware ベースで、否定は `undo` |

`show version` `show cdp neighbors detail` などを1ファイルにまとめたものでも読めます。
CSV と同じく Shift_JIS / UTF-8 のどちらでも構いません。

### 抽出するもの

| 種別 | 内容 |
|---|---|
| 機器情報 | ホスト名、型番、シリアル、OS名、OSバージョン |
| インターフェース | 名前、description、IPアドレス、モード、アクセス VLAN / ネイティブ VLAN / トランク許可 VLAN、VRF、shutdown 状態 |
| VLAN | ID と名前 |
| VRF | 名前、RD、説明（VPN インスタンス / routing-instance / VDOM を含む） |
| 隣接情報 | LLDP / CDP のネイバー（detail 形式・表形式の両方） |

### 台帳がまだ空のとき

「台帳に無い機器を Config から登録する」を有効にすると、Config から機器を作れます。
実 Config で立ち上げるときの入口です。

ただし型番が読み取れない Config は登録しません。型番はこのツールの軸で、EoL も脆弱性も
型番で引くため、空のまま登録すると判定できない機器が黙って増えます。plain な running-config には
型番が入っていないので、その場合は `show version` の出力も一緒に取り込んでください。

### 台帳との関係（重要）

Config から読み取った値で台帳を自動上書きしません。 実機と台帳が食い違っていること自体が
情報だからです。取り込み時は差分を提示するだけで、反映するかどうかは人が選びます。

さらに、`running-config` の `version 15.2` のようにConfig 側の情報が粗いだけの場合は
差分として扱いません（適用しても台帳の `15.2(7)E6` を劣化させないため）。

Config の原文は世代ごとに保存され、前の世代との差分を表示できます。同じ内容を再取り込みしても
世代は増えません（sha256 で判定）。変更追跡・監査の証跡として使えます。

## 時刻の扱い

保存は UTC、表示は使う人の時刻に分けています。拠点や利用者が増えても基準を1つに
保てるためです。表示側は既定で日本時間（`NETVISION_DISPLAY_TIMEZONE` で変更可）。

API はタイムゾーン付き（`+00:00`）で返します。付けずに返すと、ブラウザが
それを現地時刻と解釈して9時間ずれます。見た目は壊れずそれらしい時刻が出るので、
ずれていることに気づきにくい壊れ方をします。

書き出した図の「◯◯時点」には地域名（JST）まで入れます。別の場所で読まれたときに、
どの時刻か分からないと突き合わせできないためです。

## トポロジー図

Config を取り込むだけで、結線が自動で組み上がります。 LLDP / CDP のネイバー情報から
「どの機器のどのポートが、どの機器のどのポートに繋がっているか」を推定します。

- `Gi1/0/2` と `GigabitEthernet1/0/2`、`sw2.example.com` と `sw2` のような表記ゆれは吸収します
- 両側の機器から同じ結線が見えたものは「確認済み」として区別します（実線 / 点線）
- 台帳に無い機器と繋がっている場合は、記載漏れの可能性として報告します
- 機器が後から登録された場合は「Config から結線を作り直す」で再推定できます

図の上では次のことができます。

- ノードをドラッグして配置を整える（配置は保存され、機器が増えても崩れません）
- ノード同士をつないで手で線を引く（自動再推定しても手で引いた線は消えません）
- 線を選んで削除、レイヤ（物理 / L2 / L3 / 論理）ごとに別の配置を持つ
- ノードの色は保守期限・EoL のアラート状態と連動します

### VLAN で絞り込む

Config から読み取った VLAN を、番号と名前つきで一覧します。
チェックを入れると、その VLAN を持たない機器が薄くなります。

消さずに薄くするのは、選んだ VLAN が「どこまで伸びていないか」も同時に見えた方が
構成を掴みやすいためです。「VLAN 20 はどこまで伸びているのか」に図で答えられます。

VLAN を1つだけ選んだ状態で書き出すと、そのセグメントだけの構成図になります
（見出しにも VLAN 番号が入ります）。セグメント単位で資料を作るときに使えます。

数百の VLAN がある場合に備えて、チップは検索で絞り込めます（選択中のものは常に残ります）。

### アクセス / ネイティブ / トランクを分けて持つ

VLAN の事故はほぼ全部この3つの混同から出ます。混ぜて持つと、そもそも気づけません。

| 種別 | 持ち方 |
|---|---|
| アクセス VLAN | `Interface.vlan` |
| ネイティブ VLAN | `Interface.native_vlan` |
| トランク許可 VLAN | `Interface.trunk_vlans`（`10,20,30-40` の形で1カラムに畳む） |

1ポートに数十 VLAN 載ることがあるため、許可 VLAN は行に展開せず範囲のまま持ちます。
許可 VLAN を書いていないトランク（＝全許可）は番号に展開せず `all` として持ち、
その機器に定義されている VLAN と突き合わせて解決します。展開して保存すると、
あとから VLAN が増えたときに古い一覧が残ってしまうためです。

書式はベンダーごとに違いますが、意味は同じなので同じ形に寄せます。

| ベンダー | トランク許可 | ネイティブ |
|---|---|---|
| Cisco | `switchport trunk allowed vlan 10,20`（`add` / `remove` / `except` / `none` 対応） | `switchport trunk native vlan N` |
| NEC QX（Comware） | `port trunk permit vlan 10 20 to 30` / `port hybrid vlan ... tagged` | `port trunk pvid vlan N` |
| Juniper | `vlan members [ v10 v20 ]`（名前を番号に解決） | `native-vlan-id N` |

結線が実際に運んでいる VLANは、両端のポート設定を突き合わせて出します。
片側にしか無い VLAN（許可漏れ）とネイティブの食い違いは、図の上で線がオレンジになり、
ラベルに ⚠ が付きます。「繋がっているのに通らない」の典型なので、気づける形にしてあります。

### VLAN 台帳（名称・用途を人が書く）

実機の Config に書ける VLAN 名は短く、機器ごとに表記も揺れます（同じセグメントが
`SRV` と `SERVERS` になっている等）。数十〜数百の VLAN を扱う現場では、
どれが何のためのセグメントかを人が書ける場所が要ります。

そこで、実機の観測値（`device_vlans`）とは別に VLAN 台帳（`vlans`）を持ちます。

- 名称・用途・管理部署・サブネット・備考を登録できます
- Config を取り込み直しても上書きされません
- 実機の名前も並べて表示するので、食い違えば「機器側の設定が古い」と分かります
- 「実機の名前で下書きを作る」で一括して埋められます（人が書いた行は触りません）

一覧には2つの印が出ます。

- 未登録 … 実機には居るのに台帳に無い VLAN。素性の分からないセグメントです
- 定義なし … どの機器にも VLAN 定義が無いのに、トランクの許可には残っている状態

### VRF（機器の中の仮想ルーター）で絞り込む

1台の中で経路表を分ける機能です。呼び方はベンダーごとに違いますが、
同じ列に並べた方が機器をまたいで見るときに揃うので1つの表で扱います。

| ベンダー | 呼び方 | Config |
|---|---|---|
| Cisco | VRF | `vrf definition NAME` / `ip vrf NAME` |
| NEC IX | VRF | `ip vrf NAME` |
| NEC QX | VPN インスタンス | `ip vpn-instance NAME` |
| Juniper | routing-instance | `instance-type virtual-router` / `vrf`（`forwarding` は除外） |
| Fortinet | VDOM | `config vdom` |

図の上で同じ線に見えても、VRF が違えば通信できません。 トポロジー図で VRF を選ぶと
その VRF に属する機器だけが残ります。同じ VRF 名で機器ごとに RD が違えば「RD 不一致」を出します。

定義が別ファイルにあってもポートが参照していれば一覧に載せます。
「ポートは VRF に入っているのに VRF が無いことになる」方が困るためです。

### シンプル図（現場で使う図）

「シンプル表示」にすると、機器名と結線だけになります。型番・IP・保守状態・VLAN を
一切載せません。作業手順書や現場での指差し確認に使う図に余計な情報が入っていると、
読み違いのもとになるためです。書き出しも `style=simple` で同じ形になります。

シンプル図では、片側からしか確認できていない結線も実線で描きます。破線は
「取り込みの確からしさ」の話で、現場で見る図に混ぜると「未接続」と読み違えられるためです。
日付と台数だけは残します（日付の無い構成図はあとから信用できないため）。

### ポート名の出し方

構成図でポート名が読めなくなる原因は2つある。

1本の線に2つのポート名を並べると、どちら側か分からない。
「左が上位」のような規則を覚える必要が出て、図の向きが変われば規則は成り立たず、
逆に読んでしまう。そこでポート名はそれぞれの機器側に置く。ポートの隣にあれば
規則は要らない。両端のラベルは線の反対側に振り分けるので、機器が近くても重ならない。

名前が長い。 `TenGigabitEthernet1/1/1` はそのまま出すと線より長くなる。
3通りから選べる。

| 表記 | 出るもの |
|---|---|
| 略記（既定） | `Te1/1/1` |
| 番号だけ | `1/1/1`（種別は色で表すので、その分だけ文字を削れる） |
| そのまま | `TenGigabitEthernet1/1/1` |

種別の名前は機器の箱に書く。 色だけだと凡例を探しに行くことになり、視線が
図の外へ出てしまう。`GigabitEthernet` が機器の隣にあれば、そこだけ見れば分かる。
線のラベルと同じ色を使うので、1台に複数の種別があっても対応が付く。

色分けは 100M / 1G / 10G / 25G-40G / 100G / 論理集約 / 仮想。
凡例には実際に使われている種別だけを出す（使っていない色を並べても読み手が困る）。

種別が判別できない名前（`port1` など）は番号だけにしない。色にも情報が
乗らないまま元の名前が消えてしまうためで、削るのは「色に移した分だけ」に留める。

「線に沿わせる」を選ぶと、ポート名が線の向きに合わせて回ります。
上下逆さまにはならないよう、必要なら半回転させて向きを揃えます。

人が線に付けた名前（`本社⇔支社 専用線` など）はポート名とは性質が違うので、
これまでどおり線の中央に出します。

### 図の上で文字が被らないこと

自動生成した図でラベルが機器や他のラベルに重なっているのは、置き場所を
考えていないだけなので、当たり判定を持たせている。

1. 置きたい場所の候補を、良い順（機器に近い順）に並べる
2. 機器の箱・既に置いたラベルと重ならない最初の候補を採る
3. どこにも入らなければ文字を短くする（`GigabitEthernet1/0/1` → `Gi1/0/1` → `1/0/1`）

重ねるくらいなら略す。 略した場合は元の名前を `<title>` に入れてあるので、
ブラウザで開けばマウスを乗せて確認できる。

ラベルは線の中点を越えない。越えると相手側の機器の方が近くなり、
「どちらのポートか」が位置で分からなくなる。

検証は生成側とは別経路で行う。出力した SVG を読み直し、実際に描かれた矩形の
重なりを見る。乱数で200通りの配置を振る試験と、自動配置そのものの試験を通している。

> 人が機器を重なるほど寄せた場合は、どう置いても収まらない。そのときは
> 最も重なりの小さい位置に逃がす。図が出せなくなる方が困るため。

### 図の向きと、表での書き出し

自動配置は上下（種別を横の段にする）と左右（種別を縦の列にする）を選べます。
横長の紙や画面に貼るときは左右の方が収まります。人が動かした配置はそのまま残ります。

図が要らない場面もあります。作業指示・工事依頼・検収の突合で欲しいのは、並べ替えと
絞り込みができる表なので、結線表を Excel / CSV で書き出せます。
図で ⚠ が出る食い違い（許可漏れ・ネイティブ不一致）は、表でも「注意」列に出して
行を色付けします。表だけ見て作業する人が見落とすと意味がないためです。

### 拠点で絞る

拠点を選ぶと、その拠点の機器だけが残ります。書き出すとその拠点だけの構成図に
なり、見出しにも拠点名が入ります。現場では自分の拠点だけを見たいことが多いためです。

絞り込みの外に出た対向は、簡易表示で残します。 線ごと消してしまうと、
その拠点が「どこにも繋がっていない」図になります。実際には上位に繋がっているので、
相手がいることだけは残す必要があります。

簡易表示は破線の枠にして、この図の対象ではないことを見た目で示します。
出すのは相手の名前・所属拠点・相手側のポートだけで、型番や保守状態は載せません
（本体と同じ見た目にすると、その拠点の機器だと読まれてしまうため）。
位置は実際の相手の方向へ伸ばした先に置くので、どちら側に出ていく回線かは読み取れます。

VLAN / VRF で絞ったときも同じです。不要なら `show_peers=false` で消せます。

### 図をファイルに出す

「図をファイルに出す（SVG）」で、設計書や報告書に貼れる形で書き出せます。

スクリーンショットではなくベクタ（SVG）で出します。 印刷や拡大で潰れず、画面に
入りきらない範囲も切れません。Word / PowerPoint / Excel はそのまま挿入できます（Office 2016 以降）。

- 画面で整えた配置がそのまま反映されます
- 凡例（保守・EoL の状態、実線＝両側確認済み / 破線＝片側のみ）が付きます
- いつ時点の図かが必ず入ります。資料に貼った後で鮮度が分からなくなるのを防ぐためです

構成が変わったら出し直すだけなので、設計書の図が実態から離れていく問題そのものに効きます。

## リファレンス管理（EoL / 脆弱性）

外部への通信は一切行いません。 閉域環境での運用を前提に、
オフラインでの持ち込みを唯一かつ第一級の経路にしています。

### EoL は型番に紐づける

EoL は本来「型番の属性」です。機器ごとに持たせると同じ日付を何度も入力することになり、
ベンダーが訂正したときに全台直す羽目になります。そこで製品マスターに正規化しています。

```
製品リファレンス（ベンダー + 型番）
  ├ EoS / EoL / ソフトウェア保守終了 / 最終サポート日 / 推奨後継機
  ├ 出典（手入力 / CSV / NVD / KEV / ベンダー資料）
  ├ 出典URL
  └ 情報取得日   ← 「いつ時点の情報か」を必ず持つ
        ↓ ベンダー+型番で自動解決（大文字小文字の揺れは吸収）
機器（個別の事情があれば機器側の値が優先される）
```

これにより「C9500-40X の EoL が変わった」を1回の更新で該当機器すべてに反映できます。
機器詳細には EoL が製品マスター由来か機器個別の入力かを表示します。

### 鮮度の可視化

リファレンスは放っておけば古くなります。自動更新されない以上、
いつ時点の情報で判断しているかを運用者が意識できないと使えません。

- 取得日から `NETVISION_REFERENCE_STALE_DAYS`（既定180日）を過ぎたら「要更新」を表示
- リファレンスが未登録の型番を一覧表示（その機器は EoL を判定できない）
- 最も古い取得日をダッシュボードに表示

### 脆弱性データの取り込み

JSON を置くだけで、形式は中身から自動判別します。

| 形式 | 入手元 | 備考 |
|---|---|---|
| NVD 2.0 | NIST NVD | CPE からバージョン範囲を組み立てる |
| CISA KEV | CISA | 実際に悪用が確認された脆弱性。優先度判断で最も効く |
| 簡易形式 | ベンダー PSIRT を手で整理 | 型番のワイルドカード指定（`C9500*`）に対応 |

突合はベンダー・型番・OSバージョンで行い、何で一致したかを必ず表示します
（「バージョン 17.09.04a が影響範囲に含まれる」）。根拠を示せない判定は運用で使えないためです。

バージョン比較は semver ではなく自然順比較で、`17.09.04` と `17.9.4`、
`15.2(7)E6`、`21.4R3-S5.4` のような表記を正しく大小比較できます。

OSバージョンが未登録の機器は判定できないため、その台数を明示します（見落とし防止）。

### 自動取得について

公式ソースの自動取得はベンダーによって難易度が大きく異なります（Cisco EoX API と
NVD / CISA KEV は API があり、Juniper・Fortinet は実質手動）。
現状は全ベンダーを同じ手順で扱えるオフライン取り込みに統一しています。
オンライン同期を足す場合も、この取り込み経路の上にアダプタとして載る形になります。

## ベンダードキュメント（コマンドリファレンス / マニュアル）

コマンドの書式はメーカー・型番・バージョンで変わります。資料も同じ3軸で管理します。

```
資料（ベンダー ＋ 型番 ＋ 適用バージョン範囲）
  ├ 種別（コマンドリファレンス / コンフィグガイド / リリースノート / …）
  ├ 適用バージョン  17.9.0 〜 17.9.99（範囲。空なら全バージョン共通）
  ├ 実体ファイル（PDF など。省略可、URL だけの登録もできる）
  └ 後継資料へのリンク（superseded_by）
        ↓ ベンダー + 型番 + 稼働中バージョンで自動解決
機器  →「この機器で使える資料」を逆引き
```

### 古い版を消さない（設計上の約束）

現場によっては古いバージョンが現役です。新しい版を登録しても、旧版は削除されません。

- 新版を登録したら「後継を指定」でリンクするだけ。旧版の行はそのまま残る
- 一覧は既定で旧版も表示（`include_superseded=false` で現行のみ）
- 17.9 で動いている機器からは、17.12 の版が出た後も 17.9 向けの資料が引かれる
- 明示的な削除 API はあるが、UI では「版が新しくなっただけなら後継指定を使ってください」と確認する

型番は空欄でベンダー全体、`C9500*` で前方一致（シリーズ共通資料）を表せます。

### ファイルの保管

実体は DB ではなくファイル領域（`NETVISION_DOCUMENT_STORAGE_PATH`）に置き、
内容の SHA-256 でパスを決めます。同じファイルを2回登録しても実体は1つで、
片方を消してももう片方が参照している限りファイルは残ります。

> バックアップは2系統必要です。 DB（メタデータ）とファイル領域（実体）の両方を取ってください。
> Docker Compose では `documents` ボリュームが実体の置き場です。

### 自動取得について

閉域運用が前提のため、アプリからの外部通信は一切行いません。
資料は手動アップロード（またはURLの記録のみ）で登録します。
入手元URLと取得日を残せるので、後から「どこから持ってきた版か」を追えます。

## Config テンプレート

設定変更用の Config を、機器に合った書式で生成します。

- テンプレートは資料と同じ3軸（ベンダー / 型番 / バージョン範囲）で管理
- 機器を選ぶと、そのバージョンに合うテンプレートだけが候補に出る
- 根拠にしたマニュアル（`source_document_id`）を紐付けられる
- 本文は Jinja2 記法。`{{ vlan_id }}` のような変数に加え、`device.hostname` や
  `interfaces` ループで台帳・Config 取り込み済みの値をそのまま差し込める

```
vlan {{ vlan_id }}
 name {{ vlan_name }}
!
interface {{ interface }}
 description {{ vlan_name }} ({{ device.hostname }})
 switchport mode access
 switchport access vlan {{ vlan_id }}
```

### 事故を防ぐための作り

- 生成するだけで、実機には一切投入しません。 内容を確認して手で流し込む前提です
- 未定義の変数は空文字にせずエラーにします（`{{ vlna_id }}` のような打ち間違いで
  壊れた config が出ると気付けないため）
- 必須変数が埋まっていなければ「必須の変数「VLAN 名」が入力されていません」と明示
- 適用バージョン範囲から外れた機器に当てた場合は生成しつつ警告を出します
  （現場判断で流用したい場面があるため、禁止ではなく警告）
- テンプレートはサンドボックス（`SandboxedEnvironment`）で展開し、内部構造には触れられません

## Config 計画（現行フル / 将来フル / 差分）

1つの機器について「今こうなっている」と「こうしたい」を持ち、用途の違う3つを出します。

| 出力 | 何に使うか |
|---|---|
| 現行フル | 機器故障時の復旧。取り込んだ running-config そのまま |
| 将来フル | 更改で入る新しい機器にそのまま投入する |
| 差分 | 更改に合わせて既存機器に当てる投入コマンド |
| 切り戻し | 差分を当てた後、元に戻す |

### 差分は検証してから渡す

3つのうち差分が一番危ないので、正しさを作り方で担保しています。

1. 現行と将来を両方とも木にする（テキストの行差分では取らない）
2. 木の差分から投入コマンドを生成する
3. 生成したコマンドをもう一度読み直して現行に当て直し、将来フルと一致するか確かめる
4. 一致しなければコマンドを返さない。収束しなかった箇所を名指しで表示する

3 が肝です。「差分を作る処理」と「検証する処理」を別経路にしてあるので、生成側の
書き間違い（`no` の付け方を誤った、消し忘れた、順序を壊した）はそのまま検証で落ちます。
台帳の「書き出し → 取り込み」を往復で担保したのと同じ考え方です。

ランダムに変形した config 20,000 通りで、誤った差分が出ないことを確認しています。

### 木にしてから比べる理由

行単位のテキスト差分では、次のような壊れ方をします。

- 同じ行（`shutdown` など）が複数のブロックに現れて取り違える
- ブロックの境界を跨いで削除してしまう
- `no ...` を単なる別の行として扱ってしまう
- 値を書き換えただけの行を「1行削除 + 1行追加」と誤解する
  （`description` が投入の一瞬だけ消える）

そこで config を木にし、`no X` は「X が無い状態」として畳みます。
値を1つしか持てないコマンド（`description`, `ip address` など）はコマンド名までを
キーにするので、値の変更は1件の置き換えになります。

### 特に注意している箇所

- 順序が意味を持つブロック（ACL / prefix-list / route-map）は行単位で足し引きしません。
  末尾への追記だけなら追記、途中に挟む・並べ替える場合は消してから入れ直し、
  その間フィルターが効かないことを警告します
- 消し方はベンダーで違うので、`no` / `delete` / `unset` を方言として分けています
  （Cisco IOS・IOS-XE・NX-OS / Junos の set 形式 / FortiOS）
- 前提コマンド（`switchport mode access` の前に `switchport` が要る等）を補います
- 通信・接続に影響する操作（インターフェース削除、閉塞、IP 削除、ACL 作り直し、
  管理アクセス系の削除）を名指しで警告します
- 切り戻しコマンドも同時に生成し、こちらも「現行に戻りきるか」を検証します。
  戻りきらない場合は出さず、現行 config の保存を促します

### 原理的な限界（隠さずに出しています）

機器の既定値をツールは知りません。そのため「将来 config に書かれていない」が
「既定のままでよい」なのか「消したい」なのかは、config テキストだけでは決まりません。
ここは削除として扱い、削除がある差分では必ず警告を出します。

そして生成するだけで、実機には投入しません。 内容を確認して手で流し込む前提です。

## 脆弱性への対処

脆弱性を「見つける」ところまでは公開データでできます。できないのはその先で、
「じゃあどうするか」は公開データに機械可読な形で入っていません。
NVD にあるのは説明文と参照URLだけ、回避策はベンダーのアドバイザリに文章で書いてあるだけです。

そこで全自動にはせず、こう分けています。

| 機械がやること | 人が1回やること |
|---|---|
| 該当の判定（ベンダー・型番・バージョン） | 回避策の手順を書く |
| 修正版の推定と「上げれば直るか」の判定 | 確認した人と日付を残す |
| その機器で引ける資料・テンプレートの提示 | 根拠にした資料を紐付ける |

一度書いた対処は3軸（ベンダー / 型番 / バージョン範囲）で保存され、同じ型番・
同じバージョン帯の機器すべてで自動的に引き当てられます。 1台分書けば、同型機は
そのまま対処済みになります。「一度調べたことを二度と調べ直さない」がここの狙いです。

対処の種類は「修正版へ上げる / 設定で回避する / 影響を下げる / リスクを受容する /
構成上影響しない」から選べます。受容や非該当も理由付きで残せるようにしてあるのは、
判断した記録が無いと毎回同じ議論をやり直すことになるためです。

対処が未登録の CVE は件数を明示し、手掛かりとしてその機器の資料を提示します。
黙って空で返すと「対処済み」と見分けが付かないためです。

## 対処状況の台帳（対処漏れを防ぐ）

機器を1台ずつ開いて確認する運用は必ず漏れます。漏れる経路は主に4つあり、
それぞれを構造で塞いでいます。

| 漏れる経路 | 塞ぎ方 |
|---|---|
| 全体で何件残っているか見えない | 機器 × CVE を1件ずつ台帳に持ち、未対応件数を常に出す |
| 「対処を書いた」＝「入れた」に見える | 対処の登録と、機器ごとの対処状況を別に持つ |
| 暫定対処を恒久対処と混同する | 「暫定対処済み」は該当が残っている扱いにして数え続ける |
| 状況が変わっても気付かない | 洗い直しで差分を検出し、必要なら判断を差し戻す |

### 暫定と恒久を分ける理由

回避策を当てても機器のバージョンは変わらないので該当は残ります。
これを恒久対処と同じ「済み」にすると、直っていない機器が永久に見えなくなります。
そこで状態を分けています。

- `暫定対処済み` … 設定で回避した。該当は残るので「暫定対処のみ」として数え続ける
- `恒久対処済み` … 修正版へ上げた。洗い直しで自動的に該当しなくなる
- `リスク受容` … 理由の入力が必須。判断の記録が無いと毎回同じ議論をやり直すため
- `影響なし` … 構成上そもそも影響しない

### 「やったつもり」を現行 Config で裏取りする

対処を適用したと申告しても、実際に入っているとは限りません。
取り込み済みの running-config に対処の設定が入っているかを機械で確認できます。

投入コマンドの差分が空になる＝その設定は既に入っている、という判定です。
裏が取れていない申告は「済みだが未確認」として集計に残ります。

### 状況が変わったら差し戻す

洗い直し（`POST /exposures/sync`）で次を検出します。

- 新しい CVE を取り込んだ → 該当する全機器に未対応として立つ
- 新しい機器が入った → その機器の該当が立つ
- 判断した時点とバージョンが変わった → 判断を差し戻し、理由を残す
- 修正版へ上げた → 自動的に「該当しなくなった」
- 一度閉じたが再び影響範囲に入った（切り戻しなど）→ 差し戻す

判断した時点のバージョンを覚えているのがポイントです。
「あのとき大丈夫と判断した前提」が崩れたことを検出できます。

## 対応版 Config

対処から、その機器に投入するものを起こします。出るものは Config 計画と同じ4つです。

| 出力 | 用途 |
|---|---|
| 現行フル | 投入前の状態 |
| 対応版フル | 現行に対処を当てた姿。再構築・更改時にそのまま入れる |
| 差分 | 既存機器に当てる投入コマンド |
| 切り戻し | 投入後に戻す |

差分は Config 計画と同じエンジンを通すので、対応版フルに収束することを
機械で検証してからでないと出ません。

対処用テンプレートが紐付いていればそれを使い、無ければ手順の本文をコマンドとして
扱います（後者は「文章が混ざっていないか確認してください」と注意を添えます）。

## 更改支援

「いつ・何台・いくら」を年度で束ねて出します。年度は日本の会計年度（4月〜翌3月）です。

- 期限は保守期限と EoL の早い方を採ります。保守が切れれば壊れても直せず、
  EoL を過ぎれば部品がありません。遅い方を見ると間に合わなくなります
- 既に期限を過ぎている機器は「今年度に対応すべきもの」として今年度へ寄せます
- 期限が分からない機器は黙って落とさず別枠で表示します（計画からの漏れを防ぐため）
- 金額は年間保守費から逆算した概算です。稟議には見積で置き換えてください

### 更改時の影響範囲

トポロジー上でその機器を取り除き、基幹から辿れなくなる機器を名前で出します。
停止時間の調整と周知の範囲を決めるのに必要な情報なので、台数ではなく機器名で示します。

- 冗長経路があれば「経路が失われる機器はありません」と出ます
- 単一障害点になっている機器は、更改計画の一覧にも「N台に影響」と表示されます

### モデルを置く場合

用途で必要な賢さが違います。資料の要約や分類は小さいモデルで足り、Config の
下書きやレビューは大きいモデルが要ります。役割ごとに分けて置けます。

```
NETVISION_LLM_PROFILES=[
  {"role": "quick", "url": "http://127.0.0.1:11434/v1", "model": "qwen2.5:3b"},
  {"role": "deep",  "url": "http://10.0.0.50:8000/v1",  "model": "qwen2.5-coder:14b"}
]
```

置いていない役割は、置いてある方へ回します（`deep` が無ければ `quick` が答える）。
1つだけ置く場合は `NETVISION_LLM_URL` と `NETVISION_LLM_MODEL` で足ります。


### 資料を根拠に Config を下書きする

モデルを置くと、「Config 計画」の将来フルを編集しているときに、やりたいことを
言葉で書いて下書きを作れます。作りは3段です。

1. 取り込んだベンダー資料の中から、その依頼に関係する章を探す（DB の中だけで完結）
2. その章に出てくる書き方だけを材料に、下書きを起こす
3. 出てきた行を資料と突き合わせ、裏付けの無い行と、通信に影響する行に印を付ける

3 は必ず通ります。モデルが無い環境でも 1 と 3 は動くので、資料から拾ったコマンドが
手がかりとして出ます。ここで作るのは下書きだけで、実機には投入しません。

### 客先ごとに設定を分ける

現場ごとに、置き場所・しきい値・モデルの宛先が少しずつ違います。共通の `.env` に
書き足すと、どれがその現場の都合なのか分からなくなるので、現場ぶんは別ファイルに
します。

```
NETVISION_ENV_FILE=config/aomori.env python -m uvicorn app.main:app
```

見本は `config/customer.env.sample` です。実際の値が入ったファイル（`config/*.env`）は
管理IP や鍵が入るため Git には入れません。

設定しなければ、どこへも繋がずに規則ベースだけで動きます。置く場合も、
宛先が社内・手元（127.0.0.1 / 10.x / 192.168.x / ドメインの付かない名前）
でなければ繋ぎません。事業者の API を使うときだけ
`NETVISION_LLM_ALLOW_EXTERNAL=true` を明示します。設定を1つ書き換えただけで
実機の Config が社外へ出ていく、ということが起きない作りにしてあります。
