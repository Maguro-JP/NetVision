# 日報・週報・月報

報告と計画を出す。開発はしない。走っている `long-dev` が、ここで書いた優先と計画を読む。

| 周期 | 役目 | 起きる時刻（既定） |
|---|---|---|
| daily | 前日を確かめ、今日の優先を書く | 毎日 09:00 JST |
| weekly | 1週間を評価し、来週の計画と価値改善を1つ決める。PR を整理する | 月曜 09:00 JST |
| monthly | 前月を総括し、今月の目標を週単位に分解する | 1日 09:00 JST |

判断の土台は `long-dev/references/principles.md`。作業量ではなくプロダクトが良くなることが目的。

## 引数

`dev-report daily` `dev-report weekly` `dev-report monthly`。
無ければ、今日が1日なら monthly、月曜なら weekly、それ以外は daily。
1日が月曜なら monthly だけ書く。monthly が weekly を含む。

## 共通の約束

- 調べるのは git の履歴、`docs/knowledge/`、`docs/reports/` の前回分。コードは必要なところだけ
- 報告は `docs/reports/` に残す。`daily/YYYY-MM-DD.md` `weekly/YYYY-Www.md` `monthly/YYYY-MM.md`
- 報告のためにコードを変えない。変更が無かった日は無かったと書く
- 週報の PR 整理だけは書き込みを伴う。`solo-pr-flow` の判定に従う

## daily

1. 前日の変更を見る。`git log --since=yesterday`、PR とマージ、直したバグ、足したテスト、書いたドキュメント。`docs/knowledge/` と前回の日報も読む
2. プロジェクトを見直す。新しいバグ、未解決の問題、AI 精度、UX、UI、性能、セキュリティ、技術的負債、テスト、将来のリスク
3. 今日の優先を1〜3個決めて書く。開発はここではしない。走っている `long-dev` がこれを読む
4. 分かったことがあれば `docs/knowledge/` に足す
5. `docs/reports/pending.md` の判断待ちを読み、答えの付いていないものを日報に載せる
6. 日報を書く

報告の形。

```
# YYYY-MM-DD
やったこと: 
良くなったこと: 
AI 精度: 前後の数字。測っていなければ「測っていない」
直したバグ: 
テスト: 出力の要点
知識: docs/knowledge/ に足した項目
GitHub: PR 番号、マージの有無
Actions: 走った回数
残り: 
判断待ち: pending.md のうち答えの無いもの。1件1行で、決めてほしいことと推す案
次に優先するもの: 
```

変更不要だった日は、見た観点と理由を1行で書く。それも報告。

## weekly

1. 今週を評価する。実装した機能、直したバグ、AI 精度、UX、性能、セキュリティ、テスト、技術的負債、知識、GitHub、Actions の使用量
2. 未解決の問題を洗い出し、Critical / High / Medium / Low に分ける
3. 来週の計画を決める。最低1つ、利用者に価値のある新機能か、はっきりした価値改善を入れる。無理な機能追加はしない。既存の改善や精度向上の方が価値が高いならそちら
4. PR を整理する。検証済みで問題なければマージ。不要なブランチと PR を消す
5. Actions の使用量を見て、無駄が無かったか確かめる

報告の形。

```
# YYYY-Www
成果: 
改善: 
AI 精度: 
得た知識: 
解決した問題: 
未解決（Critical/High/Medium/Low）: 
GitHub: 
Actions: 
来週の目標: 
来週のタスク: 
新機能または価値改善: 
リスク: 
```

## monthly

1. 前月を評価する。新機能、バグ、AI 精度、UX、UI、性能、セキュリティ、安定性、テスト、コード品質、技術的負債、利用者の価値、知識、GitHub、Actions
2. プロダクト全体を見直す。強み、弱み、ボトルネック、精度の問題、UX の問題、技術的な問題、将来のリスク
3. 今月の目標を決める。利用者の価値、品質、精度、安定性、性能、セキュリティ、保守性から総合で
4. 週ごとに分解する。各週に目標、タスク、新機能、精度改善、技術改善、テスト、完了条件
5. 優先順位を付ける。重要度、影響、効果、コスト、リスク
6. トークン、Actions、時間を無駄にしない計画にする。品質に要るコストは削らない
7. 今月重点的に蓄える知識を決める

報告の形。

```
# YYYY-MM
前月の成果: 
前月の問題: 
品質の評価: 
AI 精度: 
技術的負債: 
得た知識: 
今月の目標: 
週ごとの計画: 第1週 / 第2週 / 第3週 / 第4週
新機能: 
精度改善の計画: 
技術改善の計画: 
リスク: 
完了条件: 
```

## 定期実行

`scheduler` で3つ作る。daily 毎日 09:00 JST、weekly 月曜、monthly 1日。
1回の起動は報告を書くだけなので短い。long-dev は 10:00 に別の Routine で再起動され、翌朝 09:00 に終わる。
報告はその直後の状態を書く。

## 他のスキルとの関係

- 終わりの無い自律開発: `long-dev`。原則は `long-dev/references/principles.md`
- 周ごとの作業: `auto-dev`
- 定期実行の設定: `scheduler`
- PR の整理: `solo-pr-flow`
