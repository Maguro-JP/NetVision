# 失敗の記録

起きたことだけを書く。一般論は書かない。
1件は4行。場面は「次から」を差し込むときの索引になるので、短い名詞で書く。
新しいものを上に足す。

## 2026-10-25 マージ前のテストが、変えた所のテストを流していなかった
場面: テスト、マージ
起きたこと: あるリポジトリで、ある部品を変えてテストの台本を exit=0 で通してマージしたが、その台本は別のディレクトリだけを流し、変えた部品のテストを流していなかった。押すと落ちる不具合を 2 版のあいだ通した
判定の誤り: 「テストの台本が通った」を「変えた所のテストが通った」と読み替えた
次から: 変えた所のテストが、マージ前のテストに入っているかを先に見る。入っていなければ、足してから流す

## 2026-10-14 パイプの後ろの終了コードを、処理の成功と読んだ
場面: 裏で処理を走らせ、出力を tail で絞るとき
起きたこと: `python3 ... | tail -1; echo "exit=$?"` が exit=0 を返したが、処理は落ちて出力のファイルが無かった。`$?` は tail の終了コードだった（あるリポジトリ）
判定の誤り: 「終了コードを見る」を守ったつもりで、どのコマンドの終了コードかを見ていなかった
次から: 出力はファイルへ書き（`> log 2>&1; echo "exit=$?"`）、絞るのはその後にする。パイプを使うなら `${PIPESTATUS[0]}` を見る。終わったら出力のファイルが在るかを ls で確かめる

## 2026-10-14 テストとコミットを 1 つのコマンドに並べ、落ちたまま push した
場面: テスト、コミット
起きたこと: テストを流してコミットと push を 1 つのコマンドに並べ、1 件落ちた（1 failed）出力を見る前に push まで進んだ（あるリポジトリ）
判定の誤り: テストの結果を見てからコミットする順番を、1 つのコマンドにまとめて飛ばした
次から: テストとコミットは別のコマンドに分ける。テストの最後の行が passed だけ（failed が無い）のを見てからコミットする
