# 失敗の記録

起きたことだけを書く。一般論は書かない。
1件は4行。場面は「次から」を差し込むときの索引になるので、短い名詞で書く。
新しいものを上に足す。

## 2026-09-25 long-dev に auto-dev の止まる条件をそのまま継がせた
場面: long-dev、スキル
起きたこと: AdaptiveAIStudio の long-dev が PR のマージ可否など3つを利用者に聞いて止まり、翌日の Routine まで何もしなかった。Routine 用に E=23h を毎回書かせてもいた
判定の誤り: 期限のある auto-dev の「当たったら止まる」を、終わりの無い long-dev にそのまま使った
次から: long-dev は条件に当たった件だけを脇に置き、判断待ちに書いて次の作業へ進む。期限は付けない。止まるのは利用者が止めろと言ったときだけ

## 2026-09-24 結びつけ先を見ずに、動く Routine を止めて作り直した
場面: Routine
起きたこと: AdaptiveAIStudio の Routine 4つを「古い作り方だから動かない」と無効にし、新しいセッションに結びつけて作り直した。実際は利用者が AdaptiveAIStudio を開いて long-dev を回していたセッションに結びついていて、そのまま動くものだった
判定の誤り: `persistent_session_id` の先のセッションが何を開いているかを `get_session` で見ずに、作り方の名前だけで判定した
次から: Routine を止める前に結びつけ先の `session_context.sources` を見る。対象リポジトリがあれば止めない

## 2026-09-24 手元のツールの制約を Routine の仕様だと書いた
場面: Routine、スキル、ツール
起きたこと: `create_trigger` にリポジトリの引数が無いのを「新しいセッションは空になる仕様」と書き、「自分自身に結びつける」を正解にした。公式は Routine をプロンプト・リポジトリ・connector の3点セットと定義していた。`create_session` に `source_url` があり、それに結びつければ通った
判定の誤り: 使っているツールが公式の作成画面と同じ項目を持つか確かめず、ツールの欠けを設計だと思った
次から: 動かないときは公式の定義を先に読み、手元のツール一覧と突き合わせる。欠けている引数があれば、別のツールで補う経路を試してから「できない」と書く

## 2026-09-24 Routine を「毎回新しいセッションで」と書いた
場面: Routine、スキル
起きたこと: 新しいセッションで起こした Routine は sources と mcp_servers が空で、clone も push もできなかった。AdaptiveAIStudio で止まり、Daikenja で再現した
判定の誤り: トークンを減らすために「新しいセッション」を勧め、起きた環境に何が付くかを確かめなかった
次から: Routine は自分自身に結びつける。仕組みの説明は、この環境で1回起こして観測してから書く

## 2026-09-23 設計を勝手に縮めた
場面: 設計、スキル
起きたこと: 本体は毎時・毎日・毎週・毎月で回す設計なのに、「まず週1だけ」に縮めて作った
判定の誤り: トークンの心配を、相手の設計より先に置いた。費用は伝えるもので、私が減らすものではない
次から: 相手の設計はそのまま作る。費用は数字で横に書く。減らすかは相手が決める

## 2026-09-22 CI が赤いまま PR をマージした
場面: マージ
起きたこと: RuleCrawler #3 を `mergeable_state: unstable` のままマージした。verify は落ちていた
判定の誤り: PR の状態を取ったのに、チェックの結果を見ずにマージへ進んだ
次から: マージの前に check runs を見る。赤なら止まる。原因が枠切れでも、確かめてから進む

## 2026-09-22 depth 1 の clone でブランチが1本だと決めた
場面: ブランチ、配布
起きたこと: RuleCrawler に `main` があるのに「唯一のブランチ」と報告した。`--depth 1` は既定ブランチしか取らない
判定の誤り: 手元の `git branch -r` を全ブランチの一覧だと思った
次から: ブランチの有無は `git ls-remote --heads origin` か API で見る。手元の clone は根拠にしない

## 2026-09-22 既定ブランチに配って、本人の main に届かなかった
場面: 配布、ブランチ
起きたこと: 既定が `claude/...` の作業ブランチだったので Raphael はそこへ配り、`main` で作業する本人には見えなかった
判定の誤り: 既定ブランチの名前が変だと気づいて書いたのに「動きはする」で流した
次から: 既定が `claude/` で始まるなら `main` か `master` に配る。変だと気づいたら、流さずその場で確かめる

## 2026-09-22 ステップ無しで数秒で落ちるジョブを、コードのせいだと疑った
場面: CI
起きたこと: Actions の枠切れ。ジョブにステップが1つも無く、3秒で失敗、ログは 404
判定の誤り: 最初にコードを疑った。手元で通したのは正しかったが、順番が逆
次から: ステップ無し・数秒・ログ 404 なら、コードより先に Billing の Actions 使用量を疑う

## 2026-09-19 スキルがセッション開始時にしか読まれないと言った

## 2026-09-18 squash マージのあと同じブランチに積んでコンフリクトさせた
場面: 配布、マージ

## 2026-09-18 失敗を数えずにジョブを緑にした
