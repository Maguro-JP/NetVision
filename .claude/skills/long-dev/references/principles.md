# 自律開発の原則

long-dev と auto-dev の判断の土台。何を「良くなる」とみなし、何を作業とみなさないか。

## 目的

作業量を増やすことではなく、プロダクトを良くすること。
時間が経つほど、品質・精度・機能性・保守性・利用者の価値が上がっている状態を目指す。
変更の前に必ず一度問う。「この変更で本当にプロダクトは良くなるか」。

## してよい変更

バグ修正、AI の精度向上、UX と UI の改善、性能、セキュリティ、安定性、保守性、
テストの強化、利用者の価値の向上、はっきりした技術的負債の解消、
将来の問題を妥当なコストで防ぐ改善。

品質が上がるなら、必要なコストは払う。
品質が同じなら、より安全で単純で速くて安いやり方を選ぶ。

## しない変更

意味の無いリファクタ、動いているコードの書き換え、好みの変更、
実績を作るためだけの変更、不要な依存の追加、不要な再実装、
不要なテストの追加。

## 自作自演の禁止

正常なコードを変えて、バグを出して、調べて、直して、テストして、「改善しました」。
このループはトークンを燃やすだけで何も良くしていない。
変更前より良くなる根拠が無い変更は、しない。

## 変更しない判断

改善対象が無ければ変更しない。次を見たうえで無ければ「今回は変更不要」と報告する。
バグ、テスト、AI 精度、UX、UI、性能、セキュリティ、保守性、技術的負債、
ドキュメント、将来のリスク。

「変更不要」は失敗ではない。無理に見つけた改善は、たいてい無関係なリファクタになる。

## トークン

有限の開発資源として扱う。必要なファイルだけ読む。同じ情報を二度取らない。
既存のドキュメントを使う。小さな問題に大きな調査をしない。小さな問題を大きな変更で解かない。
ただし、品質に必要な調査と検証は削らない。節約ではなく費用対効果を最大にする。

## バグ

1. 再現条件を確かめる
2. 原因を特定する
3. 影響範囲を見る
4. 最小限で直す
5. 回帰テストを足す
6. 直したあと同じ手順で再現しないことを見る
7. 原因と対策を記録する

症状を隠さない。根本原因を直す。

## AI の精度

AI を使う機能では、精度向上を開発目標の一つにする。

失敗の発見 → 原因分析 → 改善の仮説 → 最小の変更 → テスト → 前後の比較 → 記録

比べられるものは数字で比べる。正解率、誤り率、誤判定率、再現率、処理時間、応答の質。
「なんとなく良くなった」で完了にしない。

## 知識の蓄積

同じ問題を二度調べない。プロジェクト内の `docs/knowledge/` に残す。

| ファイル | 中身 |
|---|---|
| `tech.md` | 採用技術、ライブラリ、API、環境固有の問題、設計上の知識 |
| `problems.md` | 起きたバグ、原因、解決、再発防止、失敗した手、採用しなかった案と理由 |
| `ai.md` | 精度の問題、効いた改善、効かなかった改善、モデルとプロンプトの知見、評価方法 |
| `decisions.md` | なぜこの設計か、なぜ別案を採らなかったか、将来の制約、技術的負債 |

新しく分かったことは、将来読み返せる形でその日のうちに書く。

## 技術選定

新しい技術・ライブラリ・サービスを入れる前に見る。
本当に必要か、既存で解けないか、維持コスト、依存リスク、セキュリティ、将来性、開発コスト。

## 大きな変更の前

現在の状態、影響範囲、依存関係、テスト、戻し方。この5つを確かめてから始める。

## GitHub Actions

有限の資源。同じテストの重複、不要な build と deploy、開発中の無意味な実行を避ける。
手元で検証できるものは手元でやる。private リポジトリは分数が課金される。
枠が尽きると他の開発が止まる。
