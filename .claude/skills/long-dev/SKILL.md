# 長期開発

終わりの無い開発を、止まらずに回す。
判断の土台は `references/principles.md`。先にそれを読む。
作業量ではなくプロダクトが良くなることが目的で、「変更不要」は失敗ではない。

## 初回

そのリポジトリで初めて使うとき、Routine の一覧に `long-dev` が無ければ、作業の前に1行だけ聞く。

```
定期実行がまだありません。long-dev の再起動（毎日 10:00 JST、翌朝まで回す）と、
日報・週報・月報（09:00 JST、月曜、1日）の計4つを作りますか。
```

はいなら `scheduler` の作り方で4つ作る。いいえなら作らず、以後は聞かない。
毎回言わなくて済むように、最初に一度だけ聞く。

一覧に `long-dev` があっても、リポジトリ無しで作られたもの（`create_new_session_on_fire`
のもの、結びつけ先のセッションが別のリポジトリのもの）は動かない。無効にして作り直す。
作り方は `scheduler` にある。このリポジトリを渡したセッションを作り、4つをそれに結びつける。
どのセッションからでも作れる。作ったら `dev-report daily` を1回起こして、報告がリポジトリに
入るのを見る。

Routine を作り終えたら、定刻を待たずにその場で開発を始める。定刻の Routine は「翌日以降に起こし直す」ためのもので、初回の開始では
ない。作っただけで止まると、次の 10:00 JST まで最大 24 時間なにもしない。

## 始め方

呼ばれたら、その場で回し始める。Routine の有無や作成は上の「初回」で済ませ、済んだら
すぐ `auto-dev` に入る。「Routine を作りました。定刻に始まります」で終わらない。

## 止まらない仕組み

セッションは永遠には生きない。リモートのセッションは放置で回収され、端末のセッションは
閉じれば終わる。だから long-dev は毎日 Routine で起こし直す。

- 10:00 JST に、このリポジトリを持つセッションに `long-dev` が届く
- 止まっていれば、そこから再開する。まだ回っていれば、新しい指示ではなく「続けて」として読み、そのまま回す（S9 にしない）
- 途中でセッションが死んでも、翌日の 10:00 に立ち上がる。失った周は git 履歴から続ける
- 報告（dev-report）は 09:00 で、開発が終わった直後の状態を書く

## 回し方

`auto-dev` を `L=auto`、期限なしで回す。引数は要らない。`E=` も `L=` も書かなくてよく、
書かれていても期限は付けない。終わりの無い開発なので、自分から終わる理由が無い。
1周は auto-dev の流れそのまま。
調査 → 判断 → 実装 → 検証 → 修正 → 再検証 → コミット。

auto-dev と違うのは次の3つ。

- 優先の出どころ: `docs/reports/` の最新の日報と週報と月報。そこに書かれた優先とタスクを、auto-dev の優先指示として渡す。無ければ auto-dev の順序で選ぶ
- 止まらない: auto-dev の S2（作業が見つからない）で止まらず、principles.md の観点で探し続ける。3周続けて無ければ「変更不要」と記録して、次の周へ進む。無理に見つけない
- 記録: 周ごとに `docs/knowledge/` に書く。技術、問題、AI、設計判断の4ファイル

## 止まらない

long-dev は auto-dev の止まる条件で止まらない。条件に当たったら、その件だけを脇に置いて、
次の作業へ進む。人の答えを待って全体を止めると、答えるまで何時間も何もしない。

| 当たった条件 | すること |
|---|---|
| S3 同じ失敗を2回 / S8 堂々巡り | その件を諦めて `docs/knowledge/problems.md` に書き、別の作業へ |
| S4 設計の分岐 / S7 根拠不足 | 判断待ちに書き、推す案を添える。その件は触らず、別の作業へ |
| S5 人の判断が要る（課金、認証、本番、破壊的変更、削除、公開） | 実行しない。判断待ちに書いて、別の作業へ |
| S6 範囲の逸脱 | やらない。案として判断待ちに書いて、別の作業へ |
| S9 新しい指示 | その指示を先にやり、終わったら回し続ける |

判断待ちは `docs/reports/pending.md` に1件ずつ書く。何を決めてほしいか、選択肢、推す案、
それが決まるまで止まっているもの。`dev-report` の日報がこれを載せるので、利用者は日報で答える。
答えが書かれたら、次の周でそれを取り込む。

マージは `solo-pr-flow` が決める。CI が枠切れで赤いだけなら、手元の検証が通っていれば
マージしてよい、という判定もそちらにある。マージの可否を利用者に聞いて止まらない。

脇に置いたら、その件に縛られずに他に進められることを考える。

- 脇に置いた件の周りで、どちらに決まっても要る部分（共通の下地、今の動きを固定するテスト、測定）
- 決めてもらうための材料。選択肢ごとの影響を測る、試作を別ブランチに置く（main には入れない）
- 最新の日報・週報・月報の優先のうち、脇に置いた件と関係しないもの
- `references/principles.md` の観点で、まだ見ていない所（性能、安定性、テスト、UX、ドキュメント）

## 周の間を空けない

PR をマージしたら、同じ返答の中で次の周に入る。「次の作業選びは 20:30」のように、
時刻の起床で周を区切らない。1時間ごとの見回りを予約して返答を終えると、1周ごとに
最大1時間なにもしない。2026-09-26 の AdaptiveAIStudio は、周の間に 30分〜2時間の空きがあり、
同じ時間に NetVision は10分で3コミット進んだ。

待ってよいのは、実際に走っているものの完了だけ。

| 状況 | すること |
|---|---|
| CI が走っている | 所要時間に合わせて起床を予約して待つ |
| CI が走らない（Actions の枠切れ、`[skip ci]`、`.claude/` だけの変更） | 待たない。手元の検証で判定して次へ |
| 作業が残っている | 待たない。次の周へ |
| 脇に置いたものしか残っていない | 1時間後の起床を予約する（下） |

作業が脇に置いたものしか残っていないときも終わらない。1時間後の起床を予約して、
起きたら判断待ちに答えが入ったか、main が動いたかを見る。
**次の起床を予約せずに返答を終えない。** 終わってよいのは、利用者が止めろと言ったときだけ。

## 何を良くするか

`references/principles.md` の「してよい変更」の範囲。バグ、AI 精度、UX、UI、性能、セキュリティ、
安定性、保守性、テスト、利用者の価値、技術的負債、将来の問題の予防。

しないもの。意味の無いリファクタ、動いているコードの書き換え、好みの変更、
実績を作るための変更、自作自演のループ。

## PR とマージ

PR は日報か週報の区切りに合わせる。緊急の小さな修正はその場でよい。
マージは `solo-pr-flow` の判定に従う。不要なブランチと PR を残さない。
GitHub Actions は PR を作るときだけ動く形にし、検証は手元でやる。

## 報告

自分では書かない。`dev-report` が日報・週報・月報として書く。
long-dev が残すのは、コミット、`docs/knowledge/`、`docs/reports/pending.md` の判断待ち。

## 他のスキルとの関係

- 周ごとの作業: `auto-dev`。原則は `references/principles.md`
- 日報・週報・月報: `dev-report`
- 定期実行の設定: `scheduler`
- PR のマージと後片付け: `solo-pr-flow`
- 失敗の記録: `lessons`。自分の判定の誤りはここ、プロダクトの問題は `docs/knowledge/problems.md`
