# Skill Audit

既存のスキルを読み、**発動しない / 誤爆する / 重い** の3つの観点で診断し、修正案を出す。

## 使うとき

- スキルが想定の場面で呼ばれない
- 関係ない場面で呼ばれてしまう
- SKILL.md が肥大化してトークンを食っている
- 公開前にスキルの品質を確認したい

## 手順

### 1. 読む

対象の `SKILL.md` 全文と、`references/` `scripts/` のファイル一覧を確認する。
frontmatter の `name` と `description` を最初に抜き出す。

### 2. description を診断する

これが発動精度のほぼすべてを決める。次を順に確認する。

| 確認項目 | 不合格の例 | 直し方 |
|---|---|---|
| 発動条件が書かれているか | 「PDFを扱う便利なスキル」 | 「ユーザーが .pdf に言及、またはPDF生成を求めたとき」 |
| 具体的なトリガー語があるか | 抽象語のみ | ユーザーが実際に打つ単語を列挙 |
| 除外条件があるか | なし | 「〜には使わない」を1文追加 |
| 機能説明で終わっていないか | 「〜ができます」 | 「〜のときに使う」に書き換える |

**発動しない**なら、ユーザーが実際に使う言い回しが description に含まれていない。
**誤爆する**なら、除外条件が足りないか、責務が広すぎる（→ スキル分割を提案）。

### 3. 本文を診断する

- 500行超 → `references/` への切り出しを具体的に提案する（どのセクションをどのファイルへ）
- 決まりきった長い手順 → `scripts/` の実行可能ファイルにできないか
- 動かない例・古いAPI → 指摘する
- 「〜してください」調の冗長な説明 → 命令形の手順に圧縮
- 一つのスキルに複数の責務 → 分割案を出す

### 4. 構造を診断する

- `name` がディレクトリ名と一致しているか
- ディレクトリ名が小文字・数字・ハイフンのみか
- `scripts/` に実行権限があるか
- 参照しているファイルが実在するか（SKILL.md 内のパスを実際に確認する）

### 5. 報告する

深刻な順に並べて出す。各項目は次の形で書く。

```
[重大度] 問題の一文
  現状: <引用>
  修正: <具体的な置き換え文。抽象的な助言ではなく、そのまま貼れる文言>
```

重大度は 発動不能 > 誤爆 > 肥大化 > 体裁 の順。
問題がなければ「問題なし」と言い切る。無理に指摘を作らない。

## 原則

- 修正案は**そのままコピペできる完成文**で出す。「もっと具体的に書きましょう」は助言ではない
- description の書き換え案は必ず出す。最も効く改善だから
- 本文を削る提案をするときは、削った内容の移動先を必ず示す
- ユーザーが承認するまでファイルは書き換えない
