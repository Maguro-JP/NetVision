# Secret Leak Check

機密情報（APIキー、トークン、パスワード、秘密鍵、個人情報、内部ホスト名）の混入を調べ、
見つかったときの対応順序まで案内する。

**答えるべき問いは2つある。混同しない。**

| 問い | 調べる場所 | 見つかったときの意味 |
|---|---|---|
| これから漏らさないか | 作業ツリー、未コミットの差分、PR の差分 | まだ止められる。消せば済む |
| **すでに漏れていないか** | **git 履歴、push 済みのブランチ、公開済みのリポジトリ** | **もう漏れている。消しても戻らない** |

多くの確認は前者で止まる。**後者を飛ばしてはいけない。**

## 手順

### 1. 範囲を決める

| 状況 | 範囲 |
|---|---|
| コミット前の確認 | 作業ツリー + 未コミットの差分 |
| PR / マージ前 | その PR の差分全体 |
| **公開前（private → public）** | **履歴の全コミット**。ここを省くと公開の意味がない |
| 「push してしまった」 | 履歴 + リモートの全ブランチ + 対応（後述）へ直行 |

リポジトリがすでに public なら、**常に履歴まで見る**。

### 2. 走査する

手元に `gitleaks` か `trufflehog` があるならそれを使う。無ければ同梱の
`scripts/scan.py` を使う。

```bash
scripts/scan.py --tree              # 作業ツリー
scripts/scan.py --diff              # 未コミットの変更
scripts/scan.py --diff main..HEAD   # 範囲を指定
scripts/scan.py --history           # 全コミットの履歴
```

検出があれば終了コード 1。深刻度は `high`（ほぼ確実に本物の形式）と
`medium`（要確認。高エントロピーな値など）。

対象のリポジトリに独自の検証スクリプトがあるなら、それも併せて動かす。

### 3. 本物かどうかを判定する

**検出＝漏洩ではない。** 報告する前に必ず1件ずつ見る。

本物でないもの:

- プレースホルダ（`YOUR_API_KEY`、`xxxxx`、`<token>`、`${VAR}`）
- ドキュメントやテストの例。ただし**動く値なら例でも本物**
- 検出ルールそのもの（`scripts/` の中の正規表現）
- 公開が前提の値（公開鍵、クライアント側の publishable key、`pk_live_`）

本物と考えるもの:

- 形式が一致し、値が無作為で、プレースホルダ語を含まない
- `.env`、設定ファイル、CI 定義に実値として書かれている
- **判断がつかないなら本物として扱う。** 誤って見逃す方が高くつく

### 4. 報告する

深刻度順に、次の形で出す。**値そのものは全部書かない。**

```
[high] Anthropic API key
  場所: src/config.py:12   （履歴なら <sha>:<path>）
  状態: main に push 済み / 未コミット
  対応: 鍵をローテート → 履歴から除去
```

最後に、**まだ止められるもの**と**すでに漏れているもの**を分けて数える。
この区別が対応の緊急度を決める。

### 5. 対応を案内する

**順序を絶対に逆にしない。**

```
1. 鍵を無効化・ローテートする      ← 最優先。今すぐ
2. 使われた形跡を確認する          ← 提供元の監査ログ
3. 履歴から除去する                ← 最後
```

**push 済みの秘密情報は、消しても漏れたままである。** commit を消しても、
fork・キャッシュ・クローン・GitHub のイベント API に残る。
履歴の書き換えは「見えなくする」だけで「漏れをなくす」ものではない。
だから**先にローテートする**。

未 push なら 3 だけでよい。判断を誤らないよう、まず push 済みかを確認する。

具体的な手順は `references/response.md` を読む。

## 原則

- **`high` を1件でも見つけたら、他の作業より先に報告する**
- **値を報告に丸ごと書かない。** 報告自体が新しい漏洩経路になる
- **push 済みか未 push かを必ず区別する。** 対応がまったく違う
- **ローテートを先に案内する。** 「履歴から消しました」で終わらせない
- **判断がつかないものは本物として扱う**
- 検出ゼロでも「安全」とは言わない。**「このルールでは検出されなかった」**と言う
- 修正のためにファイルを書き換えるのは、利用者の承認を得てから

## 誤検知を抑える

- 行末に `secret-leak-check: ignore` を書く
- `.secretignore` に glob を1行ずつ並べる
- `.example` / `.sample` 付きのファイル、ロックファイル、バイナリは既定で除外

**抑止する前に、それが本当に安全か確認する。** 面倒だからという理由で無効化しない。

## 検出できないもの

このスキルは万能ではない。次は見つけられない。

- 形式に特徴のない秘密（英単語のパスワード、社内URLの一部）
- 暗号化・難読化された値
- 画像やバイナリに埋まった情報
- **人にしか判断できない機密**（顧客名、社内の意思決定、未公開の計画）

最後の1つが最も漏れやすい。**走査が通ったことは、目視を省いてよい理由にならない。**
