# Auto Dev

「自動で開発を進めて」を、そのまま回せる形にする。

毎回プロンプトを組み立て直さなくて済むように、**毎サイクル何を調べるか、何を選ぶか、
いつ止まるか、いつ push するか**を先に決めておく。

## 原則

目的は作業量ではなく、プロダクトを良くすること。変更の前に「これで本当に良くなるか」を問う。
してよい変更、しない変更、自作自演の禁止、変更しない判断、バグの手順、AI 精度の測り方、
知識の置き場、技術選定、大きな変更の前の確認は `long-dev/references/principles.md` にある。
毎サイクルの判断はそれを土台にする。

特に守るもの。

- 正常なコードを変えてバグを出し、直して「改善」と報告するループを作らない
- 改善対象がなければ「今回は変更不要」と報告する。それは失敗ではない
- 分かったこと（技術、問題、AI、設計判断）は `docs/knowledge/` にその日のうちに書く
- AI の精度は数字で前後を比べる。「なんとなく良くなった」で完了にしない

## 引数

```
/auto-dev                              無期限、周期は自動
/auto-dev E=1d L=1h TODO の空欄を優先    1日で終わる、1時間おき
/auto-dev L=5h フェーズ10まで進めて      無期限、5時間おき
/auto-dev E=2h テストを先に通して        2時間で終わる、周期は自動
```

| 記号 | 意味 | 値 | 省略時 |
|---|---|---|---|
| `E=` | End。期限 | `30m` `2h` `1d` | 無期限 |
| `L=` | Loop。周期 | `10m` `1h` `5h` `auto` | `auto`（即時連続） |
| `PR=` | PR を出す単位 | `each` `daily` | 区分で決まる（`references/verification.md`） |
| 残り | 優先指示 | 自由な文 | なし |

`E=1d` と `E1d` はどちらでもよい。順番も問わない。

普通の文で書かれても読み取る。「1日で、1時間おきに、TODO の空いてるところをやって」
なら E=1d L=1h と解釈する。ただし上の形なら確実。

### `auto` は即時連続

`L=` を省略したとき、または `L=auto` のとき、**1周が終わったらそのまま次のサイクルに入る。**
間を空けない。返答を終えて待たない。

止まってよいのは、待つものがあるときだけ。

| 待つもの | 待ち方 |
|---|---|
| CI やデプロイの完了 | その所要時間に合わせて次の実行を予約してから止まる。完了通知で再開する |
| 外部の処理（ビルドの完了など） | 同上 |
| CI が走らない（Actions のレート制限超過、`[skip ci]`、`.claude/` だけの変更） | 待たない。手元の検証で判定して次のサイクルへ |
| 何も待っていない | 待たない。次のサイクルへ |

PR をマージしたら、同じ返答の中で次のサイクルに入る。「次の作業選びは 20:30」のような
時刻の見回りでサイクルを区切らない。区切ると1周ごとに最大1時間なにもしない
（2026-09-26 に、あるリポジトリでサイクルの間が 30分〜2時間空いた）。

**次の実行を予約せずに返答を終えてはいけない。** 予約の手段がない環境なら、
返答を終えずに同じ応答の中で次のサイクルを続ける。

全体を止める条件（下記の「止める」）に当たったときだけ、予約せずに終える。それが「止まる」の意味。
その件だけの問題は、脇に置いて残りの作業を先に片付ける。

### 周期の上限

**`/loop` の間隔は最長1時間。** `L=5h` は `/loop` では動かない。

| 周期 | 使うもの |
|---|---|
| 1時間以下 | `/loop` |
| 1時間超、または無期限で長く回す | Routine（定期実行、cron） |

1時間を超える周期を指定されたら、Routine を作る。`/loop` に無理に押し込まない。
Routine はセッションが終わっても続くので、無期限の指定とも相性がよい。

### Routine は切りの良い時刻に起動する

cron を `0 */5 * * *` の形で書くと、作成した分を起点に丸められる。
23分に作れば毎回23分に実行される。**時刻を列挙する形で書く。** 列挙はそのまま保存される。

| 周期 | cron（UTC） | 日本時間で実行される時刻 |
|---|---|---|
| 5h | `0 0,5,10,15,20 * * *` | 09, 14, 19, 00, 05 |
| 6h | `0 0,6,12,18 * * *` | 09, 15, 21, 03 |
| 8h | `0 0,8,16 * * *` | 09, 17, 01 |
| 12h | `0 0,12 * * *` | 09, 21 |
| 1d | `0 0 * * *` | 09 |

起点は 09:00 JST（UTC 00:00）。周期で割り切れる時刻を UTC で並べる。
最初の1回は、次に来る列挙時刻まで待つ。今すぐ始めたいときは1周目だけ手で回す。

### 終着点

「フェーズ10まで」「テストが全部通るまで」のような到達点が優先指示に含まれていたら、
それ自体を止まる条件にする。到達したら E= に関係なく止まる。

## 始める前に一度だけ見せる

何を勝手にやられるか分からない状態で放置させない。

```
自動で進めます。

  対象      : <リポジトリ> / <ブランチ>
  期限      : 1日（明日 09:00 まで）
  周期      : auto（即時連続。待つものがあるときだけ待つ）
  優先      : TODO の空欄を先に実装
  push      : しない。まとめて必要になったときだけ
  止まる条件: 期限・終着点・新しい指示・残りが全部脇に置いた件だけ（下記）
  報告      : 変化があったときだけ、3行以内

これで回します。
```

## 1周の流れ

**調査 → 判断 → 実装 → 検証 → 修正 → 再検証 → コミット**

作業は1周につき1つ。完了まで持っていく。中途半端なまま次に移らない。

### 1. 調査

毎サイクルこれを見る。前のサイクルの記憶に頼らない。**セッションが切れても Git 履歴から続けられる。**

```bash
git status
git branch --show-current
git log --oneline -10
```

- main を取り込む（`git fetch origin && git merge origin/main`）。feedback-session など別のセッションの発見は main 経由でしか届かない
- 前のサイクルのあとで main に入った `docs/knowledge/` と `docs/reports/pending.md` の差分。`git log -p <前のサイクルのコミット>..origin/main -- docs/knowledge docs/reports/pending.md` で読み、そのサイクルの作業を選ぶ
- ユーザーからの指示が届いていれば、それを最優先にする。判断待ちに回さない（work-style「人が決める」）
- `docs/reports/deliverables.md`（成果物の表）。無ければ finish-first に従って作る（README の未着手、issue、優先指示から1〜3行、完成条件は仮）。
  あれば先頭の未完成の行が今の成果物で、その「残り」がこのサイクルの作業の候補
- 直近のコミットで何をしていたか（前のサイクルの続きがあるか）
- README と、そこに書かれた未着手の項目
- `TODO` `FIXME` `HACK` のコメント
- open の issue と PR
- テストの状態（落ちているもの、skip されているもの）
- build と lint の状態
- 最近変更されたファイル

### 2. 判断

**コードを読む前に推測しない。** 既存の設計を理解してから変更を決める。

作業は上から順に見て、最初に当たったものを選ぶ。

| 順 | 対象 |
|---|---|
| 1 | 壊れているもの。テストが落ちている、build が通らない、lint が赤い |
| 2 | 詰まっているもの。マージできない PR、コンフリクト、レビュー指摘の未対応 |
| 3 | 優先指示。引数で渡されたもの、ユーザーから届いた指示 |
| 4 | 今の成果物。`docs/reports/deliverables.md` の先頭の未完成の行の「残り」（finish-first） |
| 5 | 明示された宿題。issue、TODO、ドキュメントに書かれた未着手 |
| 6 | 自分で見つけた改善余地 |

**1と2を飛ばして新しいものを作らない。** 壊れたまま積み上げない。
4 が残っているうちは、5 と 6 で新しい成果物を始めない。中途半端な成果物を増やさない。

6 に落ちたときは、次の観点から探す。プロジェクトの現状に応じて優先順を決める。

```
バグ修正 / エラーハンドリング / 型安全性 / テスト追加 / セキュリティ
パフォーマンス / UX / コード品質 / ドキュメント / 機能追加
```

### 3. 実装

小さく安全な単位で変える。触っているファイルの外へ広げない。

### 4. 検証

**ローカルで全部やる。** 動かせるものは動かす。

```
テスト → lint → typecheck → build
```

実行できるものだけでよいが、**実行できるのに省かない**。
出力を捨てない。黙らせるのは中身を見たあとだけにする。

### 5〜6. 修正と再検証

エラーがあれば直して、もう一度同じ検証を通す。

**同じ失敗を2回繰り返したら3回目を試さない。** S3 でその件を脇に置き、別の作業へ進む。

### 7. コミット

意味のある単位でコミットする。`git show --stat` で意図したファイルが
入っているか見る。

## push と GitHub Actions

作業のブランチは `claude/DEV-<YYYYMMDD>`（日付は JST。`TZ=Asia/Tokyo date +%Y%m%d`）、PR のタイトルは `DEV <日付>: <1行>`（work-style「名前の付け方」）。

`.claude/policy/<ユーザー名>.json` の `push_policy` に従う。デフォルトは `"batch"`。

| 値 | 動き |
|---|---|
| `"batch"` | 検証済みの変更をまとめてから push（デフォルト） |
| `"never"` | push しない。ローカルのコミットで積むだけ |
| `"each"` | 作業ごとに push。CI の消費が増えるのでデフォルトにしない |

**原則として push しない。** ローカルのコミットで積む。

CI の実行回数と実行時間には実費がかかる。ローカルで確かめられることを
GitHub Actions で確かめない。

検証は手元で済ませる。手元でできる確認（lint、型検査、テスト、ビルド）を CI に回さない。
CI に残してよいのは、手元にない環境（Windows など）と配布物の組み立てだけ。
始めるときに、リポジトリの区分（公開か非公開か、個人か仕事か）を見て、PR の出し方と
CI の扱いを決める。表と細かい決まりは `references/verification.md`。

### `PR=daily`

PR をサイクルごとに出すと、PR を作るたび・push するたびに Actions が走り、月の枠が数日で尽きる。
`PR=daily` では、1日の作業を1本の PR にまとめ、Actions を1日1回にする。

- サイクルごとにコミットし、作業ブランチへ push してよい。ただし PR は作らない。開いた PR があると push のたびに CI が走る
- サイクルごとの検証は手元だけで行う。手元の検証が通らないコミットは積まない
- long-dev から起動されたときは、翌朝の Routine が報告と一緒に1本の PR にまとめてマージする。手元の検証でマージする
- 急ぎの修正（本番の不具合、壊れた main）だけは、その場で PR にしてよい。報告にそう書く
- PR を作る前とマージの前にユーザーの確認が要る（solo-pr-flow「出す前の確認」）。自律で回っていて返事が無いときは、PR を作らずに作業ブランチを push し、pending.md に「PR 待ち」と書いて次の作業へ進む

CI が失敗したときも、**まずローカルで再現してから**直す。
push して結果を見る、を繰り返さない。

止まるときに未 push のコミットがあれば、その旨を報告に書く。

## 止まる条件

止め方は2つある。**全体を止める**ものと、**その件だけ脇に置く**もの。
その件だけの問題で全体を止めると、残りの作業が手付かずのままユーザーの返事を待つことになる。

### その件だけ脇に置く

当たったら、その件を触るのをやめ、脇に置いた件の一覧に書き、**依頼の範囲で残っている別の作業を先に片付ける。**

| # | 条件 | すること |
|---|---|---|
| S3 | 同じ失敗を2回繰り返した | 3回目を試さない。何が失敗したかを書いて脇に置く |
| S4 | 設計の分岐に当たった | 選択肢と推す案を書いて脇に置く。どちらにしても要る部分があれば、そこは進めてよい |
| S5 | 人の判断が要る（仕様変更、課金、認証、本番環境、破壊的変更、データの削除、外部への公開） | 実行しない。何を決めてほしいかを書いて脇に置く |
| S6 | 依頼の範囲を超える | やらない。案として書いて脇に置く |
| S7 | 判断の根拠が足りない | 何が分からないかを書いて脇に置く |
| S8 | 同じファイルを3周続けて触っている | その件を止めて脇に置く |

脇に置いた件の一覧は `docs/reports/pending.md` に書く。1件ずつ、何を決めてほしいか、
選択肢、推す案、それが決まるまで止まっているもの。なければ作る。

S5 の操作は、脇に置いたあとも実行しない。答えが来るまで手を付けない。

脇に置いたら、その件と関係なく進められることを探す。

今の成果物（`deliverables.md` の先頭）に関わる S4 と S7 は、戻せる選択ならデフォルトを選んで進める。
デフォルトの選び方と書き残し方は `finish-first`。S5 はデフォルトで進めない。

- 脇に置いた件のサイクルりで、どちらに決まっても要る部分（共通の下地、今の動きを固定するテスト、測定）
- 決めてもらうための材料。選択肢ごとの影響を測る、試作を別ブランチに置く（main には入れない）
- 優先の指示や最新の報告のうち、脇に置いた件と関係しないもの

### 全体を止める

| # | 条件 |
|---|---|
| S1 | 期限（E=）に達した、または終着点に到達した |
| S2 | 依頼の範囲で残っている作業が、脇に置いた件だけになった。または探しても作業が見つからない（下記） |
| S9 | ユーザーから新しい指示が来た。今の依頼を置いて、新しい指示に従う |
| S10 | ユーザーが止めろと言った |

止めるときは、終えた作業、脇に置いた件の一覧（`pending.md`）、再開に何が要るかを報告する。
脇に置いた件が残っているなら、それが「ユーザーに返してほしいもの」の一覧になる。

S3 と S8 が効く。**自動で回すと、直らないものを延々と直そうとする。**
2回で諦めて脇に置く方が、10回試すより早い。

### S2 の扱い

TODO がないだけでは止まらない。上の観点でコードベースを調べて改善余地を探す。

ただし**作るために作らない**。3周続けて「探したが見つからない」なら、
素直に報告して止まる。無理に見つけた改善は、たいてい無関係なリファクタになる。

## やってはいけないこと

- 頼まれていない大きな設計変更
- 無関係なリファクタ。ついでに直すのは触ったファイルの中だけ
- テストを通すためにテストを緩めること
- 検証を省いて次へ進むこと
- 脇に置く条件に当たった件を「たぶん大丈夫」で続けること
- その件だけの問題で、残っている作業を放って全体を止めること

## 会話に出すもの

会話はユーザーが確認すべきものを読む場所にする。サイクルごとの経過で埋めると、判断待ちが流れて
見つからなくなり、文脈も膨らんで1手ごとの読み直しが重くなる。浮いたトークンは作業と報告に回す。

行は work-style の4種類だけ。先頭のマークで見分ける。

| いつ | 出すもの |
|---|---|
| サイクルの始め | `❕ auto-dev N周目: <やること1行>` |
| 脇に置いたとき | `❔ 判断待ち <番号>: <何を決めてほしいか1行>` |
| サイクルの終わり | `★ auto-dev N周目: <マージした PR かコミット>。<何がどう良くなったか1行>` |
| 変更不要のサイクル | `❕ auto-dev N周目: 変更なし（<見た観点と理由1行>）` |
| 止まるとき | `❕ auto-dev 停止 S<番号>: <再開に要ること1行>` |

始めるときにマーカー `.claude/quiet` を置く（`.git/info/exclude` に足す）。Stop フックが外れた文を差し戻す。
区切りの長い報告は書かない。日ごとのまとめは dev-report が `docs/reports/` に書き、★ で URL を出す。
調べた過程、テストのログ、差分、「次は〜します」の独り言は会話に出さない。
何をしたかはコミットに残っている。

文脈を小さく保つ。
具体的な決まり（読む前に探す、要る範囲だけ読む、出力を絞る、一覧の MCP には limit、状態はファイルへ）は `token-efficiency` の 3 と 4。

- テストやビルドの出力はファイルへ落とし、失敗の行と要約（`tail`、`grep`）だけを読む
- ファイルは要る範囲だけ読む。同じファイルをサイクルごとに全部読み直さない
- 広い調べものはサブエージェントに任せ、結論だけを受け取る
- サイクルをまたいで覚えておくことは会話ではなく `docs/knowledge/` に書く。圧縮されても消えない

日報・週報・月報は auto-dev では書かない。毎日の報告と組にして回すなら `long-dev` で Routine を作る。

## 繰り返しの担い手

**周期の指定によって、誰が次のサイクルを起動するかが変わる。** ここを取り違えると、
1周で止まって放置される。

| 指定 | 次のサイクルを起動するもの |
|---|---|
| `L=auto`（省略時） | このスキル自身。即時に次のサイクルへ。待つときは自分で実行を予約する |
| `L=` が1時間以下 | `/loop`。始まっていなければ、その間隔で自分で実行を予約する |
| `L=` が1時間超 | Routine。cron で作る（時刻は列挙する。上記） |

```
auto-dev を使って。E=1d TODO の空欄を優先          ← 即時連続で回る
/loop 1h /auto-dev E=1d TODO の空欄を優先          ← 1時間おき
auto-dev L=5h フェーズ10まで                       ← Routine になる
```

間隔の優先順は、`L=` の指定 → `/loop` の指定 → `.claude/policy/<ユーザー名>.json` の
`loop_interval` → `auto`。

**変化がないのに実行しない。** 待つものがないなら、待たずに次のサイクルへ進む方が安い。
待つものがあるなら、その所要時間まで実行しない。
短い間隔で何度も様子を見に行くのは、どちらでもない中途半端な形で、いちばん枠を捨てる。

全体を止める条件に当たったら、loop も Routine も止める。脇に置く条件では止めない。
