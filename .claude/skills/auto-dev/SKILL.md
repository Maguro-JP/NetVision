# Auto Dev

「自動で開発を進めて」を、そのまま回せる形にする。

毎回プロンプトを組み立て直さなくて済むように、**毎周何を調べるか、何を選ぶか、
いつ止まるか、いつ push するか**を先に決めておく。

## 引数

```
/auto-dev                              無期限、周期は自動
/auto-dev E=1d L=1h TODO の空欄を優先    1日で終わる、1時間おき
/auto-dev L=5h フェーズ10まで進めて      無期限、5時間おき
/auto-dev E=2h テストを先に通して        2時間で終わる、周期は自動
```

| 記号 | 意味 | 値 | 省略時 |
|---|---|---|---|
| `E=` | End。期限 | `30m` `2h` `1d` | 無期限 |
| `L=` | Loop。周期 | `10m` `1h` `5h` `auto` | 自動 |
| 残り | 優先指示 | 自由な文 | なし |

`E=1d` と `E1d` はどちらでもよい。順番も問わない。

普通の文で書かれても読み取る。「1日で、1時間おきに、TODO の空いてるところをやって」
なら E=1d L=1h と解釈する。ただし上の形なら確実。

### 周期の上限

**`/loop` の間隔は最長1時間。** `L=5h` は `/loop` では動かない。

| 周期 | 使うもの |
|---|---|
| 1時間以下 | `/loop` |
| 1時間超、または無期限で長く回す | Routine（定期実行、cron） |

1時間を超える周期を指定されたら、Routine を作る。`/loop` に無理に押し込まない。
Routine はセッションが終わっても続くので、無期限の指定とも相性がよい。

### 終着点

「フェーズ10まで」「テストが全部通るまで」のような到達点が優先指示に含まれていたら、
それ自体を止まる条件にする。到達したら E= に関係なく止まる。

## 始める前に一度だけ見せる

何を勝手にやられるか分からない状態で放置させない。

```
自動で進めます。

  対象      : <リポジトリ> / <ブランチ>
  期限      : 1日（明日 09:00 まで）
  周期      : 1時間（/loop）
  優先      : TODO の空欄を先に実装
  push      : しない。まとめて必要になったときだけ
  止まる条件: S1〜S9（下記）
  報告      : 変化があったときだけ、3行以内

これで回します。
```

## 1周の流れ

**調査 → 判断 → 実装 → 検証 → 修正 → 再検証 → コミット**

作業は1周につき1つ。完了まで持っていく。中途半端なまま次に移らない。

### 1. 調査

毎周これを見る。前の周の記憶に頼らない。**セッションが切れても Git 履歴から続けられる。**

```bash
git status
git branch --show-current
git log --oneline -10
```

- 直近のコミットで何をしていたか（前の周の続きがあるか）
- README と、そこに書かれた未着手の項目
- `TODO` `FIXME` `HACK` のコメント
- open の issue と PR
- テストの状態（落ちているもの、skip されているもの）
- build と lint の状態
- 最近変更されたファイル

### 2. 判断

**コードを読む前に推測しない。** 既存の設計を理解してから変更を決める。

作業は上から順に見て、最初に当たったものを選ぶ。

| 順 | 対象 |
|---|---|
| 1 | 壊れているもの。テストが落ちている、build が通らない、lint が赤い |
| 2 | 詰まっているもの。マージできない PR、コンフリクト、レビュー指摘の未対応 |
| 3 | 優先指示。引数で渡されたもの |
| 4 | 明示された宿題。issue、TODO、ドキュメントに書かれた未着手 |
| 5 | 自分で見つけた改善余地 |

**1と2を飛ばして新しいものを作らない。** 壊れたまま積み上げない。

5 に落ちたときは、次の観点から探す。プロジェクトの現状に応じて優先順を決める。

```
バグ修正 / エラーハンドリング / 型安全性 / テスト追加 / セキュリティ
パフォーマンス / UX / コード品質 / ドキュメント / 機能追加
```

### 3. 実装

小さく安全な単位で変える。触っているファイルの外へ広げない。

### 4. 検証

**ローカルで全部やる。** 動かせるものは動かす。

```
テスト → lint → typecheck → build
```

実行できるものだけでよいが、**実行できるのに省かない**。
出力を捨てない。黙らせるのは中身を見たあとだけにする。

### 5〜6. 修正と再検証

エラーがあれば直して、もう一度同じ検証を通す。

**同じ失敗を2回繰り返したら3回目を試さない。** S3 で止まる。

### 7. コミット

意味のある単位でコミットする。`git show --stat` で意図したファイルが
入っているか見る。

## push と GitHub Actions

`.claude/policy/<利用者名>.json` の `push_policy` に従う。既定は `"batch"`。

| 値 | 動き |
|---|---|
| `"batch"` | 検証済みの変更をまとめてから push（既定） |
| `"never"` | push しない。ローカルのコミットで積むだけ |
| `"each"` | 作業ごとに push。CI の消費が増えるので既定にしない |

**原則として push しない。** ローカルのコミットで積む。

CI の実行回数と実行時間には実費がかかる。ローカルで確かめられることを
GitHub Actions で確かめない。

| してよい | してはいけない |
|---|---|
| 複数の検証済みの変更をまとめて push | 小さな変更ごとに1回ずつ push |
| 利用者が push を求めたとき | CI を起動するためだけの push |
| ローカルで再現できない問題の確認（1回だけ） | 通るかどうか試すための push |

CI が失敗したときも、**まずローカルで再現してから**直す。
push して結果を見る、を繰り返さない。

止まるときに未 push のコミットがあれば、その旨を報告に書く。

## 止まる条件

**該当したら、その周で止めて報告する。次の周に進まない。**

| # | 条件 |
|---|---|
| S1 | 期限（E=）に達した、または終着点に到達した |
| S2 | 探しても作業が見つからない。下記を参照 |
| S3 | 同じ失敗を2回繰り返した。3回目を試さない |
| S4 | 設計の分岐に当たった。どちらでもよい選択肢が複数ある |
| S5 | 人の判断が要る。仕様変更、課金、認証、本番環境、破壊的変更、データの削除、外部への公開 |
| S6 | 依頼の範囲を超える。頼まれていない機能を足そうとしている |
| S7 | 判断の根拠が足りない。仕様が書かれていない、意図が読めない |
| S8 | 同じファイルを3周続けて触っている。堂々巡りになっている |
| S9 | 利用者から新しい指示が来た |

S3 と S8 が効く。**自動で回すと、直らないものを延々と直そうとする。**
2回で諦めて報告する方が、10回試すより早い。

### S2 の扱い

TODO が無いだけでは止まらない。上の観点でコードベースを調べて改善余地を探す。

ただし**作るために作らない**。3周続けて「探したが見つからない」なら、
素直に報告して止まる。無理に見つけた改善は、たいてい無関係なリファクタになる。

## やってはいけないこと

- 頼まれていない大きな設計変更
- 無関係なリファクタ。ついでに直すのは触ったファイルの中だけ
- テストを通すためにテストを緩めること
- 検証を省いて次へ進むこと
- 止まる条件に当たったのに「たぶん大丈夫」で続けること

## 報告

**変化があったときだけ。3行以内。** 無変化の周は黙る。

```
テストの赤を直しました。backend/app/main.py の未使用 import を削除。
ローカルで pytest と ruff が通っています。未 push のコミットが2件。
次: issue #12 の入力検証
```

経緯を再掲しない。差分が記録なので。

止まるときだけは、どこまでやったか、なぜ止まったか（条件の番号）、
再開に何が要るかを書く。

## loop との関係

繰り返しは `/loop` が行う。このスキルは1周ごとに何をするかを決める。

```
/loop 1h /auto-dev E=1d TODO の空欄を優先
/auto-dev L=5h フェーズ10まで          ← 1時間超なので Routine になる
```

間隔は次の順で決める。

1. `L=` で指定された周期
2. `/loop` に明示された間隔
3. `.claude/policy/<利用者名>.json` の `loop_interval`
4. どれも無ければこちらで決める
   - 待つものが無い → 20〜30分
   - CI やデプロイの完了を待っている → その所要時間に合わせる

**短い間隔で様子を見に行かない。** 変化が無いのに起きるのは枠を捨てるだけ。
止まる条件に当たったら loop も止める。
