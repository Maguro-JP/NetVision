## 時間制限の解釈

`30m` `2h` `1d` のように解釈する。始めた時刻を基準にする。

制限に達したかは、次の周に入る前に見る。**作業の途中で打ち切らない。**
中途半端な状態でコミットせずに終わるのが、いちばん後始末が面倒になる。

残りが明らかに足りない作業には手を付けない。1周に30分かかる作業を、
残り10分で始めない。

制限を省略されたときは無期限だが、止まる条件は変わらず効く。
無期限は「止まる条件に当たるまで」であって「永久に」ではない。

## 作業の選び方の細かい判断

### 壊れているものが複数あるとき

他をせき止めているものから直す。CI が赤だと他の PR も進められないので、
たいてい CI が最優先になる。

### 優先指示と壊れているものがぶつかるとき

壊れているものが先。優先指示は「何を作るか」の順序であって、
「壊れたまま進んでよい」という意味ではない。

ただし利用者が「テストは後でいいから機能を先に」と明示したなら、それに従う。

### 気づいた不備を拾う頻度

3周に1回まで。これを入れているのは、放っておくと**目に付いた小さな汚れを
延々と拭き続ける**ようになるため。頼まれた仕事が進まない。

拾うなら、触っているファイルの中のものを優先する。無関係な場所には広げない。

### 作業が無くなったと判断する前に

次を確認してから S2 と判断する。

- open の issue と PR
- TODO、FIXME、HACK のコメント
- ドキュメントに書かれた未着手の項目
- 失敗しているテスト、skip されているテスト
- CI が通っていない枝

全部空なら、素直に「やることが無い」と報告する。**作るために作らない。**

## 堂々巡りの見分け方

自動で回していると、進んでいないのに動き続けている状態になりやすい。
次のどれかに当たったら止める。

| 兆候 | 判断 |
|---|---|
| 同じファイルを3周続けて触っている | S8。設計に無理がある |
| 同じテストが2回落ちた | S3。原因を推測で直している |
| 直したはずのものが次の周でまた出てくる | 直っていない。根本を見ていない |
| 差分が行ったり来たりしている | 判断の根拠が無い。S7 |
| 周ごとの差分が小さくなり続けている | 終わりに近いか、無駄を足している |

**推測で2回直したら、3回目は試さずに報告する。** 情報が足りていない。

## push をまとめる判断

未 push のコミットが積むほど、まとめて push したときの CI 1回で全部を検証できる。
これが Actions の節約になる。

push してよい場面。

- 利用者が求めた
- 区切りの良いところまで進み、CI で通しておきたい
- ローカルで再現できない問題があり、CI でしか確認できない（1回だけ）

push しない場面。

- 1つ直すたびに push する
- 通るかどうか自信が無いので試しに push する
- ローカルで同じ検証ができる

ローカルで通っているものは CI でも通る。**通らないなら、ローカルの検証が
足りていない。** push して確かめるのではなく、ローカルの検証を足す。

CI が落ちたときは `ci-triage` に渡す。落ちたステップを特定してから、
ローカルで再現させて直す。再現させずに直して push し直さない。

## トークンの使い方

長く回すと、無駄が積もって効いてくる。

使ってよいところ。

- 原因の切り分け。ログを読む、差分を追う、再現させる
- 設計の判断。選択肢を比べる
- 危ない変更の確認

削るところ。

- 変化が無いのに状態を取り直す
- 同じファイルを読み直す
- 何もしていない周の報告
- 前の周の経緯の再掲
- 短い間隔での様子見

**変化が無い周は黙って次に行く。** 「変化ありません」と書くこと自体が積もる。

## 止まったあとの再開

止まったときは、次の3つを書く。

1. どこまでやったか
2. なぜ止まったか（条件の番号と、具体的な状況）
3. 再開するには何が要るか

```
止まりました（S4: 設計の分岐）。

  やったこと: 認証のトークン検証を実装、テストは通っています
  分岐      : 期限切れの扱いを、401 を返すか自動更新するかで決められません
  再開に要るもの: どちらにするかの指示
```

利用者が答えたら、そこから同じ設定で再開できる。時間制限は残り時間を引き継ぐ。
