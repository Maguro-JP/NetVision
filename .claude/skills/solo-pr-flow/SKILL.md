# Solo PR Flow

自分のリポジトリなら、PR はマージするためにある。
このスキルは「マージしてよいか」を毎回尋ねないためにある。
止まる条件は少なく、はっきりさせる。止まるときは条件名を挙げる。

以前は停止条件が30個近くあり、方針ファイルが無いと必ず尋ね、
情報が取れなければ止まっていた。結果として、自分のリポジトリでも
ほとんどマージされなかった。今はその逆に振っている。

## 判定

順に見る。どれかに当たったら止めて報告する。当たらなければマージする。

### 1. 自分のリポジトリか

| 見るもの | 止まる条件 |
|---|---|
| owner | 自分の login と違う、または Organization |
| fork | true |
| archived | true |

owner は `git remote get-url origin` からも分かる。API が使えなくてもここは判定できる。

### 2. 他の人が見ていないか

| 見るもの | 止まる条件 |
|---|---|
| star | 2以上（1は自分） |
| fork 数 | 1以上 |
| Pages | 有効 |
| Discussions | 有効 |

Raphael の配布と同じ基準。ここで止まるのは「他人が触る前提の場所」だから。

API が使えず読めないときは、止まらない。owner が自分であることを 1 で
確かめているので、「star と fork は確認できなかった」と報告に書いて進む。
分からないものを全部「該当」にすると、何も進まなくなる。

### 3. 規約が人のレビューを求めていないか

`CLAUDE.md` `CONTRIBUTING.md` `AGENTS.md` `.github/pull_request_template.md` を読む。
「レビュー必須」「approve が要る」「人が確認してからマージ」のような記述があれば止まる。
`.github/CODEOWNERS` があれば止まる。

この条件は設定で外せない。

### 4. PR の状態

| 状態 | やること |
|---|---|
| 作成者が自分でない | 止まる。他人の PR はマージしない |
| 閉じている、マージ済み | 何もしない |
| draft | draft を外して進む |
| コンフリクト | base を取り込んで解決し push。両方が同じ箇所を別々に変えていて選べないときだけ尋ねる |
| CI 実行中 | 待つ。ポーリングしない。完了通知で起きて再判定 |
| CI 失敗 | `ci-triage` に渡す。`cancelled` は失敗ではない |
| CI が無い | 進む |
| CHANGES_REQUESTED のレビュー | 対応してから |

### 5. 差分

| 内容 | やること |
|---|---|
| 秘密情報らしき文字列 | 止まる。`secret-leak-check` で走査する |
| `.github/workflows/` の変更 | 報告に載せて進む |
| LICENSE、依存関係、デプロイ設定、マイグレーション | 報告に載せて進む |
| 100ファイル以上、または 1000 行以上の削除 | 報告に載せて進む |

止まるのは秘密情報だけ。他は「報告に必ず載せる」。黙って通さない。

## マージ

1. squash でマージする。コミットの題は PR の題
2. リモートブランチを消す
3. ローカルを既定ブランチに切り替えて pull。マージ済みのローカルブランチを消す
4. PR の監視を購読していれば解除する
5. 1〜3行で報告する。PR 番号、マージ方式、後片付けの結果、報告に載せるべき差分

## 止まるときの報告

```
止まりました: <条件>
  観測値: <取れた値>
  意味:   <なぜ止めるのか 1行>

続けますか。
```

条件名を挙げずに止まらない。止まったのに黙らない。

## 設定（任意）

`.claude/policy/<login>.json` があれば読む。無くても動く。

| キー | 既定 | 意味 |
|---|---|---|
| `auto_merge` | true | false なら判定と報告だけ |
| `merge_method` | squash | squash / merge / rebase |
| `delete_branch` | true | マージ後にリモートブランチを消す |
| `protected_paths` | `[".github/workflows/"]` | 触れたら報告に載せる |

方針ファイルを作るのは `workspace-policy`。必要になったときだけ使う。
自分のリポジトリで既定のまま動かすなら要らない。

## やらないこと

- 「マージしていいですか」と尋ねる。尋ねるくらいなら条件を挙げて止まる
- CI 待ちで sleep やポーリングをする
- main へ force push する
- 情報が取れないことを理由に止まる。取れなかった項目を書いて進む

## 他のスキルとの関係

- CI が落ちた原因の特定は `ci-triage`
- 差分の秘密情報の走査は `secret-leak-check`
- 方針ファイルを作りたいときは `workspace-policy`
- 判定材料の取り方は `references/commands.md`
