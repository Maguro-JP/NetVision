# Solo PR Flow

個人開発で「PR を作る → CI を待つ → マージ → 後片付け」を確認なしで完走させる。

**このスキルの本体は停止条件である。** 自動マージは取り消しが難しく、公開リポジトリなら
履歴にも残る。だから「進めてよい条件」より**「進めてはいけない条件」を先に、広く**判定する。

判定できる材料は安いが、間違えたときの代償は高い。**迷ったら止める。**

---

## 三つの門

```
第1の門  初回か?          → 初回なら必ず尋ねる。2回目以降は尋ねない
第2の門  停止条件に該当?   → 該当したら報告し、条件のすり合わせをする
第3の門  該当なし          → 尋ねずにマージする
```

### 第1の門: 方針が決まっているか

`.claude/policy/<利用者名>.json` を読む。利用者名は GitHub の login。

**無い、または失効している場合は、ここで `workspace-policy` に渡す。**
このスキルは自分で可否を尋ねない。方針を決めるのはあちらの役目で、
リポジトリの規約を読んだうえで決める必要があるため。

失効の判定は `evidence.policy_digests` と現在の規約ファイルの突き合わせ。
判定の詳細は `workspace-policy` にある。

方針が読めたら、次を確認してから第2の門へ進む。

- `auto_merge` が false → 判定と報告だけ行い、マージはしない
- `human_review_required` が true → 自動マージしない（停止条件 B7）

### 第2の門: 停止条件

下の停止条件を**すべて**確認する。1つでも該当したら自動マージせず、次の形で報告する。

```
停止: <条件番号> <条件名>
  観測値: <実際に取れた値>
  意味:   <なぜ止めるのか 1行>

このまま続けますか? それともこの条件を変更しますか?
  1. 今回だけ続ける（設定は変えない）
  2. 続けて、この条件を今後は許容する（設定に記録する）
  3. 止める
```

利用者が **2** を選んだら `.claude/policy/<利用者名>.json` の `acknowledged` に記録する。
**観測値ごと記録し、値がさらに動いたら再び止める**（下記）。

利用者が **3** を選んだら、そこで終わる。理由を書き足したりしない。

**該当した条件を報告せずに進めてはいけない。** どの条件で止まったかを必ず名指しする。

### 第3の門: 該当なし

**尋ねずにマージする。** 確認を挟むならこのスキルの意味がない。

1. `merge_method`（既定 `squash`）でマージ。コミットメッセージは PR タイトルを使う
2. `delete_branch`（既定 true）ならリモートブランチを削除
3. ローカルを既定ブランチへ切り替えて pull、マージ済みローカルブランチを削除
4. PR の監視を購読していれば解除する
5. 1〜3行で報告。PR番号・マージ方式・後片付けの結果だけ

---

## 停止条件

**広く取る。** 疑わしいものは条件に入れる方を選ぶ。止まっても利用者が「続ける」と言えば済むが、
止まらなかった誤マージは取り消せない。

### A. 情報が取れない

| # | 条件 |
|---|---|
| A1 | 判定に必要な情報の取得に失敗した（APIエラー / 権限不足 / タイムアウト / レート制限） |
| A2 | 値が想定外で解釈できない |

**確認できなかった項目は「該当」とみなす。分からないなら止まる。**

### B. 自分ひとりのものでない

| # | 条件 | 判定材料 |
|---|---|---|
| B1 | 自分が管理者でない | `permissions.admin != true` |
| B2 | オーナーが組織 | `owner.type == "Organization"` |
| B3 | コラボレーターが2人以上 | コラボレーター一覧 |
| B4 | コミット著者が2人以上（bot を除く） | 直近100件のコミット |
| B5 | CODEOWNERS がある | `.github/CODEOWNERS` / `CODEOWNERS` / `docs/CODEOWNERS` |
| B6 | 自分以外が作った issue / PR がある | open な issue と PR の作成者 |
| B7 | 規約が人のレビューやマージを求めている | `human_review_required` が true。根拠は規約ファイルの記述 |

B7 は設定で外せない。リポジトリの規約が人の関与を求めているなら、
リポジトリが誰のものであっても自動マージしない。

### C. 他人が見ている

| # | 条件 | 判定材料 |
|---|---|---|
| C1 | Star が2以上 | `stargazers_count >= 2`（1は自分の自己Star） |
| C2 | Fork されている | `forks_count >= 1` |
| C3 | Watcher が2以上 | `watchers_count >= 2` |
| C4 | リリースまたはタグがある | 公開物として配布されている可能性 |
| C5 | GitHub Pages が有効 | `has_pages` |
| C6 | Discussions が有効で投稿がある | `has_discussions` |

### D. リポジトリの状態

| # | 条件 |
|---|---|
| D1 | `archived` が true |
| D2 | `fork` が true（他人のプロジェクトの派生） |
| D3 | `disabled` が true |
| D4 | テンプレートリポジトリ（`is_template`） |

### E. PR 自体

| # | 条件 | 対応 |
|---|---|---|
| E1 | draft のまま | `draft_is_default` が false のとき停止。勝手に外さない。true なら停止せず draft を外して進む |
| E2 | PR の作成者が自分（またはこのセッションの作業）でない | 他人の PR は絶対にマージしない |
| E3 | base が既定ブランチでない | 意図を確認する |
| E4 | コンフリクトあり | 解決して push。一意に決まらないときだけ尋ねる |
| E5 | CI が失敗 | `ci-triage` に渡す。落ちたステップまで特定してから直す |
| E6 | CI が実行中 / queued | **待つ。ポーリングしない。** 完了通知で起きて再判定 |
| E6b | `cancelled` のチェックがある | 失敗ではない。より新しい実行を探す。詳細は `ci-triage` |
| E7 | チェックが1つも無い | `no_checks` の設定に従う（既定 `proceed`） |
| E8 | CHANGES_REQUESTED のレビューがある | 指摘に対応する |
| E9 | 自分以外のレビューコメントが未解決 | 対応してから |
| E10 | PR が閉じられている / 既にマージ済み | 何もしない |
| E11 | 開いている PR の数が `max_open_prs` を超えている | 先に既存の PR を片付ける |

### F. 差分の内容

**「新規追加」と「既存の変更」を区別する。** 危険なのは多くの場合**既存の取り決めを書き換えること**で、
まだ無いものを初めて置くこととは意味が違う。変更ファイルの `status`
（`added` / `modified` / `removed`）を見て判定する。

| # | 条件 | `added`（新規） | `modified` / `removed` |
|---|---|---|---|
| F1 | `protected_paths` に触れている（既定 `.github/workflows/`） | **停止**（例外は下記 bootstrap） | 停止 |
| F2 | 秘密情報らしき文字列を含む | 停止 | 停止 |
| F3 | LICENSE | 報告のみ | 停止 |
| F4 | `.github/` 配下（workflows 以外） | 報告のみ | 停止 |
| F5 | 依存関係ファイル（package.json、lock、requirements.txt 等） | 報告のみ | 停止 |
| F6 | 公開・配布・デプロイ設定 | 報告のみ | 停止 |
| F7 | データベースのマイグレーション | 停止 | 停止 |
| F8 | 100ファイル以上、または1000行以上の削除 | 停止 | 停止 |

**報告のみ** = 停止しない。ただし報告には必ず載せる。黙って通してはいけない。
この区別は `diff_rules.added` を `"stop"` にすれば無効化できる（新規追加も全部止まる）。

F2・F7・F8 は新規でも停止する。秘密情報は新規かどうかと無関係に危険で、
マイグレーションと大量削除は「新規追加」でも取り返しがつかないため。

#### F1 の bootstrap 例外

`.github/workflows/` は**新規追加でも停止する**。CI 定義は安全装置そのもので、
新しい workflow を1本足すだけでも検査を迂回する経路を作れるため。

例外は1つだけ。**既定ブランチに workflow が1つも存在せず、この PR が最初の CI を置く場合**、
`bootstrap: true` なら停止せず報告のみとする。

- この例外は**自動的に失効する**。一度 workflow が既定ブランチに入れば、以降は常に停止側になる
- **これはこのスキルで最も弱い箇所である。** bootstrap で通す workflow は
  利用者が一度自分の目で読むこと。報告時にその旨を明記する

## 設定 `.claude/policy/<利用者名>.json`

`workspace-policy` が作る。このスキルは読むだけで、`acknowledged` 以外は書き換えない。

```json
{
  "version": 1,
  "user": "Maguro-JP",
  "repo": "Maguro-JP/Ciel",
  "auto_merge": true,
  "merge_method": "squash",
  "delete_branch": true,
  "draft_is_default": true,
  "bootstrap": true,
  "max_open_prs": null,
  "human_review_required": false,
  "no_checks": "proceed",
  "protected_paths": [".github/workflows/"],
  "diff_rules": { "added": "notice" },
  "policy_checks": [],
  "acknowledged": []
}
```

| キー | 既定 | 意味 |
|---|---|---|
| `auto_merge` | `false` | false なら判定と報告だけ |
| `merge_method` | `"squash"` | `squash` / `merge` / `rebase` |
| `delete_branch` | `true` | マージ後にリモートブランチを削除 |
| `draft_is_default` | `false` | true なら draft で停止せず、外して進む |
| `bootstrap` | `true` | 既定ブランチに workflow が皆無のとき、最初の CI 追加を F1 から外す |
| `max_open_prs` | `null` | 同時に開いてよい PR の本数。`null` は制限なし |
| `human_review_required` | `false` | true なら自動マージしない（B7） |
| `no_checks` | `"proceed"` | チェックが1つも無いとき `proceed` / `ask` |
| `protected_paths` | `[".github/workflows/"]` | ここに触れる差分は必ず確認 |
| `diff_rules.added` | `"notice"` | 新規追加ファイルの扱い。`"stop"` で新規も止まる |
| `policy_checks` | `[]` | 規約を検査する CI の名前。落ちてもコードを直さない |
| `acknowledged` | `[]` | すり合わせ済みの停止条件 |

### `acknowledged` の効き方

**観測値に紐づく。** 記録時より状況が進んだら、許容は失効して再び止まる。

| 種類 | 失効の判定 |
|---|---|
| 数値（Star、Watcher、Fork、コラボレーター数など） | 記録時の値を**超えたら**失効 |
| 真偽（archived、fork、has_pages など） | 状態が変わったら失効 |
| 一覧（コミット著者、issue 作成者など） | 記録に無い人物が現れたら失効 |
| 差分の性質（F 系） | **記録しても次回は再び止まる**。差分は毎回別物だから |

`draft_is_default` と `bootstrap` は `acknowledged` ではなく設定で扱う。
前者は運用の宣言であって例外の許容ではなく、後者は自動失効するため。

F 系だけは常に止まる。「前回 LICENSE を変えてよかった」は「今回もよい」の根拠にならない。

**`auto_merge` 以外の設定で停止条件を無効化することはできない。**
設定で決められるのは「どうマージするか」だけで、「マージしてよいか」ではない。

## 原則

- **方針が無ければ `workspace-policy` に渡す。** 自分で可否を尋ねない
- **2回目以降は可否を尋ねない。** それがこのスキルの存在理由
- **停止条件に該当したら、条件名を挙げて報告する。** 黙って進めない、黙って止まらない
- **確認できなかった項目は該当扱い。** 分からないなら止まる
- **停止条件は設定より強い**
- **停止条件は広く取る。** 迷ったら条件に入れる
- **緩めるなら精度を上げる形で緩める。** 「初回だから素通し」ではなく
  「新規追加と既存の変更は危険度が違う」のように、根拠のある区別で緩める
- **CI 待ちで sleep やポーリングをしない。** 完了通知で起きて再判定する
- **main へ force push しない。** どんな状況でもしない
- 「たぶん大丈夫」で進めない。根拠が無いのは A1 に該当する

## 他のスキルとの関係

- 方針を決めるのは `workspace-policy`。このスキルは読むだけ
- チェックが落ちた原因の特定は `ci-triage` が行う（E5、E6b）
- 差分の秘密情報の走査（F2）は `secret-leak-check` を使う

## 判定の順序

リポジトリ側（A〜D）→ PR 側（E）→ 差分（F）の順。
対象外のリポジトリなら PR を調べる意味がなく、往復が減る。

判定材料の取り方と API フィールドの対応は `references/commands.md` を読む。
