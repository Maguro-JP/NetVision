# 致命的なバグの修正版を出す手順

SKILL.md の 5 の 14 手を、手ごとに細かく書いた物です。順番は変えません。急ぐときほど、飛ばした手があとで 2 つ目の事故になります。

出どころ: 公開されているスキルの要点を取り込みました（文は写していません）。Donchitos/Claude-Code-Game-Studios の `hotfix`（MIT）、
duthaho/skillhub の `bugfix`（MIT）、eugenelim/agent-ready-repo の `bug-fix`（Apache-2.0 か MIT）、Semantic Versioning 2.0.0（CC BY 3.0）、
Keep a Changelog 1.1.0（MIT）。どこに何を取り込んだかは docs/SOURCES.md に書いてあります。

## 1. いまの作業を止めて区切る

- 作りかけは、その作業のブランチにコミットします。メッセージは「作りかけ: <何>（致命的なバグ <番号> の修正で中断）」のように、あとで戻れる形にします
- 捨てません。main ブランチにも混ぜません。修正版に、関係の無い作りかけが入るのを避けるためです
- 裏で動かしている長い処理は、止めなくてよいです。結果はあとで読みます

## 2. 帳簿に書く

- `bugs.py --add "<症状>" --severity 致命的 --repro "<再現の手順>" --source "<知った所>"` で足し、`--set <番号> --state 修正中` にします
- 症状は、使う人から見えることを 1 行で書きます（「保存のあとに起動しない」）。原因の推測は書きません
- 似た節が帳簿にもうあれば、新しく足さずに、その節を使います。前に直した物の再発なら、症状の欄に「再発」と元の番号を書きます

## 3. main ブランチから修正のブランチを切る

- `git fetch origin` のあと、`origin/main` から `claude/FIX-<何>-<YYYYMMDD>` を切ります（日付は日本時間）
- main ブランチに、まだ出していない大きな変更が入っていて、修正版に混ぜたくないときは、最後の Release のタグから切ります。
  そのときは、直したあと main ブランチにも同じ修正を入れ、入ったことを `git log` で確かめます。入れ忘れると、次の版でバグが戻ります

## 4. 再現するテストを先に書いて、落ちるのを見る

- 直す前に、バグを再現するテストを 1 つ書き、動かして落ちるのを見ます。落ちた出力を残します
- 落ちた理由が、バグそのものであることを確かめます。import の誤りや、テストの準備の失敗で落ちているテストは、再現ではありません
- テストにできない物（画面の操作、環境に左右される物）は、再現の手順をコマンドか操作の列で書き、1 回動かして、出力か画面を残します
- 再現できないときは、直しません。試したこと、足りない情報（版、環境、手順、データ）を帳簿に書き、❕ で 1 行知らせます。見えていない物を「直した」とは言えません
- 再現の出力に鍵や個人情報が入るときは、伏せてから貼ります

## 5. 最小の修正

- 原因を直します。症状を隠す手当て（例外を握りつぶす、再試行で包む、機能を外す）で終えません
- 関係の無い整理、名前の変更、作り直しを混ぜません。気づいた別の不具合は、帳簿に書いて、この修正には入れません
- 直しが 3 回外れたら、原因の読みが違います。原因の調べ方（common-sense の references/signals.md）に戻ります
- 修正が大きくなり、設計の判断が要るときは、まず害を止める最小の手当て（その機能を安全な側に倒す）を修正版にし、根の直しは次の作業にします。手当てだと分かるように、帳簿と変更履歴に書きます

## 6. テストと code-check

- 4 のテストが通ること、テスト一式が通ること、`code_check.py` の重大が 0 であることを、出力で確かめます
- 最初の再現の手順を、もう一度動かします。新しいテストが通っても、再現の手順で直っていなければ、テストが別の物を見ています
- 直した関数を呼んでいる所をほかに探し、壊れた動きに頼っていた所が無いかを見ます

## 7. 版を上げる

修正版は、patch（3 つ目の数）を 1 つ上げます。一度出した版の中身は、変えません。新しい版として出します（Semantic Versioning 2.0.0 の 3 と 6）。

版を持つ場所は、リポジトリごとに違います。`scripts/version.py` が次を探し、`--bump` で上げたあとの形を出し、`--bump --apply` で書きます。
あった所を全部上げます。一部だけ上げると、インストーラーの版と中身の版がずれます。

| 物 | 版の場所 |
|---|---|
| Node、Electron | `package.json` の `version`。`package-lock.json` があれば、その先頭の `version` と `packages[""]` の `version` |
| Python | `pyproject.toml` の `[project]` か `[tool.poetry]` の `version`。`dynamic` なら `__version__` のあるファイル。`setup.cfg`、`setup.py` |
| Rust、Tauri | `Cargo.toml` の `[package]` の `version`（Tauri は `src-tauri/Cargo.toml`）。`Cargo.lock` の自分のパッケージの行 |
| Tauri | `tauri.conf.json` の `version`（v2 は先頭、v1 は `package` の中）。書いていなければ `Cargo.toml` の版が使われます |
| そのほか | `VERSION` のファイル、インストーラーの設定、画面や `--version` に出す定数 |

- どこにも無ければ、版は上げません。タグも、今までそのリポジトリがタグを付けていなければ、付けません（マージまでが修正版です）
- 場所によって版が違っていたら、`version.py` が注意を出します。上げる前に ❕ で 1 行知らせ、それぞれを 1 つずつ上げます。勝手にそろえません
- 版が `1.2.3` の形でない物（`1.2.3-beta.1` など）は、`version.py` は触りません。そのリポジトリの今までの上げ方（タグの一覧）に合わせて、手で上げます
- 表に無い場所（インストーラーの設定、画面に出す定数）は、`version.py` は探しません。古い版の文字を Grep で探して確かめます

## 8. 変更履歴

- `CHANGELOG.md` があれば、先頭に新しい版の節を作り、直した物を 1 行で書きます。形は、今までのそのファイルに合わせます
- Keep a Changelog 1.1.0 の形なら、節の見出しは `## [1.2.4] - 2026-01-01`、バグ修正は `### Fixed`、脆弱性は `### Security` の下に書きます
- 書くのは、使う人から見えることです（「保存のあとに起動しなくなる問題を直しました」）。コミットの一覧を貼りません
- ファイルが無ければ、新しく作らずに、Release の本文に同じ 1 行を書きます
- 出した版に致命的なバグがあって使ってはいけないときは、その版の見出しに `[YANKED]` を付けます

## 9. ❔ を 1 行だけ出す

precheck を通してから、PR・マージ・修正版の Release をまとめて、1 行で聞きます。帳簿の状態を確認待ちにします。

```
❔ 修正版 <リポジトリ> <版>: <症状>を直しました（<番号>）。再現するテストと precheck は通っています。PR を作り、Actions が通り次第マージまで進めて、Release とタグで修正版を出します。出してよいですか。
```

- リポジトリの名前、版、症状、テストの結果を入れます。確認のフック（pr_gate.py）は、❔ の行にリポジトリの名前か PR の番号があることと、直後の返事を見ます
- この 1 行で、PR の作成、Actions が通ったあとのマージ、Release とタグまでの返事をもらいます。Actions が通る前にマージはしません
- 文は、この形のまま使います。リポジトリの名前を省くと、pr_gate.py が確認として読みません。「マージして」と書くと、actions-watch の Stop フックが、PR の番号の無いマージの確認として差し戻します（作った会話の記録で確かめました）
- 返事が「違う」「待って」「直して」なら、止めます。直してから、もう一度 ❔ を出します

## 10. PR、Actions、マージ

- 返事があり次第、PR を作り、同じターンで `subscribe_pr_activity` で購読します（actions-watch）
- 完了の通知が来たら、❕ で結果を 1 行書き、通っていればそのままマージします。9 の返事が、このマージの確認です
- 落ちたら、ci-triage で原因を読み、直して push します。直したあとは、PR の番号と結果を添えて ❔ を出し直します
- Actions の無いリポジトリでは、9 の ❔ に「Actions は無い」と書きます

## 11. Release とタグ

- リリースの workflow があるかは、`version.py` の出力の「リリースの workflow」の行で見ます。タグの push で動く物か、手で動かす物か、Release の公開で動く物かが出ます
- workflow があれば、それで修正版を作ります。タグの形（`v1.2.4` か `1.2.4`）は、今までのタグに合わせます（同じ出力の「次のタグの形」）
- workflow が無ければ、マージしたあとの main ブランチに `gh release create <タグ> --target main --title "<タグ>" --notes "<変更履歴の 1 行>"` で Release を作ります
- インストーラーや実行ファイルを付けているリポジトリでは、修正版にも同じ物が付いたことを Release のページで確かめます。付いていない修正版は、使う人が入れられません
- 版もタグも持たないリポジトリでは、マージまでが修正版です。Release は作りません

## 12. ★ で周知

```
★ 修正版 <リポジトリ> <版>: <症状>を直しました。<Release か PR の URL>
```

- 使う人がすることがあれば、同じ行に書きます（入れ直す、設定を作り直す、鍵を作り直す）
- 破損や漏洩のバグでは、害を受けたかもしれない範囲（どの版で、何をしたとき）も書きます

## 13. 帳簿と lessons

- `bugs.py --set <番号> --state 修正済み --commit <コミット> --release <版>` で書きます。版を持たないリポジトリは `--release 版なし` です
- lessons に 1 件足します（場面・起きたこと・判定の誤り・次から）。書くのは、なぜ出す前に見つけられなかったかです
- 見つけられなかった原因がテストの抜けなら、4 のテストがその抜けを塞いでいることを確かめます

## 14. 止めた作業に戻る

- 1 でコミットした作業のブランチに戻り、main ブランチを取り込みます（修正が入った main ブランチの上で続けます）
- ほかに直していない致命的が帳簿に無いことを、`bugs.py --count` で見てから戻ります

## 漏洩のとき

- 鍵、トークン、個人情報が外に出たバグでは、secret-leak-check の手順に先に入ります。鍵のローテートの案内が先です。コードを直しても、出た鍵は戻りません
- 帳簿、コミットメッセージ、PR の本文、変更履歴に、漏れた値そのものを書きません。場所と種類だけを書きます
- 履歴に残った値の扱い（履歴の書き換え、GitHub 側のキャッシュ）は、secret-leak-check と content-audit の手順に従います

## 破損のとき

- 直す前に、壊れたデータを増やさない手当てをします。書き込みを止める（その機能を外す、読み取り専用にする）、壊れる前のデータを退避する、のどちらかです
- 手当てだけの版を先に出し、根の直しをそのあとに出してもかまいません。手当ての版も、この手順で出します
- 壊れたデータを戻せるかを調べ、戻せるなら、戻す手順を周知に書きます。戻せないなら、戻せないと書きます
