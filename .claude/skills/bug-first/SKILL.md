# 何よりもバグ修正を優先する

ユーザーの決まりは 2 つです。

1. 何よりもバグ修正を優先させて
2. 特に致命的なバグ、クラッシュや操作不能、破損や漏洩等は即修正版を出せ

指摘は「バグも放置」です。放置は、次の 3 つがそろうと起きます。

- バグを見つけても、いま進めている作業を続ける。新しい機能や成果物は、進んだ量が数に出るためです
- 見つけたバグを書く場所が無い。会話の中だけにあり、セッションが閉じると消えます
- 直しても修正版を出さない。main ブランチは直っても、使う人の手元は壊れたままです

このスキルは、優先の順番、帳簿、修正版の手順で、この 3 つを塞ぎます。

## 1. 優先の順番

| 先 | あと |
|---|---|
| バグ修正 | 新しい機能、作り直し、文書、いま進めている成果物（finish-first）、スキルの手入れ |

開発のサイクルごとに、最初に「直していないバグがあるか」を見ます。見る物は 3 つです。

1. 帳簿を見ます。`python3 .claude/skills/bug-first/scripts/bugs.py --list --open`
2. main ブランチのテストと Actions を見ます。落ちていれば、それはバグです
3. code-check の重大（crash・vuln・info）を見ます

1 件でもあれば、それを先に直します。ユーザーが別の作業をはっきり指示したときは指示に従い、
`❕ バグ: <残っているバグと、先にしなかった理由>` を 1 行書きます。

## 2. バグを知る所

| 知る所 | 見方 |
|---|---|
| ユーザーの発言 | 「落ちる」「固まる」「動かない」「消えた」などの語があれば、バグの報告として受けます |
| main ブランチで落ちているテストと Actions | テストを動かします。Actions は ci-triage の手順で読みます |
| クラッシュの出力 | Traceback、panic、Unhandled、Segmentation fault、core dumped、FATAL が出た実行です |
| code-check の重大 | `code_check.py` の crash・vuln・info の重大です |
| Issue | open の Issue のうち、不具合の報告です |
| 帳簿 | 前のセッションが書いた、直していない節です |

知ったら、その場で帳簿に書きます。すぐ直せる物も、書いてから直します。書かないと、数にも報告にも残りません。

## 3. 帳簿

場所は `docs/reports/bugs.md` で、1 件 1 節です。ひな形は `assets/bugs.md` にあり、最初の 1 件を足すときに作られます。
欄は、症状、重さ、見つけた日、知った所、再現の手順、状態、直したコミット、修正版、直した日です。

| 状態 | 意味 |
|---|---|
| 未修正 | 知っただけで、まだ直し始めていない |
| 修正中 | 修正のブランチで直している |
| 確認待ち | 修正は済み、PR と修正版の ❔ の返事を待っている |
| 修正済み | マージし、修正版を出した（版を持たないリポジトリは、マージまで） |
| 対象外 | バグではなかった、再現しない。理由を症状の欄に足す |

| コマンド（`scripts/bugs.py`） | すること |
|---|---|
| `--list [--open] [--json]` | 一覧を出します。`--open` は直していない物だけです |
| `--add "<症状>" [--severity 致命的\|重い\|軽い] [--repro "<再現の手順>"] [--source "<知った所>"]` | 1 件足します。重さを書かなければ語から決め、迷う物は重い側にします |
| `--set B-003 --state 修正済み --commit <コミット> --release <修正版>` | 節を書き換えます。修正済みにすると、直した日が入ります |
| `--count [--strict]` | 直していない致命的を数えます。`--strict` は 1 件でもあれば終了コード 1 です |
| `--stats [--since YYYY-MM-DD]` | 日報・週報に写す 1 行を出します（見つけた、直した、残り、致命的を直すまでの時間） |

- 漏洩のバグでは、漏れた値そのものを帳簿に書きません。場所と種類だけを書きます。public のリポジトリでは、帳簿も人に見えます
- 悪用できる脆弱性の再現の手順は、public のリポジトリでは、修正版を出したあとに書き足します

## 4. 重さ

| 重さ | 当たる物 | 扱い |
|---|---|---|
| 致命的 | クラッシュ、起動しない、操作不能、データの破損や消失、情報の漏洩、悪用できる脆弱性 | 今の作業を止めて、修正版を即出す（5） |
| 重い | 主な機能が動かない。回避はできる | その日の開発の最初に直す |
| 軽い | 見た目、文言、まれな場面 | 次の PR にまとめる |

迷ったら重い側にします。例と決め方は `references/severity.md` にあります。

## 5. 致命的: 修正版を即出す

細かい決まり（版の場所、変更履歴の書き方、❔ の文、Release の出し方）は `references/hotfix.md` にあります。

1. いまの作業を止めて区切ります。作りかけは、その作業のブランチにコミットします（捨てない、main ブランチに混ぜない）
2. 帳簿に書き（`bugs.py --add`）、状態を修正中にします
3. main ブランチから修正のブランチを切ります（`claude/FIX-<何>-<YYYYMMDD>`）
4. 再現するテストを先に書いて、落ちるのを見ます。落ちた理由がバグそのものであることを、出力で確かめます
5. 最小の修正をします。ついでの整理や作り直しを混ぜません
6. テスト一式と code-check を通します。最初の再現の手順も、もう一度動かします
7. 版を上げます。`scripts/version.py` で、そのリポジトリが版を持つ場所を探し、`--bump --apply` で patch を 1 つ上げます。どこにも無ければ上げません
8. 変更履歴に書きます。CHANGELOG があれば 1 行足し、無ければ Release の本文に書きます
9. precheck を通し、❔ を 1 行だけ出します（8 の決まり）。帳簿の状態を確認待ちにします
10. 返事があり次第、PR を作り、Actions の通知を待ち、通ったらマージします
11. Release とタグで修正版を出します。そのリポジトリにリリースの workflow があれば、それで作ります
12. ★ で周知します（何が起きていたか、どの版で直ったか、使う人がすること）
13. 帳簿を修正済みにしてコミットと修正版を書き、lessons に 1 件書きます
14. 止めた作業に戻ります

- 漏洩のときは、secret-leak-check の手順に先に入ります。鍵のローテートの案内が先で、修正はそのあとです
- 破損のときは、直す前に、壊れたデータを増やさない手当てを先にします（書き込みを止める、退避する）
- 再現できないときは、推測で直しません。試したことと、足りない情報（版、環境、手順）を 1 行で書き、帳簿に残します

## 6. 重い・軽いの扱い

- 重いバグは、その日の開発の最初に直します。auto-dev の作業を選ぶ表では、先頭に来ます
- 軽いバグは、次の PR にまとめます。帳簿に書いたまま、月をまたいで残しません（月に 1 回の整理整頓で見ます）
- どちらも、直し方は 5 の 4〜6 と同じです（再現するテストを先に、最小の修正、テストと code-check）

## 7. 自分で気づいた不具合を、黙って残さない

作業の途中で気づいた不具合（落ちたテスト、警告、直していない `TODO`、予想と違う出力）は、直すか、帳簿に書くかのどちらかにします。
「今回の変更とは関係が無い」は、黙って残す理由になりません。関係が無くても、帳簿には書けます。
返答を終える前に、気づいたのに書いていない物が無いかを見ます。

## 8. 確認のゲートとの関係

- PR の作成・マージ・main への push の前の確認（pr_gate.py）は、そのまま残ります
- 致命的の修正版の Release とタグは、ユーザーが「即修正版を出せ」と決めたので、頼まれた物として出します（tidy の「Release とタグは頼まれたときだけ」の、頼まれた側です）
- ❔ は、修正・テスト・版・変更履歴・precheck まで全部済ませてから、1 行だけ出します。返事があり次第、その場で PR・マージ・Release まで出します
- マージは、Actions が通ったあとです（actions-watch の ci_merge_gate.py）。落ちたら ci-triage で直し、直したあとの ❔ は、PR の番号と結果を添えて出し直します
- 自律で回っていて返事が無いときは、修正のブランチを push し、`docs/reports/pending.md` の先頭に「修正版の PR 待ち」と書きます。確認待ちの間は、次のバグか、止めた作業に進みます
- 確認そのものを外すのは、ユーザーが自分の手でゲートを変えたときだけです。AI は自分に権限を付与しません

## フック

| 何 | いつ | すること | 止めるか |
|---|---|---|---|
| `hooks/bug_prompt.py` | UserPromptSubmit | ユーザーの発言にバグの症状の言い方があるとき、「バグ修正が最優先。重さを決めて帳簿に書き、致命的は今の作業を止めて修正版を出す」を 1 行 | 止めない |
| `hooks/bug_prompt.py` | SessionStart | 帳簿に、直していない致命的か重いがあるとき、件数と先頭の 1 件を 1 行 | 止めない |
| `hooks/bug_gate.py` | Stop | 直していない致命的があるのに、このターンでそれを直す以外の開発の編集をして終えるとき | 止める。直すか、帳簿の状態を変えるか、`❕ バグ: <理由>` で通る |
| `hooks/crash_nudge.py` | PostToolUse（Bash） | 出力にクラッシュのマークがあり、テストの出力ではないとき、帳簿に書いて先に直すよう 1 行。同じ出力には 1 回だけ | 止めない |

- `BUG_FIRST_OFF=1` で 3 本とも止まります（ユーザーが自分の手で入れます）
- 帳簿が無いリポジトリでは、`bug_gate.py` と SessionStart の行は何もしません
- 差し戻しの文は 1 行です。差し戻されたら、足りない 1 行だけを足します。`stop_hook_active` が真なら通します
- `bug_gate.py` が修正と見るのは、帳簿を書き換えた、呼び出しにその節の番号がある、編集したファイルが修正のブランチ（名前に `fix`、`hotfix`、`bug`）にある、のどれかです
- PostToolUse は成功したツールでしか動きません。失敗した実行のクラッシュは、次に成功した Bash のときに、会話の記録から拾います。
  記録の読み方は common-sense の `_cs.py` に合わせてあり、common-sense が無いリポジトリでは、`bug_gate.py` は黙って通り、`crash_nudge.py` は成功した実行の出力だけを見ます
- 偽の差し込みを減らすため、`bug_prompt.py` は、問い（「バグは無い?」）、決まりの話（「落ちたら直して」）、語そのものの話、テストや Actions が落ちた話には出しません
- 同じ失敗が 3 件以上並ぶ出力と、同じ失敗の 2 回目は common-sense の `odd_nudge.py` が言うので、`crash_nudge.py` は重ねて言いません
- テストは `scripts/test_bugs.py`、`scripts/test_version.py`、`scripts/test_hooks.py` です

## 使わないとき

- 作った物の穴を機械で探す（code-check）、依存の CVE の見張り（vuln-watch）、鍵の有無（secret-leak-check）
- 落ちた Actions の原因の特定（ci-triage）、原因の調べ方（common-sense の references/signals.md）
- 新しい機能の要望と、仕様の変更（バグではありません。成果物の表に書きます）

## 他のスキルとの関係

重なる決まりは、docs/GUIDELINES.md の 10 に、どちらに従うかを書いてあります。

- auto-dev と long-dev は、サイクルの最初にこの帳簿を見ます。finish-first の「未完成があるうちは新しい成果物を始めない」より、バグ修正が先です
- code-check の重大と、ci-triage で分かった main ブランチの失敗は、帳簿に書きます
- dev-report は、`bugs.py --stats` の 1 行を日報・週報に写します
- PR とマージの流れは solo-pr-flow、Actions の通知は actions-watch、失敗の記録は lessons が持ちます
