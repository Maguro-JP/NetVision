# スキルの手入れ

スキルは使われて初めて穴が分かる。走っているセッションが詰まった所、利用者が直させた所、
各リポジトリの lessons に溜まった失敗が、次に直すべき場所を教える。
週に1回、それを Ciel に戻す。土曜 0:00 JST に直せば、9:00 JST の配布で全リポジトリに届く。

## 1周の流れ

### 1. 観察

- `list_sessions` で動いているセッションを見る。題名、`post_turn_summary`、`context_usage`、`rate_limit_info`。止まっている・同じことを繰り返している・文脈が膨らんでいるものを控える
- `list_triggers` で Routine を見る。起きたのに成果が無いもの、一回きりのまま残っているもの
- 各リポジトリ（Routine の結びつけ先）で、この1週間の PR の題と、`.claude/skills/lessons/LESSONS.md` に増えた項目、`docs/reports/pending.md` の答え待ちを読む
- 利用者がこの1週間に直させたこと（Ciel の git log と lessons）

止まっているセッション（IDLE で次の起床が無い）があれば、`patrol` の判定に従って一回きりの Routine で起こす。

### 2. 教訓の収穫

リポジトリの LESSONS.md にあって Ciel に無い項目のうち、そのリポジトリに限らないものを
Ciel の LESSONS.md に写す。固有名（非公開リポジトリの名前、ID、メール）は伏せる。

### 3. 改修

使われているスキルから順に見る（auto-dev、long-dev、feedback-session、dev-report、solo-pr-flow、skill-sync）。

| 見えたもの | 直し方 |
|---|---|
| 同じ失敗が2つ以上のセッションで出た | その場面の決まりをスキルに足す。lessons にも1件 |
| 利用者が同じ指示を2回以上送った | 指示をスキルの本文に入れる。次から言わせない |
| 会話が流れている | 会話に出すものの形を直す（work-style の4種類） |
| スキルの手順と実際の動きが違う | 動きに合わせて書き直すか、動きを直す。観測したことだけ書く |

直す前に、そのスキルをこのセッションで1回使い、書いてあることと実際の動きの差を見る。使わずに直さない。
1つ直すごとに `./scripts/validate.sh` と `scan.py --diff` を通し、PR を1本にして `solo-pr-flow` でマージする。

### 3.5 自分のための開発

Ciel 自身の道具（`scripts/`、`.claude/hooks/`、各スキルの `scripts/`）も直してよい。
検査の抜け、配布の取りこぼし、門（gate.sh）の誤差し戻し、観察に手間がかかる所。
使っていて手間だと感じた所が候補。1周1件まで。

精度は数で見る。前の週と比べて報告に書く。

| 物差し | 取り方 |
|---|---|
| 同じ場面の失敗が翌週も出たか | Ciel と各リポジトリの LESSONS.md の「場面」の重なり |
| 利用者が直させた回数 | Ciel の git log のうち、利用者の指示で直したコミットの数 |
| 門の差し戻し | 各リポジトリの transcript は読めないので、スキルの「会話に出すもの」に外れた PR の説明・コミット文の数で代える |
| Routine の成果 | 起きた回数に対して、リポジトリにコミットか PR が増えた回数 |

数が良くならない物差しがあれば、次の週の改修はそこに絞る。

### 4. 新作

次のどれかに当たったら、新しいスキルを作る。当たらなければ作らない。

- 同じ手順を2つ以上のリポジトリかセッションで組み立てていた
- 利用者が同じ種類の依頼を2回以上した
- 既存のスキルに書くと、そのスキルの責務がぼやける

作るときは `docs/GUIDELINES.md` に従い、description に発動する場面と発動しない場面を書く。
名前は work-style「名前の付け方」に合わせ、利用者に一言で説明できるものにする。

### 5. 報告

Ciel の `docs/reports/weekly/YYYY-Www.md` に、直したスキル・作ったスキル・写した教訓・見送ったものを表で書く。
Ciel は public なので、非公開リポジトリの名前と ID は伏せる（「あるリポジトリ」「リポジトリ A」）。
会話には `★ skill-upkeep <週>: <PR の URL>。直した N、作った N、教訓 N` の1行だけ。

## 判断の決まり

- 人が決めたこと（出力の形、名前、方針）は変えない。変えたくなったら `❔` で1行聞いて、答えが来るまでそのまま
- 走っているセッションの枝・PR・Routine には触らない。観察だけ
- 走っているセッションにスキルの直しは届かない（起動時に読まれる）。届けたいことは一回きりの Routine で1行送る
- 1周で直すのは3件まで。多く直すと、どれが効いたか分からない

## 会話に出すもの

work-style の4種類だけ。始め `❕ skill-upkeep <週>: 観察を始める`、終わり `★ ...`、決めてほしいことは `❔`。
3行を超える説明は報告のファイルへ。

## 他のスキルとの関係

- 1つのスキルの診断: `skill-audit`。配る: `skill-sync`（毎週土曜 9:00 JST は配布側が自動で行う）
- 失敗の記録: `lessons`。全体を見る: `patrol`。判断待ち: `pending`
- Routine の作り方: `scheduler`
