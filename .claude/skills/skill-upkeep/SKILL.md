# スキルの手入れ

スキルは使われて初めて穴が分かる。走っているセッションが詰まったところ、ユーザーが直させたところ、
各リポジトリの lessons に溜まった失敗が、次に直すべき場所を教える。
週に1回、それを Ciel に戻す。土曜 0:00 JST に直せば、9:00 JST の配布で全リポジトリに届く。

## 1周の流れ

### 1. 観察

- `list_sessions` で動いているセッションを見る。タイトル、`post_turn_summary`、`context_usage`、`rate_limit_info`。止まっている・同じことを繰り返している・文脈が膨らんでいるものを控える
- `list_triggers` で Routine を見る。実行されたのに成果がないもの、1回きりのまま残っているもの
- 各リポジトリ（Routine の紐づけ先）で、この1週間の PR のタイトルと、`.claude/skills/lessons/LESSONS.md` に増えた項目、`docs/reports/pending.md` の答え待ちを読む
- ユーザーがこの1週間に直させたこと（Ciel の git log と lessons）
- Ciel に `content-audit` の `--all` と `ja-proofread` の `--tree` を当て、見せてはいけないものと壊れた日本語が増えていないか見る。見つかったら直す PR を先に出す

止まっているセッション（IDLE で次の実行がない）があれば、`patrol` の判定に従って1回きりの Routine で起動する。
週の上限（`rate_limit_info.status` が `rejected`）で止まったものは起こさない。枠の使い道はユーザーが決める（patrol）。

### 2. 教訓の収穫

リポジトリの LESSONS.md にあって Ciel にない項目のうち、そのリポジトリに限らないものを
Ciel の LESSONS.md に写す。固有名（非公開リポジトリの名前、ID、メール）は伏せる。

### 3. 改修

使われているスキルから順に見る（auto-dev、long-dev、feedback-session、dev-report、solo-pr-flow、skill-sync）。

| 見えたもの | 直し方 |
|---|---|
| 同じ失敗が2つ以上のセッションで出た | その場面の決まりをスキルに足す。lessons にも1件 |
| ユーザーが同じ指示を2回以上送った | 指示をスキルの本文に入れる。次から言わせない |
| 会話が流れている | 会話に出すものの形を直す（work-style の4種類） |
| スキルの手順と実際の動きが違う | 動きに合わせて書き直すか、動きを直す。観測したことだけ書く |

直す前に、そのスキルをこのセッションで1回使い、書いてあることと実際の動きの差を見る。使わずに直さない。
1つ直すごとに `./scripts/validate.sh` と `scan.py --diff` を通し、PR を1本にして `solo-pr-flow` でマージする。

### 3.5 自分のための開発

Ciel 自身のツール（`scripts/`、`.claude/hooks/`、各スキルの `scripts/`）も直してよい。
検査の抜け、配布の取りこぼし、ゲート（gate.sh）の誤差し戻し、観察に手間がかかるところ。
使っていて手間だと感じたところが候補。1周1件まで。

精度は数で見る。前の週と比べて報告に書く。

| 物差し | 取り方 |
|---|---|
| 同じ場面の失敗が翌週も出たか | Ciel と各リポジトリの LESSONS.md の「場面」の重なり |
| ユーザーが直させた回数 | Ciel の git log のうち、ユーザーの指示で直したコミットの数 |
| ゲートの差し戻し | 各リポジトリの transcript は読めないので、スキルの「会話に出すもの」に外れた PR の説明・コミット文の数で代える |
| 会話の形から外れた数 | Ciel のセッションでは `~/.claude/state/verify-before-done/metrics.jsonl`（done_check.py が返答ごとに書く）の、マーク以外の行・2 つ以上の ❔・根拠の無い完了の数 |
| 短い一言の数と、そのあとの聞き返し | Ciel のセッションでは `~/.claude/state/prompt-from-context/metrics.jsonl`（brief.py が短い一言ごとに書く）の件数と、同じセッションの直後の返答で ❔ を出した数（verify-before-done の metrics.jsonl の questions） |
| ツールの出力に根拠の無い主張、矛盾、撤回 | 同じ metrics.jsonl の unbacked（完了の語の種類の一覧）、contradiction、retraction の数 |
| Routine の成果 | 実行された回数に対して、リポジトリにコミットか PR が増えた回数 |

数が良くならない物差しがあれば、次の週の改修はそこに絞る。

### 4. 新作

次のどれかに当たったら、新しいスキルを作る。当たらなければ作らない。

- 同じ手順を2つ以上のリポジトリかセッションで組み立てていた
- ユーザーが同じ種類の依頼を2回以上した
- 既存のスキルに書くと、そのスキルの責務がぼやける

作るときは `docs/GUIDELINES.md` に従い、description に発動する場面と発動しない場面を書く。
名前は work-style「名前の付け方」に合わせ、ユーザーに一言で説明できるものにする。

### 5. 報告

Ciel の `docs/reports/weekly/YYYY-Www.md` に、直したスキル・作ったスキル・写した教訓・見送ったものを表で書く。
Ciel は public なので、非公開リポジトリの名前と ID は伏せる（「あるリポジトリ」「リポジトリ A」）。
会話には `★ skill-upkeep <週>: <PR の URL>。直した N、作った N、教訓 N` の1行だけ。

## 判断の決まり

- 人が決めたこと（出力の形、名前、方針）は変えない。変えたくなったら `❔` で1行聞いて、答えが来るまでそのまま
- 走っているセッションのブランチ・PR・Routine には触らない。観察だけ
- 走っているセッションにスキルの直しは届かない（起動時に読まれる）。届けたいことは1回きりの Routine で1行送る
- 1周で直すのは3件まで。多く直すと、どれが効いたか分からない

## 会話に出すもの

work-style の4種類だけ。始め `❕ skill-upkeep <週>: 観察を始める`、終わり `★ ...`、決めてほしいことは `❔`。
3行を超える説明は報告のファイルへ。

## 他のスキルとの関係

- 1つのスキルの診断: `skill-audit`。配る: `skill-sync`（毎週土曜 9:00 JST は配布側が自動で行う）
- 失敗の記録: `lessons`。全体を見る: `patrol`。判断待ち: `pending`
- Routine の作り方: `scheduler`
