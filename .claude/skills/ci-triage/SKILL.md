# CI Triage

GitHub のチェックを読んで、何が起きているかを確定させる。

「CI が落ちました」で報告を止めない。**どのチェックの、どのジョブの、どのステップが、
なぜ落ちたか**まで特定してから報告する。そこまで見ないと、結局もう一度取りに行くことになる。

## 手順

### 1. 対象のコミットを確かめる

チェックは `head_sha` に紐づく。**新しいコミットを push した後に古い結果を見ると、
直したものが落ちたままに見える。**

PR の現在の `head.sha` と、見ているチェックの `head_sha` が一致していることを先に確認する。

### 2. チェック一覧を取る

一度にまとめて取る。1件ずつ往復しない。

`status` が `completed` になったものだけ `conclusion` を見る。
`queued` と `in_progress` の間は判定を保留する。

### 3. conclusion を分類する

| conclusion | 扱い |
|---|---|
| `success` | 合格 |
| `skipped` / `neutral` | 合格として扱う |
| `cancelled` | **失敗ではない。** 下記を読む |
| `failure` / `timed_out` | 不合格。原因を特定する |
| `action_required` | 人の操作が要る。尋ねる |
| `stale` | 古い実行。無視して現在の結果を見る |

#### cancelled を失敗として報告しない

多くのリポジトリは `concurrency` に `cancel-in-progress: true` を設定している。
新しいコミットを push すると、走っていた古い実行が `cancelled` になる。

これを失敗として報告すると、**直っているのに落ちていると言うことになる**。

`cancelled` を見たら、同じワークフローのより新しい実行があるかを確認する。
あればそちらが本当の結果。無ければ、何かが中断させたので原因を調べる。

### 4. チェックの性質を見分ける

**落ちたときにやることが、チェックによって違う。**

| 種類 | 見分け方 | 落ちたときにやること |
|---|---|---|
| コードの検査 | test、lint、build、typecheck など | コードを直して push |
| 規約の検査 | 名前に policy、規約、rule。PR の出し方を検査する | **コードは正しい。** PR の出し方を直す |
| 配布物の生成 | release や workflow_dispatch でのみ走る | PR では走らない。待たない |

`.claude/policy/<利用者名>.json` の `policy_checks` に、規約を検査する CI の名前が
入っていることがある。入っていればそれを使う。

**規約の検査が落ちたときにコードを直そうとするのは完全な的外れ。**
その PR の base が違う、未マージの PR が残っている、といった出し方の問題なので、
直すのは PR であってコードではない。

### 5. 失敗したジョブのログを読む

チェックの名前だけでは何が起きたか分からない。ジョブは複数のステップからなる。

1. 失敗したジョブのログを取る
2. 失敗したステップを特定する
3. そのステップのエラー行を抜き出す

ログは長い。**全部読まず、失敗したステップの周辺だけを見る。**
`##[error]` や `Error:`、`FAILED`、`exit code` を手がかりにする。

### 6. 直す

| 原因 | やること |
|---|---|
| コードの不具合 | 直して push。CI の完了通知を待って再判定 |
| 依存の解決に失敗 | 再実行で直ることがある。2回続けて落ちるなら本物 |
| 規約違反 | PR の base、枝、開いている PR の数を直す |
| 基のブランチが既に壊れている | その PR の問題ではない。1行で報告して待つ |
| 直せない | 何がどう落ちているかを1〜2行で報告して止まる |

**基のブランチで再現するかを確認する。** 自分の差分が原因でないものを
直そうとして時間を溶かさない。

### 7. 待つ

**ポーリングしない。sleep で待たない。**

チェックが `queued` や `in_progress` の間は、そこで判定を止める。
完了の通知で起きてから再判定する。

## 報告の形

```
CI: 1件失敗

  ci / backend  failure
    ステップ: ruff check .
    backend/app/main.py:42:1  F401 'os' imported but unused

  ci / frontend  success
  PR policy      success

対応: 未使用の import を削除して push します
```

書くこと。

- 失敗したチェックの名前とジョブ名
- 落ちたステップ
- エラーの実体（推測ではなく、ログの該当行）
- 次にやること

書かないこと。

- ログの貼り付け
- 「CI が落ちました」だけの報告
- 原因が分からないのに分かったふりをした要約

## 原則

- **cancelled を失敗として報告しない**
- **規約の検査とコードの検査を区別する。** 前者でコードを直さない
- **落ちたステップまで特定してから報告する**
- **ポーリングしない。** 完了の通知で起きる
- **見ているチェックが現在の head のものか確かめる**
- 分からないものを分かったように書かない。ログの該当行を引く

## 他のスキルとの関係

`solo-pr-flow` の E5（CI が失敗）と E6（CI が実行中）の中身をこのスキルが引き受ける。
規約を検査する CI の名前は `workspace-policy` が `policy_checks` に記録する。

状態の値の意味、ログの取り方、コマンドの対応は
`references/reading-checks.md` を読む。
