# トークン節約

ユーザーの目とトークンは、いちばん足りない資源。文脈は保存場所ではなく注意の予算で、
埋まるほど判断が鈍る。だから節約は、費用の前に正しさの問題。

最適化するのは、この1ターンの短さではなく、セッション全体の合計。
要る質問や検証を削ると手戻りが起き、削った分より高くつく。

## 3つの層

| 層 | 何 | いつ |
|---|---|---|
| 常時 | `CORE.md`（8行）。`hooks/efficiency_core.py` が UserPromptSubmit で差し込む。1ターン目と 10 ターンごとに全文、ほかは `CORE_SHORT.md` の1行 | 毎ターン |
| 見張り | `hooks/trajectory_guard.py` が PostToolUse で、変わっていないファイルの読み直し・編集直後の読み直し・探さずに全体を読む・通った検査の再実行、の4つだけを見つけて1行知らせる。1セッション 12 回まで | 起きたときだけ |
| 報告 | `hooks/session_report.py` が Stop で、所要時間・入出力トークン・キャッシュ率・ツール回数を `systemMessage` で端末に出す（文脈には乗らない）。無駄が 3 件たまったときだけ文脈に1行 | 返答の終わり |

スキル本文はモデルが呼ぶときだけ読まれるので、「毎回守る」決まりはフックで差し込む。
差し込む量は小さく保つ（全文で約 130 トークン、ほかのターンは約 35 トークン）。フックの出所は下の表。

## 1. 測る

```bash
.claude/skills/token-efficiency/scripts/budget.py          # このリポジトリが常時読ませている量
```

CLAUDE.md、全スキルの description、フックの出力を数え、300 文字を超える description を挙げる。
セッションの消費は `get_session` の `context_usage`、手元の端末では `/context` と `/cost`。
数字を横に置くところまでがこのツールの仕事で、削るかはユーザーが決める。

消費の出どころは4つ（valorisa の整理）。キャッシュの外れ、文脈の膨らみ、重すぎるモデルや effort、冗長な入力の形。
途中で MCP やツールを足すとキャッシュが外れて全部読み直すので、ツールはセッションの前にそろえる。

## 2. 会話と推論

- 答えの形（数、判断、ファイル、はい・いいえ）を先に決めて、そこへ向けて考える
- 分かっていることを再導出しない。確かめるのは間違えやすい段（計算、端の条件）だけ。1回で終える
- 返事は ★ ↩ ❕ ❔ の1行。3行を超えるものはファイルへ（work-style）
- 前置き、依頼の言い直し、締めの要約、「次は〜します」を書かない
- 簡単な答えに見出しや箇条書きを被せない。長さは質問に合わせる

## 3. ツールの使い方

| 場面 | する | しない |
|---|---|---|
| ファイルを探す | Grep、Glob で行を絞ってから、その範囲を Read | 200 行超のファイルを探さずに全部読む |
| 編集のあと | 次の工程（テスト、実行）で確かめる | 編集が入ったか見るために読み直す |
| 検査・テスト | 落ちた、不安定、依存が変わった、のときだけ回し直す | 通ったあとに「念のため」もう1回 |
| 複数の呼び出し | 互いに依存しないものは1ターンにまとめる | 1つずつ直列に出す |
| 長い出力 | `--stat`、`head`、`tail`、`grep`、`--format json` と抽出。ファイルに落として落ちた行だけ読む | ログや JSON をそのまま文脈に入れる |
| 一覧の MCP | `list_sessions`、`list_triggers` には `limit` と絞り込み。1件なら `get_session`、`get_trigger` | 全件を取って目で探す |
| 広い調べもの | サブエージェント（Explore）に任せ、結論だけ受け取る | 20 ファイルを自分で順に読む |
| 返事に貼る | file:line で指す | ツールの出力を本文に貼り直す |
| PR の購読 | 自分でマージまで見るなら購読を切る。通知1件は約 9 千文字 | CI 完了やマージの通知で起きて、会話全体を読み直す |
| 一回きりの Routine | 起きたら消す（tidy） | 一覧に残して `list_triggers` を太らせる |

## 4. 文脈の寿命

- 覚えておくことは会話ではなくファイルに書く（`docs/knowledge/`、`pending.md`、記録）。圧縮を越えて残るのはファイルだけ
- 圧縮が近いと分かったら、先にパスと決めたことと残りをファイルに書く。あとから探し直すより安い
- 結論が出た調べものは、以後は結論だけを指す。元の出力を引き回さない
- 1セッション1トピック。並列にするならセッションを分ける（feedback-session）。1つに積むと 100 万トークンで頭打ちになる
- 自律の作業（auto-dev、long-dev）は、このスキルの 3 と 4 を「文脈を小さく保つ」の中身として使う

## 5. 仕組み側で減らす

リポジトリが毎ターン読ませているものは、仕事と関係なく積もる。`budget.py` で数えて、候補を出す。

| 候補 | 目安 | なぜ |
|---|---|---|
| description を発動の語だけに | 300 文字以内（validate.sh が注意を出す） | 名前と description は全スキル分が毎ターン読まれる |
| SessionStart で差し込む本文 | 要点だけ | 開始・再開・圧縮のたびに全文が乗る |
| CLAUDE.md | 常時要る決まりだけ。手順はスキルへ | 常時読まれる |
| フック | 同じ事象のフックは1本にまとめる | 1本ごとに出力が足される |
| MCP とプラグイン | その仕事に要るものだけ | ツールの一覧も常時読まれる |

削るかはユーザーが決める。費用を数字で横に書いて、提案する。

## 6. 削らないもの

- 正しさ。注意書き、端の条件、安全に関わる1文
- 要る質問。曖昧なまま進めて外す方が高い
- 検証の実行。省いて「通りました」と書くのは推測
- ツールやサブエージェントが一発で成功するための文脈。削って2往復になる方が高い
- 長い作業の記録。書く手間より、探し直す手間の方が大きい
- ユーザーが「詳しく」「徹底的に」と言ったとき。短さはデフォルトであって、依頼より上ではない（フックが見分けて歯止めを差し込む）

## 7. 送る前の点検

1. 最初の文を消しても失うものがないなら消す
2. 最後の段落が本文の繰り返しなら消す
3. 言い訳、「〜と思われます」、依頼の言い直しが残っていないか
4. ツールを呼んだターンなら、再確認・直列・貼り直しがなかったか。あれば次から直す
5. 二度と要らないものを文脈に入れていないか。残す結論は、圧縮を越える場所（ファイル）にあるか
