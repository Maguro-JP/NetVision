# 完了前の検証

「できた」と言えるのは、動かして、その出力を見せたときだけ。
書いただけ、通るはずと思っただけでは、まだできていない。

## 手順

### 1. 何を動かせば「できた」と言えるかを先に決める

変更に手を付ける前に、1行で書く。
「`validate.sh` が誤り 0 で終わる」「1リポジトリで PR がマージ済みになる」のように。
これが決まっていないと、あとで都合のいい確認を選んでしまう。

### 2. 本番の前に1件で試す

書き込みを伴う作業は、全件に当てる前に1件で通す。

| 作業 | 1件 |
|---|---|
| 複数リポジトリへの配布 | `ONLY=` で1リポジトリ |
| データの移行・変換 | 1レコード、1ファイル |
| 一括削除・一括更新 | 1つ消して結果を見る |
| 定期実行の仕組み | 手動で1回起動する |

dry run は書き込みの経路を通らない。dry run が通っても、push や PR 作成や
マージで落ちる。dry run は「対象の選び方」の確認であって、本番の保証ではない。

### 3. 動かして、出力をそのまま貼る

要約しない。「通りました」の代わりに、通った行を貼る。

```
誤り 0  注意 0
```

失敗したなら、失敗した行を貼る。成功した部分だけ並べて失敗を省かない。

### 4. 状態を言葉で区別する

| 言葉 | 意味 |
|---|---|
| 予約した | 自動マージなどを依頼した。結果はまだ見ていない |
| 入った | main にある、本番にある、のを自分の目で見た |
| 見ていない | 確認する手段があるが、まだ見ていない |
| 確かめられない | 権限や環境の都合で、このセッションからは見えない |

「予約した」を「入った」と書かない。
「見ていない」を省略しない。この一言があれば、相手は自分で見に行ける。

### 5. 期限つきの確認は、仕組みに入れる

「明日確認します」「土曜の定期実行で分かります」と言うなら、
見に行く仕組みをその場で入れる。`send_later`、Routine、または相手に頼む。

仕組みが入れられないなら「見に行く仕組みはないので、結果を見たら教えてください」と書く。
言っただけの確認は、確認されない。

### 6. コミットしたら中身を見る

```
git show --stat HEAD
```

意図したファイルだけが入っているか。余計なものが混ざっていないか。

## 報告のひな型

確認したことと、していないことを分けて書く。

```
確認したこと
- validate.sh: errors 0 / warns 0
- Python 1件で本番実行: PR #3 マージ済み

確認していないこと
- 残り21件は次の定期実行で入る。9/20 の結果はまだ見ていない
```

## 実際にあった取り違え

| 言ったこと | 実際 |
|---|---|
| dry run が通ったので本番も通ります | push と PR 作成で3回続けて失敗した |
| 自動マージを予約したので入ります | 予約と結果は別。dry run で差分なしを見るまで入ったとは言えない |
| 明日確認できます | 見に行く仕組みを入れなかった。2週間経った |
| ジョブが緑なので成功です | 失敗を数えていなかっただけ。21件入っていなかった |

## フックが最後に見るもの

`hooks/done_check.py`（Stop）が、止まる直前の返答を見る。

- 「直しました」「通りました」「マージしました」のような完了の言い方があるのに、根拠が無ければ差し戻す。
  根拠と数えるのは、URL、コミットのハッシュ、バッククォートの中身、コードブロック、ファイルの場所、PR 番号、`exit=` の行。
  「確かめていない」と書いてあれば通す。正直に書く方が、根拠の無い完了より良い
- ❔ が 1 ターンに 2 つ以上あれば差し戻す。質問を並べると、決める負担が人に移る
- 人の一言に指示が 2 つ以上あるのに、★ も ↩ も無く「やっていない」とも書いていなければ差し戻す。一部だけやって残りを黙って落とすのを防ぐ
- 予定の文（「〜します」で終わる ❕ や ★）は数だけ残す。途中で出た行は消せないので差し戻さない
- 返答ごとの行数、❔ の数、マーク以外の行数、根拠の無い完了の有無を `~/.claude/state/verify-before-done/metrics.jsonl` に残す。
  週の報告（skill-upkeep）が「会話の形から外れた数」として読む
- `DONE_CHECK_OFF=1` で止まる。登録は `repo-bootstrap/templates/settings.json` にあり、skill-sync が配る

## 他のスキルとの関係

姿勢全体は `work-style`。このスキルはその「完了前」を詳しくしたもの。
PR を作ってからの流れは `solo-pr-flow`、CI が落ちたときは `ci-triage`。
