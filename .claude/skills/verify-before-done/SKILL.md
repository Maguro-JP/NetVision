# 完了前の検証

「できた」と言えるのは、動かして、その出力を見せたときだけ。
書いただけ、通るはずと思っただけでは、まだできていない。

## 手順

### 1. 何を動かせば「できた」と言えるかを先に決める

変更に手を付ける前に、1行で書く。
「`validate.sh` が誤り 0 で終わる」「1リポジトリで PR がマージ済みになる」のように。
これが決まっていないと、あとで都合のいい確認を選んでしまう。

### 2. 本番の前に1件で試す

書き込みを伴う作業は、全件に当てる前に1件で通す。

| 作業 | 1件 |
|---|---|
| 複数リポジトリへの配布 | `ONLY=` で1リポジトリ |
| データの移行・変換 | 1レコード、1ファイル |
| 一括削除・一括更新 | 1つ消して結果を見る |
| 定期実行の仕組み | 手動で1回起動する |

dry run は書き込みの経路を通らない。dry run が通っても、push や PR 作成や
マージで落ちる。dry run は「対象の選び方」の確認であって、本番の保証ではない。

### 3. 動かして、出力をそのまま貼る

要約しない。「通りました」の代わりに、通った行を貼る。

```
誤り 0  注意 0
```

失敗したなら、失敗した行を貼る。成功した部分だけ並べて失敗を省かない。

### 4. 状態を言葉で区別する

| 言葉 | 意味 |
|---|---|
| 予約した | 自動マージなどを依頼した。結果はまだ見ていない |
| 入った | main にある、本番にある、のを自分の目で見た |
| 見ていない | 確認する手段があるが、まだ見ていない |
| 確かめられない | 権限や環境の都合で、このセッションからは見えない |

「予約した」を「入った」と書かない。
「見ていない」を省略しない。この一言があれば、相手は自分で見に行ける。

### 5. 期限つきの確認は、仕組みに入れる

「明日確認します」「土曜の定期実行で分かります」と言うなら、
見に行く仕組みをその場で入れる。`send_later`、Routine、または相手に頼む。

仕組みが入れられないなら「見に行く仕組みはないので、結果を見たら教えてください」と書く。
言っただけの確認は、確認されない。

### 6. コミットしたら中身を見る

```
git show --stat HEAD
```

意図したファイルだけが入っているか。余計なものが混ざっていないか。

## 報告のひな型

確認したことと、していないことを分けて書く。

```
確認したこと
- validate.sh: errors 0 / warns 0
- Python 1件で本番実行: PR #3 マージ済み

確認していないこと
- 残り21件は次の定期実行で入る。9/20 の結果はまだ見ていない
```

## 実際にあった取り違え

| 言ったこと | 実際 |
|---|---|
| dry run が通ったので本番も通ります | push と PR 作成で3回続けて失敗した |
| 自動マージを予約したので入ります | 予約と結果は別。dry run で差分なしを見るまで入ったとは言えない |
| 明日確認できます | 見に行く仕組みを入れなかった。2週間経った |
| ジョブが緑なので成功です | 失敗を数えていなかっただけ。21件入っていなかった |

## フックが最後に見るもの

`hooks/done_check.py`（Stop）が、止まる直前の返答を見る。

- 完了や確認の語を、このターンのツールの出力（tool_result）と呼んだツールの名前と照合する。自分の文に書いた URL やハッシュは、
  書けば通ってしまうので根拠にしない。語ごとに要る出力は次の表。無ければ差し戻す。
  「確かめていない」「やっていない」「見ていない」と書いてあれば通す。正直に書く方が、根拠の無い完了より良い
- ツールの出力に FAILED や誤りがあるのに「通った」と書いた返答は差し戻す（出力と逆のことを言わない）
- 撤回（「間違えていました」「できていませんでした」）は差し戻さず、数だけ残す。正直に言い直すのを止めない
- 上の表に無い一般の完了の語（完了、できました）は、文の中の URL・コミットのハッシュ・バッククォートの中身・コードブロック・
  ファイルの場所・PR 番号・`exit=` の行を根拠として受ける

| 書いた語 | 要る根拠（このターンのツールから） |
|---|---|
| 見ました・確認しました・読みました・調べました | ツールを 1 つ以上呼んでいる（Read・Grep・Bash・MCP など）。「〜と読みました」は読み取りの言い方なので除く |
| マージしました | 出力に `"merged": true`・`successfully merged`・`Merged pull request`・`Merge made by`・`Fast-forward` |
| push しました・配りました | 出力に `a..b  x -> y`・`[new branch]`・`push:`・`Everything up-to-date` |
| コミットしました | 出力に `files changed`・`insertions(`・`[branch hash]`・行頭のハッシュ |
| 通りました・テストが通・validate が通 | 出力に `OK`・`N passed`・`誤り 0`・`All checks passed`・`exit=0`・`検出なし`・`重大 0`・`success`。FAILED があって通った印が無ければ矛盾 |
| 直しました・作りました・足しました・書きました | 書き込むツール（Edit・Write・MultiEdit・NotebookEdit・Bash）を呼んでいる |

- ❔ が 1 ターンに 2 つ以上あれば差し戻す。質問を並べると、決める負担が人に移る
- 人の一言に指示が 2 つ以上あるのに、★ も ↩ も無く「やっていない」とも書いていなければ差し戻す。一部だけやって残りを黙って落とすのを防ぐ
- 予定の文（「〜します」で終わる ❕ や ★）は数だけ残す。途中で出た行は消せないので差し戻さない
- 返答ごとの行数・❔ の数・マーク以外の行数・根拠の無い完了の有無・呼んだツールの数・出力に根拠の無い語（unbacked）・
  矛盾（contradiction）・撤回（retraction）を `~/.claude/state/verify-before-done/metrics.jsonl` に残す。
  週の報告（skill-upkeep）が「会話の形から外れた数」として読む
- `DONE_CHECK_OFF=1` で止まる。登録は `repo-bootstrap/templates/settings.json` にあり、skill-sync が配る

## AI が作ったものには間違いがある（読み直し）

書いた直後の自分は、自分の書いたものを正しいと思っている。行番号で置き換えた sed が文を壊しても、表に書いた値が
ユーザーの意図と違っても、気づかずに「直した」と言う。だから、書いたら読み、動かし、推測は推測と書く。

1. 書いたら、最後の編集のあとに差分（`git diff -- <ファイル>`）かそのファイル（Read、`sed -n`）を読む。置換は文字列で指定し、
   行番号で置き換えない。置換後の行を出力して読む
2. コミットの前に差分を読む（`git diff --cached`）。`--stat` は読んだことにならない
3. ユーザーが言っていない値（模型の名前、数、手順、デフォルトの値）を自分で決めたら、返答に「私の推測」と書く。決める根拠
   （ユーザーの一言、決めたこと、動かした出力）が無ければ書かず、直したあとに ❔ で 1 行聞く
4. 指摘されたら、自分が間違っている前提で見直す（follow-instructions の 4）。「〜のはずです」で押し返さない
5. 自分の書いた決まり・表・スクリプトは、ユーザーが使う前に自分で 1 回使う。使わずに「できた」と言わない
6. 常に自分が間違っていると疑う。作業や完了の主張のある返答には、間違っているかもしれない所と確かめていないことを
   `❕ 疑い: <1 行>` で書く（例: `❕ 疑い: 表は読み直したが、配った先では動かしていない`）。疑いが無いと思ったときが一番危ない

`hooks/reread_check.py`（Stop）が、編集のあとに読み直しも実行も無い返答、Markdown を書いたのに文を読んでいない返答、
差分を読まずにコミットした返答、作業や完了の主張があるのに疑いの 1 行が無い返答を差し戻す。「読み直していない」と書いてあれば通す。数は `reread.jsonl` に残す。
`REREAD_CHECK_OFF=1` で止まる。テストは `scripts/test_reread_check.py`。

## 出す前の確認（precheck と pr_gate）

PR を作る前・マージの前・main に push する前の検査は、`scripts/precheck.py` で 1 本にまとめる。テストは、そのリポジトリの
`.claude/hooks/test.sh`（repo-bootstrap が置く台本）があればそれを流し、無ければ pytest を流す。
手で選んで動かすと抜けて、出したあとに間違いが分かる。precheck は、あるものだけを順に動かし、結果と HEAD を
`~/.claude/state/pr-gate/<repo>.json` に残す。`hooks/pr_gate.py`（PreToolUse）が、その記録と、出す内容を ❔ で見せたあとの
ユーザーの返事の無い PR の作成・マージ・main への push を止める。手順は `solo-pr-flow` の「出す前の確認」。
返事は、❔ を出した直後の一言だけを数える。別の話のあとでは、もう一度 ❔ を出す。
頼まれていない Release やタグの作成も止める。テストは `scripts/test_pr_gate.py`。`PR_GATE_OFF=1` で止まる。

## 他のスキルとの関係

姿勢全体は `work-style`。このスキルはその「完了前」を詳しくしたもの。
PR を作ってからの流れは `solo-pr-flow`、CI が落ちたときは `ci-triage`。
