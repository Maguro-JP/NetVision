# おかしいの合図と、原因の調べ方

おかしいと気づけるのは、先に予想を持っているときだけ。呼び出す前に「何が、いくつ、どのくらいで返るか」を 1 つ決める。
返った物が予想と違ったら、それが合図になる。

## 合図の表

| 合図 | 例 | 最初に見る所 |
|---|---|---|
| ユーザーの言葉と機械の判定が逆 | 進める意味の一言を、確認のフックが拒否として読んだ | フックが読み取った文と、当てた語。フックの側を疑う |
| 全部が同じ失敗 | 配った先の全部で、同じテストが落ちた | 1 件だけを開いて、共通の原因（配った物、前提）を見る。個別に直さない |
| 速すぎる成功 | 長いはずのテストが 0.1 秒で通った。0 件を検査して「問題なし」 | 動いた件数。対象が空ではないか |
| 数の桁が違う | 3 ファイルのはずの差分が 100 ファイル | 比べる相手（base のブランチ、merge-base） |
| 成功と言うのに状態が変わらない | push が通ったのに、リモートに無い。マージしたのに main に無い | 相手の側（GitHub の一覧、リモートの log） |
| 同じエラーの 2 回目 | 言い方を変えて同じ所に当たった | エラーの文を最後まで。直前に変えた所 |
| 自分の予想と違う出力 | 無いはずの行がある。あるはずのファイルが無い | 予想の前提（場所、ブランチ、版） |
| 通知が事実と逆 | Actions が通っているのに、フックが「動いている」と止めた | GitHub のチェックの一覧。通知の読み取り |

## おかしいと思ったら

1. `❕ おかしい: <何が>。予想は <A>、実際は <B>` を 1 行書く
2. 先に原因を調べる。回り込まない（別のやり方で同じ結果を取りに行かない）、慣れない（2 回目から流さない）、ユーザーに丸投げしない
3. 一次情報で事実を確かめる。GitHub の側、ファイルの中身、コマンドの出力。記憶と通知の読み取りは事実ではない
4. ツール（フック、スクリプト、テスト）の不具合なら直す。再現する入力をテストに足してから直す
5. 権限で直せないなら、直し方を 1 行で渡す（どのファイルの、どの判定を、どう変えるか）

## 原因の調べ方

出典: [obra/superpowers](https://github.com/obra/superpowers) の `systematic-debugging` と `root-cause-tracing.md`（MIT License, Copyright (c) 2025 Jesse Vincent）。要点だけを日本語で写した。

原因を掴む前に直さない。症状の出た所を直すのは、回り込みと同じ。

| 段 | すること |
|---|---|
| 1 読む | エラーの文を最後まで読む。行の番号、パス、終了コード。答えが書いてあることが多い |
| 2 再現する | 同じ手順で、もう 1 回起こす。起きないなら、足りない情報を集める。推測で進めない |
| 3 変えた所を見る | 直前の差分、足した依存、設定、環境の違い |
| 4 境目で確かめる | 部品がいくつも続くとき（通知 → 読み取り → 判定）は、境目ごとに入った物と出た物を出力し、どこで変わるかを見る |
| 5 さかのぼる | 悪い値がどこから来たかを、呼び出しの元へたどる。元で直す |
| 6 動いている物と比べる | 似ていて動く物を探し、違いを全部並べる。「関係ないはず」で外さない |
| 7 仮説は 1 つ | 「X が原因。なぜなら Y」と書き、いちばん小さい変更で試す。違ったら、足さずに戻して次の仮説 |

直しが 3 回続けて外れたら、やり方そのものがおかしい。4 回目を試す前に、前提（設計、置き場所、使うツール）を疑う。

## してはいけない回り込み

- 落ちたテストを飛ばす、検査を外す、`--no-verify` を付ける、待ち時間を足す
- エラーを握りつぶす（`|| true`、空の except）
- フックに止められて、同じ意味の別のコマンドで通す
- 予想と違う数を、そのまま報告に書いて先へ進む
