# 当たり前をやる・おかしいと思う・疑問は調べる・知識は古い

ユーザーの指摘は 5 つ。このスキルとフックで矯正する。

1. AI が当たり前のことをやってくれない
2. おかしいことをおかしいと思わない
3. 疑問を調べようとしない
4. 自分が優秀だと思っているのか、自分の認識だけで済ませて調べようとしない
5. 自分の知識は数年前の物だという認識がない

根は 1 つで、自分の認識を事実として扱っている。頼まれた言葉だけをやって目的を見ない。予想と違う出力を見ても、予想の方を捨てない。
分からない所を、もっともらしい文で埋める。学習の時点の世界を、今の世界だと思っている。
直し方も 1 つで、認識と事実を分け、事実は取りに行く。

## 4 本の柱

| 柱 | 場面 | すること | しないこと | 機械の見張り |
|---|---|---|---|---|
| A 当たり前をやる | 仕事を引き受けた直後、区切りごと | 目的に当たり前に含まれる手順を先に並べ、最後までやる | 途中で止める。答えをもらったことを聞き直す | `followup_gate.py`（Stop） |
| B おかしいと思う | 予想と違う結果、同じ失敗、フックに止められたとき | `❕ おかしい` を 1 行書き、先に原因を調べる | 回り込む。慣れる。ユーザーに丸投げする | `odd_nudge.py`（PostToolUse、PostToolUseFailure） |
| C 疑問は調べる | 「たぶん」「はず」「と思う」と書きたくなったとき | 手元、入っている版、公式の文書、検索の順に調べる | 推測の語で済ませる。自分の認識だけで書く | `guess_gate.py`（Stop） |
| D 知識は古い | 外の事実（API、フラグ、版、モデルの名前、値段、最新）を書く前 | 今日の日付を見て、一次情報で確かめ、確かめた版か日付を書く | 記憶で書く。学習の時点の最新を、今の最新と書く | `today.py`、`memory_nudge.py`（PostToolUse） |

## A 当たり前をやる

1. 着手の前に、頼まれた仕事の目的に当たり前に含まれる手順を並べる。表は `references/followups.md`
   （スキルを作ったら配る。PR を作ったら購読する。マージしたら配布と後片付けをする。直したら動かす。
   配るファイルを変えたら、配った先の clone で 1 回動かす。止められたら原因を調べる）
2. 並べた手順を、最後までやる。区切りで止まらない。次の手順に確認が要るなら、用意まで済ませてから ❔ を出す
3. 次の手順を残してターンを終えるときは、`❕ 次: <次の手順と、いま始めたこと>` を 1 行書く
4. ユーザーが 1 回答えたことを、同じ流れの中で聞き直さない。聞き直してよいのは、ツールの権限かフックに止められて、
   進めるのにユーザーの一言が要るときだけ。そのときは「何が止めたか・何と言えば通るか」を 1 行で書く

## B おかしいと思う

呼び出す前に、何が・いくつ・どのくらいで返るかを 1 つ予想する。予想が無ければ、おかしいと気づけない。

| 合図 | 例 |
|---|---|
| ユーザーの言葉と機械の判定が逆 | 進める意味の一言を、確認のフックが拒否として読んだ |
| 全部が同じ失敗 | 配った先の全部で、同じテストが落ちた |
| 速すぎる成功 | 0 件を検査して「問題なし」 |
| 数の桁が違う | 3 ファイルのはずの差分が 100 ファイル |
| 成功と言うのに状態が変わらない | マージしたのに main に無い |
| 同じエラーの 2 回目 | 言い方を変えて同じ所に当たった |
| 自分の予想と違う出力 | 無いはずの行がある |

1. `❕ おかしい: <何が>。予想は <A>、実際は <B>` を 1 行書く
2. 先に原因を調べる。回り込まない、慣れない、ユーザーに丸投げしない。調べ方は `references/signals.md`
3. 一次情報で事実を確かめる（GitHub の側、ファイルの中身、コマンドの出力）。記憶と、通知の読み取りは事実ではない
4. ツール（フック、スクリプト、テスト）の不具合なら直す。再現する入力をテストに足してから直す
5. 権限で直せないなら、直し方を 1 行で渡す（どのファイルの、どの判定を、どう変えるか）

## C 疑問は調べる

「たぶん」「おそらく」「はず」「と思います」「記憶では」は、調べていないときに出る語。書く前に調べる。

1. 調べる順は、手元のコードと出力、`--help` と入っている版、公式の文書（Context7）、WebSearch。表は `references/lookup.md`
2. 調べる前に `knowledge.py --find <語>` で前の知識を見る。調べたら research-to-tech の形（`docs/knowledge/tech/`）で残す
3. 分かったことは断定で書き、根拠（ファイルと行、コマンドの出力、文書の場所）を添える
4. `❕ 疑い` に残してよいのは、このセッションでは調べられなかったことだけ。
   `❕ 疑い: <何>は調べられない（理由）` の形で、理由を添える

## D 知識は古い

学習の知識は、数年前で止まっている前提で動く。セッションの始めにフックが今日の日付（日本時間）を出す。

1. 外の事実は、記憶で書かない。ライブラリの API、CLI のフラグ、サービスの仕様、版、モデルの名前、値段、「最新」
2. 書く前に一次情報で確かめる。入っている版（`--help`、`--version`、`pip show`、`npm view`、lockfile）、公式の文書、変更履歴
3. 確かめた版か日付を、書いた物の近くに書く（コメント、文書の出所、`docs/SOURCES.md`）
4. 記憶と一次情報が違ったら、記憶を捨てる。違いは知識に残す
5. 公開されているスキルやリポジトリの名前と中身は、開いて読んでから書く。「ある」と記憶で書かない

## 実際に起きた場面

| 場面 | 足りなかったこと | 柱 |
|---|---|---|
| スキルを main ブランチに入れたあと、配布を始めずに、同じ確認の ❔ を出し直した | マージの次は配布。用意まで進めてから 1 回だけ聞く | A |
| 確認のフックが、進める意味の一言の中の語を拒否として読んだ。気づいたのに、返事を求め続けた | 言葉と判定が逆なら、フックの読み取りを調べて直す道を出す | B |
| Actions が通っている PR のマージを、フックが止めた | 良い例。GitHub のチェックの一覧で事実を確かめ、通知の読み取りの不具合を直した | B |
| 配った先の全部で、同じテストが落ちた | 配るテストを、配った先で 1 回も動かしていなかった。全部が同じ失敗なら原因は配った物 | A、B |
| 差分は 3 ファイルのはずの PR が、100 ファイルで衝突していた | 作る前に、差分のファイルの数を見る。桁が違えば base を疑う | A、B |
| 公開されているスキルの名前と中身を、調べずに記憶で書きかけた | 開いて読んでから書く | C、D |

## フック

| 何 | いつ | すること | 止めるか |
|---|---|---|---|
| `hooks/today.py` | SessionStart、UserPromptSubmit（10 ターンに 1 回と、日付が変わったとき） | 今日の日付（日本時間）と「学習の知識は古い。外の事実は一次情報で確かめてから書く」を 1 行 | 止めない |
| `hooks/guess_gate.py` | Stop | 最後の返答の `❕ 疑い` の行の外に推測の語があり、このターンに調べる呼び出しが 1 回も無いとき | 止める。調べるか、`❕ 疑い: <何>は調べられない（理由）` で通る |
| `hooks/odd_nudge.py` | PostToolUse、PostToolUseFailure（Bash、MCP） | 1 回の出力に同じ失敗の行が 3 回以上、または同じ呼び出しが同じ失敗で 2 回目のとき、原因を先に調べるよう 1 行 | 止めない |
| `hooks/memory_nudge.py` | PostToolUse（Edit、Write、MultiEdit） | 書いた中身に外の物への新しい依存があり、直近 3 ターンに外の事実を見に行く呼び出しが無いとき、1 行。同じ依存には 1 回だけ | 止めない |
| `hooks/followup_gate.py` | Stop | このターンで PR のマージが成功したのに、配布の開始も `❕ 次:` の行も無く、❔ で終えるとき | 止める。始めるか、`❕ 次: …` で通る |

- `COMMON_SENSE_OFF=1` で 5 本とも止まる（ユーザーが自分の手で入れる）
- 止めるフックの文は 1 行。差し戻されたら、足りない 1 行だけを足す。`stop_hook_active` が真なら通す
- PostToolUse は成功したツールでしか動かない。失敗は PostToolUseFailure に来る。この登録が無いリポジトリでは、
  `odd_nudge.py` が次に成功した呼び出しのときに、会話の記録から失敗を拾う
- `odd_nudge.py` は、探した結果（`cd … && grep …`、`cat x | grep …`）、ソースコードのファイルの中身（`sed -n 1,80p x.py`）、
  数えた結果だけの行（`"うち失敗": 2`）を、失敗の行に数えない。実行の出力を grep で絞った形（`pytest | grep FAILED`）と、ログを読む形（`tail x.log`）は数える
- 推測の語は、コード・引用・言われたことのコピー（↩ の行）・`❕ おかしい` の行の中では見ない。人が予想や意見を聞いたターンも見ない
- テスト: `scripts/test_gates.py`、`scripts/test_nudges.py`

## 使わないとき

- 完了と言う前の検証と、疑いの 1 行の書き方（verify-before-done）
- 調べたことを 5 段で残す手順（research-to-tech）
- 落ちた Actions の原因の特定（ci-triage）、通知と ❔ の順番（actions-watch）
- 訂正の受け方（follow-instructions）、成果物を 1 つずつ完成させる（finish-first）

## 他のスキルとの関係

重なる決まりは、docs/GUIDELINES.md の 10 に、どちらに従うかを書いてある。

- verify-before-done の `❕ 疑い` は、確かめていないことを書く場所。このスキルは、そこに書いてよい物を「調べられなかったこと」に絞る
- research-to-tech は、調べたあとの残し方。このスキルは、調べる前（調べずに済ませない）を持つ
- token-efficiency の「成功したツールを信じる」は、ツールの成否の話。予想と違う中身を疑うのは、このスキル
- token-efficiency の `trajectory_guard.py` は、通った検査の再実行を見る。`odd_nudge.py` は失敗だけを見る

## 取り込んだ公開の物

出どころとライセンスは docs/SOURCES.md に書いてある。

- obra/superpowers の `systematic-debugging`（原因を掴む前に直さない、境目で確かめる、3 回外れたら前提を疑う）
