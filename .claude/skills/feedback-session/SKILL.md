# フィードバックのセッション

ユーザーの目は一番足りない資源。会話に置くのは成果物と1行だけにし、
フィードバックの中身は成果物と、リポジトリの記録に残す。

1つのセッションは1度に1つしか進まず、文脈は100万トークンで頭打ちになる。
トピックごとにセッションを分ければ、それぞれの文脈は小さいまま、同時に進む。擬似的な複数人開発。

## このセッションで使うとき

`feedback-session` と言われたら、そのセッション自身をフィードバック専用に切り替える。
新しいセッションでも、途中まで作業したセッションでも同じ。外から指示を送り直す必要はない。

1. トピックを1つに決める。引数があればそれ。なければセッションのタイトルとこれまでの作業から絞る
2. 成果物の形と判定を決める。これまでに出していたもの（絵、PR）をそのまま成果物の形にする。判定が決められなければ、最初の成果物を見せたときに `❔` で1行聞く
3. ブランチは今のものを使い続ける。他のセッションと同じブランチに push していたら、自分の分を `claude/FB-<トピックの英小文字>-<YYYYMMDD>`（work-style「名前の付け方」）に移す
4. 記録の場所を決める。そのリポジトリの記録の決まりに従う。なければ `docs/knowledge/feedback/<トピック>.md`
5. マーカーを置く。`.claude/feedback-session` にトピックを1行書き、`.git/info/exclude` に `.claude/feedback-session` を足す（コミットしない）。マーカーのあるセッションでは Stop フック `scripts/gate.sh` が、返答の中の文が ★ ↩ ❕ ❔ で始まる3行以内でなければ差し戻す。指示だけでは了解の返事や経過が混ざり続けたので、最後に機械で見る。フックは起動時に読まれるので、途中からマーカーを置いたセッションでは次に開き直したときから効く
6. 返事は `❕ <トピック>: <成果物の形>。判定は <1行>` の1行だけ。そのまま次の成果物に取りかかる

切り替えたあとに変わること。

| 前 | 後 |
|---|---|
| 経過を書く | 書かない。コミットと記録に残す |
| チェックの結果を並べる | 通ったものだけ見せる。落ちた数と崩れの種類は記録へ |
| 「了解しました」と返す | 返さない。次の成果物で答える |
| 次の予定を書く | 書かない |
| 成果物がないまま返答を終える | 成果物がない回は `❕ <トピック>: 落ちた N 件（<種類>）` の1行だけ |
| 待つために `sleep` や `loop` を回す | 返答を終える。続きは返事が来たとき |

人が開いたセッションは人のもの。片付け（アーカイブ）の対象にしない。

## 1回の流れ

1. 作る
2. 裏でチェックする。自分の検査、測定、チェック担当（subagent）。落ちたものは見せない
3. 通ったものを見せる。画像なら `SendUserFile`、コードなら PR の URL。本文は `★` の1行
4. 記録に1行足す。何を変えたら、どうなったか。落ちた数と崩れの種類もここ
5. 返答を終える

ユーザーから1行返ってきたら、了解の返事は書かず、裏で処理して次の成果物で答える。
人の判定が最終。チェック担当が落としたものでも人が通すと言えば通し、検査の数値や決まりを人の判断に合わせて直す。
人が落としたものは通さない。人の1行を判断待ちに回さない。
次の `★` と一緒に `↩ <トピック>: <言われたこと>を受けて、<変えたこと>。<結果>。` を1行付ける。
記録にも同じ形で書く。発言の引用は写さない（記録の決まり: 何を決めたかを書き、やり取りは書かない）。

文脈を小さく保つ（auto-dev と同じ）。テストや描画の出力はファイルへ落として失敗の行だけ読む。
ファイルは要る範囲だけ読む。広い調べものはサブエージェントに任せて結論だけ受け取る。
覚えておくことは会話ではなく記録に書く。
ツールの使い方の決まりは `token-efficiency` の 3 と 4。

## ブランチと PR

- トピックの完成条件は `docs/reports/deliverables.md` に1行持つ（finish-first）。無ければ最初の回で仮に書き、`❔` で1行確かめる。
  完成条件が無いまま回数だけ重ねると、いつまでも「進行中」になる
- push するのは自分のブランチだけ。他のトピックのブランチ、auto-dev の `claude/DEV-` のブランチには触らない
- 成果物ごとにコミットして push する
- ★ を出した回と、記録（docs/knowledge/ など）を書いた回は、その回のうちに main を取り込み、手元の検証を通して PR にし、`solo-pr-flow` でマージする。溜めない。本開発（auto-dev）は main からしか受け取れないので、main に入らない発見はないのと同じ
- 複数のトピックが同じファイルを直すときは、先に main に入れた方が勝ち。あとの方が取り込んで直す。重なると分かっているトピックは、並列にせず順に回す

## 終わり

文脈が大きくなったときも区切る。`get_session`（引数なし）の `context_usage.used_tokens` が 70 万を超えたら、
その回で記録と PR を済ませ、新しいセッションに引き継ぐ。1セッションの上限は 100 万で、近づくほど判断が鈍る。
引き継ぎは、トピック・成果物の形・判定・ブランチ・記録の場所・直近3回の結果を `docs/knowledge/feedback/<トピック>.md` の
末尾に「引き継ぎ」として書き、親セッションがあれば「セッション間の連絡」の形で `❕ <トピック>: 文脈 N 万。新しいセッションで続ける`
を送る。人が開いたセッションなら `❔ <トピック>: 文脈が N 万トークンになった。新しいセッションに移ってよいか` を1行で聞き、
返事が来るまでは続ける。自分で新しいセッションを立ててよいのは、親セッションから立てられたセッションだけ。

判定が通った、または3回続けて判定が上がらない（諦める条件）ときに終わる。
PR をマージし、親セッションがいれば下の「セッション間の連絡」の形で `★ <トピック> PR #N <1行>` を送り、
返答を終える。自分では自分を片付けない。

## 会話に出すもの

行は4種類だけ。先頭のマークで見分ける（マークはユーザーが決めたもの。変えない）。

| マーク | 何 | 形 |
|---|---|---|
| ★ | 成果物 | 成果物（画像か PR の URL）と `★ <トピック> N回目: <何を変えてどうなったか1行>` |
| ↩ | 言われたことへの返事 | `↩ <トピック>: <言われたこと>を受けて、<変えたこと>。<結果>。` 次の ★ と一緒に出す |
| ❕ | 1行報告 | `❕ <トピック>: <成果物の形>。判定は <1行>`（切り替え）、`❕ <トピック>: 落ちた N 件（<種類>）`（成果物がない回）、`❕ <トピック> ×N 開始`（親セッション） |
| ❔ | 質問 | `❔ <トピック>: <1行>` |

これ以外は出さない。了解・承知の返事、経過、チェックのログ、謝罪、「次は〜します」は書かない。
指示を受けた回も了解を書かず、次の成果物で返す。ツールを呼ぶ間に文を書かない。途中の文も会話に出る。
本文は返答の最後の1行だけ。経過はコミットと記録にある。

## 親が取りまとめる並列開発

独立した作業が 2 つ以上あり、それぞれ 10 手以上なら、人に「並列で」と言われるのを待たずに子のセッションに分ける。
1 本で順に進めると、その間ユーザーの一言も届かず、開発が遅いままになる。親は分けて、見て、取りまとめる。

1. 計画を出す。`scripts/fanout.py plan` に作業の列を渡すと、触る場所の重ならない束、題、tag、難易度、モデル、触ってよい場所と触らない場所、プロンプトの全文が出る

```
python3 .claude/skills/feedback-session/scripts/fanout.py plan \
  --task "<題> | <触る場所>,<触る場所> | <手数> | <説明>" --task "..." \
  --parent-model <自分の session_context.model> --permission-mode <自分の permission_mode> \
  --keep <親が持つ場所> --json <scratchpad>/plan.json --md <scratchpad>/plan.md
```

   作業の列を書かずに `--from-reports` を付けると、`docs/reports/deliverables.md` の未完成と `pending.md` の答えが付いた項目から作る。
   「❕ 並列: 分けない（理由）」が出たら分けない（作業が 1 つ、どれも 10 手に満たない、場所が重なる）。その 1 行を会話に出して自分で進める
   ユーザーがセッションを増やさないと言ったとき（会話かルーティンのプロンプトに「セッションを増やさない」「子のセッションを立てない」がある）は、計画を出さずに自分で進める。
   子に出すのは区切りのある作業だけで、long-dev そのものとルーティンは子に渡さない（紐づけ先はユーザーが使っているセッション。scheduler の「紐づけ先」）
2. 設定を取る。`get_session`（session_id 無し）で自分の `session_context.model` と `permission_mode` を取る。権限はそのまま渡す。
   モデルは引き継がず、束の難易度で選ぶ（下の表。計画が束ごとに出す）。effort は `create_session` に渡さない（渡すのはユーザーが言ったときだけ）。作ったら
   `❕ <題> を作った（モデルは <ID>、難易度 <難易度>。effort は既定）` と 1 行出す
3. 立てる。束ごとに、計画の JSON の `create_session` の欄をそのまま `create_session` に渡す（`title`、`source_url`、`source_revision` と `outcome_branch` は親のブランチ、`model`、`permission_mode`、`tags`、`prompt`）。
   立てたら `fanout.py record --repo <owner>/<repo> --session-id <id> --title "<題>" --model <ID>` で覚える（置き場はリポジトリの外。public なので ID を書かない）
4. 子は親のブランチに rebase して push する。自分のブランチも PR も作らない（リモートのブランチは消せず、基盤が付ける draft の PR の印も外せないので、残る物を増やさない）。
   区切りごとに push し、Agent を使わず、cd せず、ユーザーに質問しない。この決まりは計画のプロンプトに入っている。手で書き直すときも削らない
5. 見る。立てて 3〜5 分で 1 回、`get_session` で子を取り、結果を JSON に写して `fanout.py status --repo <owner>/<repo> --input <JSON>` に渡す。子からは親に連絡できないので、親が見る。
   見に行く予約は新しく重ねず、1 本を `update_trigger`（`run_once_at` と `prompt`）で入れ直して使い回す（実行済みの予約は消せない）。待つ間、親は自分の束を進める
6. 取りまとめる。表の「次の処置」に従う

| 状態 | 見分け方 | 処置 |
|---|---|---|
| 終わった | 子のターンが終わっている（最後の報告は `post_turn_summary`） | 親のブランチを fetch して子のコミットと差分を読み、検査を通す。取り込んだその回に `archive_session` し、`fanout.py record --archived` で外す |
| 動いている | 費用かトークンか作業の要約が動いている | 待つ |
| 止まった | 落ちた、確認待ち、一定の時間（既定 10 分）費用もトークンも動いていない | `archive_session` して親が引き取る。push 済みのコミットは使い、残りは親が進める。催促で起こさない（同じ所でまた止まる） |

7. 全部の束が入ったら、親が precheck を通し、PR は 1 本にまとめる（PR の前の ❔ は親が出す。子は出さない）

### 難易度とモデル

指示の難易度でモデルを選ぶ。判定の語、規模の決まり、モデルの ID は `references/models.md` にあり、`fanout.py` がそこを読む（ID はそこだけに書く）。

| 難易度 | どんな作業 | create_session の model | Agent の model |
|---|---|---|---|
| 難しい | 設計、原因の分からない不具合、フックやゲートの判定、複数のスキルにまたがる変更 | 親と同じ | 省く（親と同じ） |
| 普通 | 決まった手順の実装、テストの追加、文書の書き直し | 普通のモデル | `sonnet` |
| 易しい | 一覧の更新、置換、配布、確認、要約、検索 | 易しいモデル | `haiku` |

難易度が分からないときは普通にする。Agent ツールで裏に出すときも同じ表で `model` を選ぶ。
ユーザーがモデルを名指ししたときは、表よりそちらに従う。

### 合図（フック）

| 何 | すること |
|---|---|
| `hooks/fanout_nudge.py` | UserPromptSubmit。独立した指示が 2 つ以上あるか、「並列」「同時に」「それぞれ」「全部のリポジトリ」などの語があるとき、計画を促す 1 行を差し込む。同じセッションでは 15 分に 1 回。`FANOUT_NUDGE_MIN=N` で間隔を変える |
| `hooks/fanout_gate.py` | Stop。このターンのツール呼び出しが 40 回を超え、指示が 3 個以上あり、Agent も create_session も使っていないとき、残りを分けるか「❕ 並列: 分けない（理由）」を 1 行書くよう求める。`FANOUT_GATE_CALLS`、`FANOUT_GATE_ITEMS` でしきい値を変える |
| `background-first/hooks/background_first.py` | PreToolUse。ツール呼び出しが 24 回からは、独立した残りを子のセッションに分けるよう知らせる |

どれも `FANOUT_OFF=1` で止まる（background_first.py は `BACKGROUND_FIRST_OFF=1`）。子のセッション（プロンプトに「セッションやルーティンを作らない」がある）には出さない。
fanout_nudge.py と fanout_gate.py は、ユーザーがセッションを増やさないと言った会話と、順にやる決まりのルーティン（long-dev の 報告・まとめ・開発）にも出さない。あとの発言で「並列で」と言い直されたら、新しい方に従う。

## 親セッション（並列で立てるとき）

ユーザーがトピックを並べて「並列で」と言ったとき。そのセッションが親セッションになる。
トピックごとに判定を回し続ける形（1 トピック 1 ブランチ）で、上の「親が取りまとめる並列開発」（1 回の作業を束に分け、親のブランチに集める形）とは別。モデルの選び方は同じ表を使う。

1. トピックを切る。触るファイルが重ならないように。重なるものは1つにまとめるか順にする
2. 数を決める。レート制限は全セッションで共有。デフォルトは3つまで。`rate_limit_info.status` が `allowed` 以外なら増やさない。セッションを1つ立てるだけで文脈に10万トークン前後が乗るので、小さいトピックで分けない
3. トピックごとにセッションを立てる

```
create_session(
  title="FB <repo> <トピック>",
  source_url="https://github.com/<owner>/<repo>",
  model=<トピックの難易度で選ぶ（「難易度とモデル」の表）>,
  permission_mode=<元のセッションの permission_mode>,
  tags=["feedback-session:auto", "ciel:<親の skill>:<トピック>"],
  prompt=<下の定型>)
```

AI が作るセッションは、権限とエフォートを元のセッション（作る側）から引き継ぎ、モデルは指示の難易度で選ぶ。先に `get_session`（session_id 無し）で自分の
`session_context.model`、`permission_mode`、`effort_level` を取る。

| 設定 | 値 | 理由 |
|---|---|---|
| model | 指示の難易度で選ぶ（「難易度とモデル」の表。難しいは元のセッションの `session_context.model`、普通と易しいは `references/models.md` の ID） | 難しい作業を下のモデルに出すと間違え、易しい作業を上のモデルに出すと遅くて高い |
| permission_mode | 元のセッションの `permission_mode` をそのまま（親より緩くは作れない） | `plan` は人の承認で止まる。自律のセッションには使わない |
| effort | 元のセッションの `effort_level` を引き継ぎたいが、`create_session` に渡す欄が無く、作られた側は low になる。作ったら `❕ <題> を作った（effort は low。元は <値>。上げるならユーザーが切り替える）` と 1 行出す | ツールに欄が無い。黙っていると low のまま回る |
| tags | `feedback-session:auto` と `ciel:<親の skill>:<トピック>` | 消すときに、自分で立てたものを見分ける |
| title | work-style「名前の付け方」の形 | 一覧で見分ける |

```
<owner>/<repo> の feedback-session <トピック>。成果物: <形1行>。判定: <1行>。
.claude/skills/feedback-session/SKILL.md に従う。ブランチは claude/FB-<トピック>-<YYYYMMDD>（日付は JST。TZ=Asia/Tokyo date +%Y%m%d）。PR のタイトルは「FB <トピック>: <1行>」。
終わったら親セッション（session_id <親セッションの id>）に「セッション間の連絡」の形で ★ <トピック> PR #N <1行> を送る。
```

4. 立てたら `❕ <トピック> ×N 開始` の1行を出して返答を終える。見に行かない
5. 連絡が届いたら、その1行をそのまま出す。PR がマージ済みで、そのセッションが IDLE なら `archive_session` で片付ける
6. 実行されたあとの1回きりの Routine は `tidy` で消す
7. 連絡が来ないまま終わっているものは、週 1 回（skill-upkeep）に `tidy`「終わったセッション」の手順で消す。立てたまま残さない

片付けてよいのは自分で立てたもの（`parent_session_id` が自分、tag `feedback-session:auto`）だけ。
人が開いたセッションと、人が「残して」と言って `feedback-session:keep` を付けたものは片付けない
（付けるのは `set_session_tags`）。

## セッション間の連絡

相手のセッションに紐づけた1回きりの Routine で送る。相手が空いたときに本文が届く
（作業中なら終わるまで待たされる。21分待った例がある）。

```
create_trigger(name="feedback-session 連絡 → <相手のトピック>", prompt="<本文1行>",
               run_once_at=<2分後の UTC>, persistent_session_id="<相手の session_id>",
               initiation="own_followup")
```

トピックのセッションから親セッションの id を知るには、引数なしの `get_session` の `parent_session_id` を見る。

`fire_trigger` で相手の Routine を起動する形は使わない。2026-10-17 に試して、子から親へは届かず、
自分宛てでは本文（text）が落ちた。届かないときは `get_session` で相手の `post_turn_summary` を見る。

## やらないこと

- 人が開いたセッション、`feedback-session:keep` の付いたセッションを片付けること
- 他のセッションのブランチに push すること
- チェックを飛ばして見せること。落ちたものを「参考に」と出すこと
- 待つために `sleep` や `loop` を回すこと。返答を終えて、起動されるのを待つ
- ユーザーの言葉を記録に写すこと。変えたことと結果を書く
- 「親が取りまとめる並列開発」の子に、PR を作らせること・質問させること・自分のブランチを作らせること
- 小さい作業（10 手に満たない）や、触る場所の重なる作業を分けること。立てる費用とぶつかった rebase の方が高い
- トピックのセッション（1 トピック 1 ブランチの形）のブランチを、親セッションや別のセッションがまとめて main に入れること。入れる時期はそのトピックのセッションが区切りで決める。外から統合すると、並列に分けた意味が消え、各セッションが取り込み直す手間だけが残る

## 他のスキルとの関係

- 1セッションで順に進める: `auto-dev`。毎朝起動する: `long-dev`（Routine の 3 で auto-dev の代わりに feedback-session と書けば、毎朝親セッションから回る）
- トピックが「できないことを身につける」なら、そのセッションの中で `self-learn` のサイクルを回す
- セッションを作って Routine を紐づける手順: `scheduler`
- PR のマージ: `solo-pr-flow`。片付け: `tidy`。全体を見る: `patrol`
