# フィードバックのセッション

利用者の目は一番足りない資源。会話に置くのは成果物と1行だけにし、
フィードバックの中身は成果物と、リポジトリの記録に残す。

1つのセッションは1度に1つしか進まず、文脈は100万トークンで頭打ちになる。
題目ごとにセッションを分ければ、それぞれの文脈は小さいまま、同時に進む。擬似的な複数人開発。

## このセッションで使うとき

`feedback-session` と言われたら、そのセッション自身をフィードバック専用に切り替える。
新しいセッションでも、途中まで作業したセッションでも同じ。外から指示を送り直す必要はない。

1. 題目を1つに決める。引数があればそれ。無ければセッションの題名とこれまでの作業から絞る
2. 成果物の形と判定を決める。これまでに出していたもの（絵、PR）をそのまま成果物の形にする。判定が決められなければ、最初の成果物を見せたときに `❔` で1行聞く
3. 枝は今のものを使い続ける。他のセッションと同じ枝に push していたら、自分の分を `claude/FB-<題目の英小文字>-<YYYYMMDD>`（work-style「名前の付け方」） に移す
4. 記録の場所を決める。そのリポジトリの記録の決まりに従う。無ければ `docs/knowledge/feedback/<題目>.md`
5. 目印を置く。`.claude/feedback-session` に題目を1行書き、`.git/info/exclude` に `.claude/feedback-session` を足す（コミットしない）。目印のあるセッションでは Stop フック `scripts/gate.sh` が、返答の中の文が ★ ↩ ❕ ❔ で始まる3行以内でなければ差し戻す。指示だけでは了解の返事や経過が混ざり続けたので、最後に機械で見る。フックは起動時に読まれるので、途中から目印を置いたセッションでは次に開き直したときから効く
6. 返事は `❕ <題目>: <成果物の形>。判定は <1行>` の1行だけ。そのまま次の成果物に取りかかる

切り替えたあとに変わること。

| 前 | 後 |
|---|---|
| 経過を書く | 書かない。コミットと記録に残す |
| 検品の結果を並べる | 通ったものだけ見せる。落ちた数と崩れの種類は記録へ |
| 「了解しました」と返す | 返さない。次の成果物で答える |
| 次の予定を書く | 書かない |
| 成果物が無いまま返答を終える | 成果物が無い回は `❕ <題目>: 落ちた N 件（<種類>）` の1行だけ |
| 待つために `sleep` や `loop` を回す | 返答を終える。続きは返事が来たとき |

人が開いたセッションは人のもの。片付け（アーカイブ）の対象にしない。

## 1回の流れ

1. 作る
2. 裏で検品する。自分の検査、測定、検品担当（subagent）。落ちたものは見せない
3. 通ったものを見せる。画像なら `SendUserFile`、コードなら PR の URL。本文は `★` の1行
4. 記録に1行足す。何を変えたら、どうなったか。落ちた数と崩れの種類もここ
5. 返答を終える

利用者から1行返ってきたら、了解の返事は書かず、裏で処理して次の成果物で答える。
人の判定が最終。検品担当が落としたものでも人が通すと言えば通し、検査の数値や決まりを人の判断に合わせて直す。
人が落としたものは通さない。人の1行を判断待ちに回さない。
次の `★` と一緒に `↩ <題目>: <言われたこと → 変えたこと → 結果>` を1行付ける。
記録にも同じ形で書く。発言の引用は写さない（記録の決まり: 何を決めたかを書き、やり取りは書かない）。

文脈を小さく保つ（auto-dev と同じ）。試験や描画の出力はファイルへ落として失敗の行だけ読む。
ファイルは要る範囲だけ読む。広い調べものはサブエージェントに任せて結論だけ受け取る。
覚えておくことは会話ではなく記録に書く。

## 枝と PR

- push するのは自分の枝だけ。他の題目の枝、auto-dev の `claude/DEV-` の枝には触らない
- 成果物ごとにコミットして push する
- ★ を出した回と、記録（docs/knowledge/ など）を書いた回は、その回のうちに main を取り込み、手元の検証を通して PR にし、`solo-pr-flow` でマージする。溜めない。本開発（auto-dev）は main からしか受け取れないので、main に入らない発見は無いのと同じ
- 複数の題目が同じファイルを直すときは、先に main に入れた方が勝ち。あとの方が取り込んで直す。重なると分かっている題目は、並列にせず順に回す

## 終わり

判定が通った、または3回続けて判定が上がらない（諦める条件）ときに終わる。
PR をマージし、束ねる側がいれば下の「セッション間の連絡」の形で `★ <題目> PR #N <1行>` を送り、
返答を終える。自分では自分を片付けない。

## 会話に出すもの

行は4種類だけ。先頭の印で見分ける（印は利用者が決めたもの。変えない）。

| 印 | 何 | 形 |
|---|---|---|
| ★ | 成果物 | 成果物（画像か PR の URL）と `★ <題目> 回N: <何を変えてどうなったか1行>` |
| ↩ | 言われたことへの返事 | `↩ <題目>: <言われたこと → 変えたこと → 結果>`。次の ★ と一緒に出す |
| ❕ | 1行報告 | `❕ <題目>: <成果物の形>。判定は <1行>`（切り替え）、`❕ <題目>: 落ちた N 件（<種類>）`（成果物が無い回）、`❕ <題目> ×N 開始`（束ねる側） |
| ❔ | 質問 | `❔ <題目>: <1行>` |

これ以外は出さない。了解・承知の返事、経過、検品のログ、謝罪、「次は〜します」は書かない。
指示を受けた回も了解を書かず、次の成果物で返す。ツールを呼ぶ間に文を書かない。途中の文も会話に出る。
本文は返答の最後の1行だけ。経過はコミットと記録にある。

## 束ねる側（並列で立てるとき）

利用者が題目を並べて「並列で」と言ったとき。そのセッションが束ねる側になる。

1. 題目を切る。触るファイルが重ならないように。重なるものは1つにまとめるか順にする
2. 数を決める。利用枠は全セッションで共有。既定は3つまで。`rate_limit_info.status` が `allowed` 以外なら増やさない。セッションを1つ立てるだけで文脈に10万トークン前後が乗るので、小さい題目で分けない
3. 題目ごとにセッションを立てる

```
create_session(
  title="FB <repo> <題目>",
  source_url="https://github.com/<owner>/<repo>",
  permission_mode="auto",
  tags=["feedback-session:auto"],
  prompt=<下の定型>)
```

```
<owner>/<repo> の feedback-session <題目>。成果物: <形1行>。判定: <1行>。
.claude/skills/feedback-session/SKILL.md に従う。枝は claude/FB-<題目>-<YYYYMMDD>。PR の題は「FB <題目>: <1行>」。
終わったら束ねる側（session_id <束ねる側の id>）に「セッション間の連絡」の形で ★ <題目> PR #N <1行> を送る。
```

4. 立てたら `❕ <題目> ×N 開始` の1行を出して返答を終える。見に行かない
5. 連絡が届いたら、その1行をそのまま出す。PR がマージ済みで、そのセッションが IDLE なら `archive_session` で片付ける
6. 起きたあとの一回きりの Routine は `tidy` で消す

片付けてよいのは自分で立てたもの（`parent_session_id` が自分、tag `feedback-session:auto`）だけ。
人が開いたセッションと、人が「残して」と言って `feedback-session:keep` を付けたものは片付けない
（付けるのは `set_session_tags`）。

## セッション間の連絡

相手のセッションに結びつけた一回きりの Routine で送る。相手が空いたときに本文が届く
（作業中なら終わるまで待たされる。21分待った例がある）。

```
create_trigger(name="feedback-session 連絡 → <相手の題目>", prompt="<本文1行>",
               run_once_at=<2分後の UTC>, persistent_session_id="<相手の session_id>",
               initiation="own_followup")
```

題目のセッションから束ねる側の id を知るには、引数なしの `get_session` の `parent_session_id` を見る。

`fire_trigger` で相手の Routine を起こす形は使わない。2026-10-17 に試して、子から親へは届かず、
自分宛てでは本文（text）が落ちた。届かないときは `get_session` で相手の `post_turn_summary` を見る。

## やらないこと

- 人が開いたセッション、`feedback-session:keep` の付いたセッションを片付けること
- 他のセッションの枝に push すること
- 検品を飛ばして見せること。落ちたものを「参考に」と出すこと
- 待つために `sleep` や `loop` を回すこと。返答を終えて、起こされるのを待つ
- 利用者の言葉を記録に写すこと。変えたことと結果を書く
- 題目のセッションの枝を、束ねる側や別のセッションがまとめて main に入れること。入れる時期はその題目のセッションが区切りで決める。外から統合すると、並列に分けた意味が消え、各セッションが取り込み直す手間だけが残る

## 他のスキルとの関係

- 1セッションで順に進める: `auto-dev`。毎朝起こす: `long-dev`（Routine の 3 で auto-dev の代わりに feedback-session と書けば、毎朝束ねる側から回る）
- 題目が「できないことを身につける」なら、そのセッションの中で `self-learn` の周を回す
- セッションを作って Routine を結びつける手順: `scheduler`
- PR のマージ: `solo-pr-flow`。片付け: `tidy`。全体を見る: `patrol`
