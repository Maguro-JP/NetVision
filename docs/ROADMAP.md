# NetVision ロードマップ

目的は「ネットワークの構成・保守・バージョンを1か所で把握できる状態」を作ることです。
価値が早く出る順に段階を切っています。

## フェーズ1: インベントリ + 保守期限管理 ✅ 実装済み

- 機器 / 拠点 / 保守契約のデータモデルと CRUD API
- 保守期限・EoS・EoL の残日数計算と重要度判定
- ダッシュボード、機器一覧（検索・絞り込み）、機器詳細
- 単体でも Excel 台帳を置き換えられる状態

## フェーズ1.5: 既存台帳の取り込みと書き出し ✅ 実装済み

ゼロから導入する現場はまず無いので、移行導線を先に整備した。

- Excel(.xlsx) / CSV(Shift_JIS・UTF-8) / TSV の読み込み
- 列名の自動対応付け（別名辞書 + 表記揺れの正規化）と、画面での手動上書き
- 取り込み前プレビュー（行ごとに 新規/更新/スキップ/エラー と理由を表示）
- エラーが1行でもあれば全体を反映しない all-or-nothing
- 再取り込みでの更新は「値が入っている列だけ」反映（空欄で既存値を消さない）
- 拠点の自動作成、保守契約の自動作成と重複防止
- Excel / CSV(UTF-8・Shift_JIS) への書き出し。一覧の絞り込みをそのまま引き継ぐ
- **書き出し ⇄ 取り込みの往復**：出力の列見出しを取り込み側の項目名と一致させ、
  「書き出し → Excel で一括編集 → 取り込み」が回るようにした（往復の不変性はテストで担保）

- エラー行だけを元の列のまま書き出し、Excel で直して再取り込みできる導線

### 今後の拡張候補
- 保存済みマッピングのプロファイル化（毎月同じ台帳を取り込むケース向け）
- 取り込み単位でのロールバック（履歴のバッチIDを使えば実装できる）

## フェーズ1.7: 変更履歴・最適化の指摘・将来構成シナリオ ✅ 実装済み

### 変更履歴
- 機器 / 保守契約 / 拠点への変更を、項目単位で「変更前 → 変更後」として自動記録
- SQLAlchemy のフラッシュに介入し、1か所で全ての変更を捕捉（APIごとの記録漏れを構造的に防ぐ）
- 発生元（画面操作 / 取り込み / デモデータ）とバッチIDで追跡できる
- 対象が削除された後も、何を削除したかが読める

### 最適化の指摘
- 外部データを使わず、台帳だけで判定できる「無駄」と「リスク」を洗い出す
- 撤去済み機器の保守契約、予備機の過剰保守、契約の重複、EoL 超過での稼働、保守なし稼働など
- 削減できる年額の見込みを添える（稟議で使えるのは結局そこなので）

### 将来構成シナリオ
- 実際の台帳に触れずに「入れ替えたらどうなるか」を試算する
- 期限が近い機器から入れ替え案のたたき台を自動生成
- 現状と適用後を同じ指標で比較し、初期投資と年間保守費の増減を出す
- 評価時点を将来に置いた試算ができる

### 今後の拡張候補
- 承認されたシナリオを台帳へ反映する導線（適用時に変更履歴へ一括記録）
- シナリオ同士の比較（案A / 案B の並列評価）
- 年度別の予算割当と、複数年にまたがる更改ロードマップ
- 指摘のしきい値（更改年数など）を設定で変更できるようにする

## フェーズ2: Config 取り込みとパース ✅ 実装済み

- Config / show 出力のアップロード（複数ファイル同時）
- ベンダー自動判別と、ベンダー別パーサ（Cisco IOS/IOS-XE/NX-OS、Junos、FortiOS）
  - 外部ライブラリに依存せず自前実装。`app/services/configparse/` にベンダーごとに分離
  - running-config だけでなく `show version` `show cdp neighbors detail` なども1ファイルで読める
- 抽出: ホスト名 / 型番 / シリアル / OSバージョン、インターフェース、VLAN、LLDP・CDP ネイバー
- 原文を世代ごとに保存し、世代間差分を表示（変更追跡・監査証跡）
  - 同一内容の再取り込みでは世代を増やさない（sha256 判定）

### 設計メモ（実装した方針）
Config パース結果は「観測値」、台帳は「台帳値」として分けて保持している。
**自動で上書きせず、差分を提示して人が承認する**方式。
さらに `version 15.2` のように観測値の方が粗いだけの場合は差分として扱わない
（適用したときに台帳の `15.2(7)E6` を劣化させないため）。

### 今後の拡張候補
- SSH / SCP / TFTP による自動収集と定期実行
- ルーティング設定・ACL の抽出
- Config のコンプライアンスチェック（禁止設定の検出）

## フェーズ3: トポロジ可視化エディタ ✅ 実装済み

- LLDP / CDP から結線を自動推定し、図として描画（React Flow）
  - インターフェース名・ホスト名の表記ゆれを正規化して突き合わせる
  - 両側から確認できた結線は「確認済み」として区別（実線 / 点線）
  - 台帳に無い隣接先は記載漏れの可能性として報告
- 種別を段にした自動レイアウトを初期配置として与える
- 人がドラッグして配置を整え、**配置は永続化**（機器追加時も既存配置を壊さない）
- 手で線を引ける。自動再推定しても手動の線は消えない
- レイヤごとに独立した配置（物理 / L2 / L3 / 論理）
- ノードの色は保守期限・EoL のアラート状態と連動

### 今後の拡張候補
- 図の PNG / SVG エクスポート（設計書への貼り付け用）
- VLAN / セグメント単位でのフィルタ表示（L2・L3 レイヤの中身の作り込み）
- グルーピング（拠点・ラック単位の枠）
- 更改シナリオの影響範囲を図上でハイライト

## フェーズ4: リファレンス管理と脆弱性の突合 ✅ 実装済み

### 型番リファレンス（EoL の正規化）
- EoL を機器ごとではなく**型番に紐づけて**管理（同じ型番が何台あっても1か所で更新）
- ベンダー+型番で自動解決。大文字小文字の揺れは吸収する
- 機器側に値があればそちらを優先（個体の延長保守などを上書きできる）
- **出典と情報取得日を必ず記録**。放置すれば古くなるデータなので、
  いつ時点の情報かを示せないと判断に使えない
- 取得日から一定期間（既定180日）を過ぎたら「要更新」を表示。
  リファレンス未登録の型番も一覧化する

### 脆弱性の突合
- 「ベンダー + 型番 + 稼働バージョン」から該当 CVE をマッチング
- **閉域環境を前提に、オフライン取り込みを唯一の経路とした**（外部通信は一切しない）
  - NVD 2.0 形式（CPE からバージョン範囲を組み立て）
  - CISA KEV 形式（実際に悪用が確認された脆弱性の印を付ける）
  - 簡易形式（ベンダー PSIRT を手で整理したもの。型番のワイルドカード指定に対応）
  - 形式はファイル名ではなく中身から自動判別する
- バージョン比較は semver ではなく自然順比較。`17.09.04` と `17.9.4`、
  `15.2(7)E6`、`21.4R3-S5.4` を正しく大小比較できる
- **何で一致したかを必ず表示**する（根拠を示せない判定は運用で使えない）
- OSバージョン未登録の機器は判定できないため、その台数を明示する
- 悪用確認済み（KEV）の該当は、最適化の指摘でも最優先で挙がる

### 今後の拡張候補
- オンライン同期のアダプタ（Cisco EoX API / NVD API / CISA KEV）。
  ネット接続可能な環境向けに、この取り込み経路の上に載せる形で足せる
- 推奨アップグレード先バージョンの管理と、更改シナリオへの連携
- ベンダー PSIRT の取り込み補助（HTML/PDF からの半自動抽出）

## フェーズ4.5: ベンダー資料と Config 生成の土台 ✅ 実装済み

### ベンダードキュメント
- コマンドリファレンス / マニュアルを、ベンダー・型番・**バージョン範囲**の3軸で管理
- 機器から「この機器で使える資料」を逆引きし、該当理由を必ず表示する
- 型番は空欄でベンダー全体、`C9500*` で前方一致（シリーズ共通資料）
- 実体は内容の SHA-256 でファイル領域に保管。同一内容は1つにまとまる
- 実体が無く URL だけの登録も可（社内ファイルサーバ参照など）

**古い版を消さない**のが設計上の約束。現場によっては古いバージョンが現役なので、
新版の登録は「後継へのリンクを張る」だけで、旧版の行はそのまま残る。
17.9 で動いている機器からは、17.12 の版が出た後も 17.9 向けの資料が引かれる。

### Config テンプレート
- 資料と同じ3軸で管理し、機器を選ぶとそのバージョンに合う候補だけが出る
- 根拠にしたマニュアルを紐付けられる
- Jinja2 記法。台帳・Config 取り込み済みの値（`device.hostname`、`interfaces`）を差し込める
- **生成するだけで実機には投入しない。** 未定義変数はエラー、範囲外の機器には警告

### 設計メモ（実装した方針）
- 打ち間違いを黙って空文字にすると壊れた config が出るので `StrictUndefined` で落とす
- 範囲外の機器への適用は禁止せず警告に留める（現場判断で流用したい場面があるため）
- テンプレートはサンドボックスで展開し、内部構造には触れさせない
- 資料の実体は DB に入れないので、**バックアップは DB とファイル領域の2系統**になる

### 今後の拡張候補
- テンプレートから投入手順書（作業前確認・投入・切り戻し）を通しで生成
- 現行 Config との差分プレビュー（生成結果を当てたら何が変わるか）
- 資料本文の全文検索（PDF テキスト抽出）と、コマンド単位での引き当て
- シナリオ（フェーズ1.7）と連携し、更改後の初期 Config をまとめて生成

## フェーズ4.7: 現行 / 将来 / 差分の Config 出し分け ✅ 実装済み

用途が3つあり、出したいものがそれぞれ違う。

- 現行フル … 機器故障時の復旧に使う
- 将来フル … 更改で入る新機種にそのまま投入する
- 差分   … 更改に合わせて既存機器に当てる

### 設計メモ（実装した方針）
- 差分が一番難しく、一番事故に近い。正しさを勘ではなく**作り方**で担保する：
  生成したコマンドを読み直して現行に当て直し、将来フルと一致するかを機械で確かめる。
  一致しなければコマンドを出さず、収束しなかった箇所を名指しで返す
- 生成経路と検証経路を分けてあるので、生成側の書き間違いが検証で落ちる
- テキストの行差分ではなく木で比較する（ブロック跨ぎ、`no` の扱い、値の書き換えで壊れるため）
- 順序が意味を持つブロック（ACL 等）は行単位で足し引きせず、必要なら消して入れ直す
- 切り戻しも生成し、同じ検証を通す
- 既定値を知らないという原理的な限界は隠さず警告に出す
- ランダム変形 20,000 通りで誤差分が出ないことを確認

### 今後の拡張候補
- 投入順序の最適化（管理経路に関わる行を最後に回す、依存関係で並べ替える）
- 作業手順書の生成（事前確認コマンド → 投入 → 事後確認 → 切り戻し）
- シナリオ（フェーズ1.7）から、更改対象機器の将来フルを一括生成
- 差分を当てた後の running-config を取り込んで、意図どおりになったかを突合

## フェーズ5: 更改支援

- 「今後N年で保守切れ・EoL を迎える機器」を年度別に集計
- 更改対象の影響範囲をトポロジ上でハイライト（その機器配下のノード）
- 更改案件のグルーピングと予算年度への割当（フェーズ1.7 のシナリオを年度軸に拡張する）
- トポロジ上での影響範囲の可視化（フェーズ3 と組み合わせる）

## 横断的に必要になるもの

- 認証・認可（まずはローカルアカウント、将来的に LDAP / OIDC）
- 変更履歴（誰がいつ何を変えたか）
- 期限アラートのメール / Webhook 通知
