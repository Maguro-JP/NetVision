# 運用手順書

導入後、日々どう使うかをまとめています。導入自体は [INSTALL.md](INSTALL.md) を参照してください。

---

## 全体の流れ

```
Config を集める ──▶ 取り込む ──▶ 台帳・トポロジが立ち上がる
                                      │
      EoL / 保守期限を登録 ───────────┤
      CVE を取り込む ─────────────────┤
                                      ▼
                    ダッシュボード / 更改支援 / 対処状況 で見る
                                      │
                                      ▼
                      更改・設定変更時に Config を生成
```

**このツールは機器に直接触りません。** 読むのはアップロードされたファイル、
設定変更は生成するだけです。投入は人が手で行います。

## 初期セットアップ（最初の1回）

### 1. Config を集める

**`show version` の出力を必ず一緒に取ってください。**
running-config だけでは型番が分かりません。型番はこのツールの軸で、EoL も脆弱性も
型番で引くため、無いと何も判定できません。

1ファイルにまとめて構いません。パーサは混在を読めます。

```
! ---- core-sw-01.txt ----
show version の出力          ← 型番・バージョン・シリアル
show inventory の出力        ← あればシリアルがより確実
show cdp neighbors detail    ← あれば結線が自動で引ける
running-config
```

| ベンダー | 対応 | 型番が取れる出力 |
|---|---|---|
| Cisco IOS / IOS-XE / NX-OS | ✅ | `show version`（Catalyst 2960 〜 9500 で確認済み） |
| Juniper Junos | ✅ | `show version` / `show chassis hardware` |
| Fortinet FortiOS | ✅ | `get system status` |
| NEC IX シリーズ | ✅ | `show version`（`IX Series IX2215 ...` の行） |
| NEC QX シリーズ | ✅ | `display version`（Comware ベース） |

文字コードは Shift_JIS でも UTF-8 でも構いません。

### 2. まとめて取り込む

「Configの取り込み」画面で、**「台帳に無い機器を Config から登録する」にチェック**して
ファイルをまとめて放り込みます。

```
core-sw-01.txt      新規登録   Cisco     C9500-40X   17.09.04a
edge-rt-01.txt      新規登録   Juniper   mx204       21.4R3-S5.4
fw-01.txt           新規登録   Fortinet  FGT100F     7.2.8
acc-sw-osaka-01.txt 未登録   → 型番が読み取れないため登録していません
```

**型番が読めないものは登録しません。** 判定できない機器が黙って増えるのを防ぐためです。
該当ファイルは `show version` を足して取り込み直してください。

### 3. トポロジを作る

「トポロジ図」→「Config から結線を作り直す」。LLDP / CDP から結線が引かれます。

- 両側から見えた結線は「確認済み」（実線）、片側だけは点線
- 足りないところは**手で線を引けます**（自動再推定しても消えません）
- ノードをドラッグして配置を整えると、その配置は保存されます

**VLAN / VRF で絞り込めます。** チェックを入れると、そのセグメントを持たない機器が
薄くなるので、「どこまで伸びているか」を図で確認できます。1つだけ選んで書き出すと、
そのセグメントだけの構成図になります。

トランクの許可 VLAN が両端で食い違っている結線、ネイティブ VLAN が片側だけ違う結線は
**線がオレンジになり、ラベルに ⚠ が付きます**。「繋がっているのに通らない」の典型なので、
図の上で気づけるようにしてあります。

**図は既定で動きません。** 開いた直後にうっかりドラッグして配置が崩れるのを防ぐため、
編集はロックしてあります。並べ替えるときはツールバーの「編集する」を押してください。
編集中は機器を動かす・線を引く・線の引き出し位置を変える、ができます。
**「配置を保存」を押すまで反映されません。**

**線はどの辺からでも出せます。** 機器の位置関係から自動で決めていますが、
線を選んで「上/下/左/右」を指定すれば固定できます（「自動」に戻せます）。
同じ辺に複数本来るときは、3か所に散らして重ならないようにしています。

**ポート名は機器の隣に出ます。** 1本の線に2つ並べると「左が上位」のような規則を
覚える必要が出て、図の向きが変わると逆に読んでしまうためです。

長いポート名で図が読めないときは、ツールバーの「ポート名」を切り替えてください。

| 表記 | 出るもの |
|---|---|
| 略記（既定） | `Te1/1/1` |
| 番号だけ | `1/1/1`（**種別名は機器の箱に出ます**。色も線のラベルと揃えてあります） |
| そのまま | `TenGigabitEthernet1/1/1` |

「線に沿わせる」で、ポート名を線の向きに合わせて回せます（逆さまにはなりません）。
この設定は SVG の書き出しにもそのまま反映されます。

**拠点で絞れます。** 拠点を選んで書き出すと、その拠点だけの構成図になります。
このとき、**拠点の外にある対向機器は破線の簡易表示で残ります**。線ごと消すと
上位への接続が無いように見えてしまうためです。相手の名前・拠点・ポートだけが出ます。

書き出した図では、**ポート名が機器や他のラベルに被らない**ように置き場所を選びます。
どうしても入らない場合は文字を短くします（重ねるより略す方がまし、という判断です）。
略した名前はブラウザで開いてマウスを乗せれば元の名前が出ます。

**図を資料に使うとき**は「図をファイルに出す（SVG）」から書き出してください。
スクリーンショットと違い、印刷や拡大で潰れず、Word / PowerPoint にそのまま貼れます。
構成が変わったら出し直すだけです。

**現場で使う図には「シンプル表示」**にチェックを入れてから書き出してください。
機器名と結線だけになり、型番・IP・保守状態・VLAN が載りません。作業手順書や
指差し確認で使う図に余計な情報が入っていると、読み違いのもとになります。

### VLAN の管理

| 画面 | 持っているもの |
|---|---|
| VLAN 台帳 | **人が書く**名称・用途・管理部署・サブネット |
| 機器ページのポート表 | **実機から読んだ**アクセス / ネイティブ / トランク許可 |

台帳に書いた内容は **Config を取り込み直しても上書きされません**。実機の名前とは
別に持っているので、食い違っていれば「機器側の設定が古い」と分かります。

VLAN が多い場合は「実機の名前で下書きを作る」で実機の VLAN 名を台帳に流し込んでから、
用途を書き足してください。既に書いてある行は触りません。

台帳の一覧には2つの印が出ます。

- **未登録** … 実機には居るのに台帳に無い VLAN。素性の分からないセグメントです
- **定義なし** … どの機器にも VLAN 定義が無いのに、トランクの許可には残っている状態。
  消し忘れであることが多いところです

### VRF（機器の中の仮想ルータ）

1台の中で経路表を分ける機能で、ベンダーによって呼び方が違います。

| ベンダー | 呼び方 | Config の書き方 |
|---|---|---|
| Cisco | VRF | `vrf definition NAME` / `ip vrf NAME` |
| NEC IX | VRF | `ip vrf NAME` |
| NEC QX（Comware） | VPN インスタンス | `ip vpn-instance NAME` |
| Juniper | routing-instance | `set routing-instances NAME instance-type virtual-router` |
| Fortinet | VDOM | `config vdom` / `edit NAME` |

**図の上で同じ線に見えても、VRF が違えば通信できません。** 「繋がっているのに通らない」
の原因として最初に確認したいところなので、トポロジ図で VRF を選んで絞り込めます。
同じ VRF 名で機器ごとに RD が違う場合は「RD 不一致」の印が出ます。

### 4. 保守期限・EoL を入れる

Config には入っていない情報なので、別途登録します。

- **既存の Excel 台帳がある場合** … 「台帳の取り込み」でそのまま読めます。列名は自動で対応付きます
- **EoL** … 「リファレンス管理」で**型番ごと**に登録します。同じ型番の全機器に一度で効きます

### 5. CVE を取り込む（任意）

閉域なので、ファイルを持ち込んで取り込みます。

| ソース | 入手先 | 備考 |
|---|---|---|
| CISA KEV | CISA の公開JSON | 小さい。**悪用確認済み**なので優先度判断に一番効く |
| NVD 2.0 | NIST NVD の公開JSON | 全量は大きいので年次ファイルを選ぶ |
| 簡易形式 | ベンダー PSIRT を手で整理 | 型番のワイルドカード指定に対応 |

取り込み後は必ず**「対処状況」→「該当状況を洗い直す」**を実行してください。
これを通していない限り「未対応ゼロ」は信用できません。

## 日常の運用

### 月次でやること

| やること | 画面 | 目的 |
|---|---|---|
| Config を再取り込み | Configの取り込み | 実機との差分を見る。変更履歴も残る |
| CVE ファイルを更新 | リファレンス管理 | 新しい脆弱性を取り込む |
| 該当状況を洗い直す | 対処状況 | 新しい該当・差し戻しを検出する |
| 未対応を潰す | 対処状況 | 悪用確認済み → 期限超過 の順に並んでいる |

### 年次でやること

| やること | 画面 |
|---|---|
| 更改計画の確認 | 更改支援（年度別の台数と概算） |
| 契約の見直し | 最適化の指摘（払わなくてよい保守費） |
| リファレンスの鮮度確認 | リファレンス管理（取得日が古いものは「要更新」） |

### Config を変更するとき

1. 「Config計画」で対象機器の計画を作る（既定で現行 Config のコピーから始まる）
2. 将来フルを編集する
3. **差分**タブで投入コマンドを確認する
   - 「✓ 収束を確認」が出ていること。出ていなければコマンドは出ません
   - 危険な操作（インターフェース削除、閉塞、ACL 作り直し）は警告が出ます
4. **切り戻し**タブの内容も控えてから投入する
5. 投入後、実機から Config を取り直して再取り込みし、意図どおりか確認する

**生成するだけで実機には投入しません。** 内容を確認して手で流し込んでください。

### 脆弱性に対処するとき

1. 「対処状況」で未対応を開く
2. 「対応版Config」で投入コマンドを出す
3. 投入後、実機の Config を取り込み直す
4. 「確認」ボタンで**現行 Config に設定が入っているか裏取り**する

「対処した」と申告しただけでは「済みだが未確認」として残ります。
裏取りまで済ませて初めて閉じたことになります。

> **暫定対処（設定で回避）は該当が消えません。** 機器のバージョンは変わらないためです。
> 恒久的に消すには修正版へ上げる必要があり、上げれば洗い直しで自動的に閉じます。

## バックアップ

### 1台完結モード

止めてから、データディレクトリごとコピーするだけです。

```bash
cp -r ~/.netvision ~/backup/netvision-$(date +%Y%m%d)
```

Windows の場合は `C:\Users\<ユーザー名>\.netvision` フォルダをコピーします。

### Docker Compose

**DB とファイル領域の2系統**が必要です。資料の実体は DB の外にあります。

```bash
docker compose exec db pg_dump -U netvision netvision > netvision-$(date +%Y%m%d).sql
docker run --rm -v netvision_documents:/d -v "$PWD:/out" alpine \
  tar czf /out/documents-$(date +%Y%m%d).tar.gz -C /d .
```

**復旧の手順も一度試しておいてください。** 取れているつもりで戻せないのが一番困ります。

## 版を上げる

1. ネット側で新しいバンドルを作る
2. 閉域へ持ち込む
3. **バックアップを取る**
4. 止める → 展開 → `./install.sh` → `./start.sh`

データディレクトリ（`~/.netvision`）は触らないので、そのまま引き継がれます。
スキーマの変更は起動時に自動で適用されます。

Docker Compose の場合は `docker compose down` → イメージ差し替え → `docker compose up -d`。
マイグレーションは起動時に自動適用されます。

## 困ったとき

| 症状 | 見るところ |
|---|---|
| Config が読めない / 型番が取れない | `show version` が含まれているか。文字コードが壊れていないか |
| 機器が登録されない | 「台帳に無い機器を Config から登録する」にチェックが入っているか |
| トポロジに線が出ない | CDP / LLDP の出力が Config に含まれているか。両側の機器が登録されているか |
| EoL が出ない | リファレンス管理に型番が登録されているか。ベンダー名の表記が合っているか |
| 未対応が 0 のまま | 「該当状況を洗い直す」を実行したか |
| 差分が出ない | 「収束しませんでした」の内容を確認。対処内容が機器の書式に合っているか |

Config のパーサはベンダーごとに分かれています（`backend/app/services/configparse/`）。
実機の出力で読めないパターンが出た場合は、その出力を控えておいてください。
**実データでしか分からない部分**なので、開発側に渡せば対応できます。

## いま無いもの（把握しておいてほしいこと）

| 無いもの | 影響 |
|---|---|
| **認証・認可** | URL を知っていれば誰でも全部見られる。既定で `127.0.0.1` に絞っているのはこのため |
| 変更者の記録 | 変更履歴は残るが「誰が」は埋まらない（認証が前提のため） |
| SSH での自動収集 | Config は手動アップロード。定期取得は別途仕組みが必要 |
| 洗い直しの自動実行 | 「該当状況を洗い直す」は手動。押し忘れると古い数字を見ることになる |

複数人で運用する段階になったら、**認証が最優先**になります。
